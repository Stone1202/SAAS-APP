## 补充内容注入

用户补充明确了三端定位：

> **小程序**：轻量知识传播 + 糖尿病食品交易 + 深入咨询入口→企微客服→引导安装APP  
> **APP**：平台完整业务前端（问诊/处方/商城/支付/营销/交易/直播/课程/慢病管理/档案管理/预警/血糖仪器链接）  
> **业务后台**：小程序+APP闭环流程支撑  
> **入驻方**：合作药房/OTC商家/器械商家

## 第二轮：跨部门讨论（基于v1+补充）

### 运营部（第二轮）

**发言**：
v1 中我们把小程序当作「内容+入口」，现在补充明确了小程序自身承担**糖尿病食品交易**，这意味着小程序不止是引流，它本身就是一个独立交易场景。

这意味着全病程管理的运营触点从原来的「微信端→APP」变成了：
```
小程序（知识+食品交易）──企微客服──→ APP（医疗+服务+商城）
       ↑                                      │
       └──── 数据回流（用户画像统一）─────────┘
```

关键运营新增动作：
- **小程序端运营**：科普内容运营 + 食品类目运营 + 限时活动（秒杀/拼团）
- **企微客服SOP**：小程序「深入咨询」按钮→自动分配企微客服→标准化话术→引导下载APP
- **APP承接**：企微引导来的用户自动标记渠道来源，新用户首屏个性化转化

**新增干预节点**：
- 干预点11：小程序浏览食品≥3次未下单 → 企微推送优惠券
- 干预点12：APP未安装（企微引导后24h） → 企微再次提醒+专属权益
- 干预点13：小程序→APP安装转化成功 → 首单立减+新客专享

**产品部质询**：小程序食品交易要自营还是平台撮合？这决定运营复杂度。

**运营部修正**：建议 Phase 1 自营（精选糖尿病食品SKU，100-200个），Phase 2 开放商家入驻。自营能控制品质和用户体验，且糖尿病食品用户对安全和品质极度敏感。

#### 新识别的核心业务规则

**多商户入驻模式**（业务部新增分析）：

参考领域知识（trade/order-flow + payment/wechat-pay），平台需设计三套入驻流程：

| 入驻类型 | 资质要求 | 商品类型 | 结算周期 | Phase |
|----------|----------|----------|----------|-------|
| 合作药房 | GSP证书+药品经营许可证+互联网药品信息服务资格证 | 处方药/OTC/器械 | T+7 | Phase 1 |
| OTC商家 | 药品经营许可证+品牌授权 | OTC药品 | T+7 | Phase 2 |
| 器械商家 | 医疗器械经营备案+品牌授权 | 血糖仪/CGM/血压计/试纸 | T+7 | Phase 1 |

**关键业务规则**：
- OTC/处方药需展示批准文号（国药准字）
- 医疗器械需展示注册证号（国械注准/国械注进）
- 禁售清单：精麻药品、注射剂（胰岛素等需处方，不直售）

#### 三端数据贯通规则

```
小程序用户 → 微信UnionID → APP用户关联
小程序交易数据 → 用户标签「食品偏好」→ APP商城个性化推荐
企微会话 → 客服标签 → APP医生端可见「患者关注点」
APP处方 → 处方中心RxID → 合作药房调配 → 物流追踪
血糖数据(CGM) → 慢病管理 → 食品推荐「根据血糖状态推荐合适食品」
```

**设计部质询**：小程序和APP都卖东西，用户会不会混淆？为什么有的东西在小程序买，有的在APP买？

**业务部修正**：明确差异化定位——
- 小程序：**轻决策**食品（控糖饼干/代餐/低GI零食），客单价<200元，即看即买
- APP商城：**重决策**医药（处方药/血糖仪/医疗器械），客单价>200元，需问诊+处方
- 小程序设置「APP专享」引导，「该商品需医生指导使用，前往APP咨询后购买」

### 设计部（第二轮）

**发言**：
三端设计需要统一的**糖尿病健康设计语言**，但每端体验重点不同：

#### 小程序设计重点
- **轻快**：页面加载<1.5s，核心路径≤3步
- **信任感**：食品详情页强制展示「营养成分表」「GI值」「适宜人群/禁忌」
- **咨询引导**：全站统一的悬浮「咨询专家」按钮（绿色+心跳动效），点击→企微客服
- **APP引导**：下单成功后弹层「下载APP享完整健康管理」，含利益点（血糖监测/专属医生）

#### APP设计重点
- **专业感**：深层体验，质感优于速度
- **首页重构**：从单一病程仪表盘→三Tab首页（健康/商城/我的）
  - Tab1 健康：血糖天气+用药提醒+病程进度+待办
  - Tab2 商城：个性化推荐+药房/OTC/器械分类+直播入口+课程入口
  - Tab3 我的：订单+档案+优惠券+设置
- **商城设计**：商品详情页含「药监局备案信息」「批准文号/注册证号」「用药指南」，处方药详情→引导问诊
- **直播设计**：APP内嵌直播间（医生直播+带货直播两种模式），支持送礼物+商品卡片+@医生提问

#### 设计约束（新增）

| 场景 | 约束 |
|------|------|
| 小程序食品详情 | 必须展示GI值（升糖指数），低GI绿色标/高GI红色标 |
| APP药品详情 | 必须展示批准文号（国药准字），处方药标注「凭处方购买」 |
| 医疗器械详情 | 必须展示注册证号，使用视频教程入口 |
| 直播带货 | 医药类直播需药师实时审核，延迟30s播出 |

**业务部质询**：直播带货卖药合规吗？

**设计部修正**：严格禁止直播卖处方药。直播分为两种：
- 医生科普直播：纯内容，可推荐健康生活方式，可关联课程，不可售卖药品
- 带货直播：仅限非药品商品（控糖食品/血糖仪/血压计），不涉及OTC/处方药
- 所有直播内容需先审后播（延迟30s），医药直播需执业药师实时监督

#### 关键集成链路（新增）

```
小程序食品下单→微信支付→order-service→商品发货→物流追踪
APP商城下单→聚合支付(payment-gateway)→order-service→处方校验(处方药)→药房打单→物流

直播→推流(RTMP)→CDN→APP内嵌播放器→商品卡片→加购→order-service
企微客服→scrm-gateway→消息同步→用户标签→SCRM后台
```

**测试部质询**：三端数据一致性如何保证？例如小程序下单的食品订单，APP订单中心能否实时看到？

**开发部修正**：
- 订单数据统一存储在 order-service（单一数据源）
- 小程序和APP通过同一 UnionID 关联用户
- 订单查询通过 API 实时拉取，不依赖缓存
- 支付回调使用幂等键防重，确保订单状态一致
