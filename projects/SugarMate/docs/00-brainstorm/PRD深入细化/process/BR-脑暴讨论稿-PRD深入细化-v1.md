### 状态机补充（Q29）

**需要全部补全，PRD V2.0强制包含以下状态机：**

| # | 状态机 | 优先级 | 说明 |
|----|--------|--------|------|
| 1 | 问诊订单状态机 | P0 | 待支付→已支付→接诊中→问诊中→已完成/已取消/已退款 |
| 2 | 电子处方状态机 | P0 | 待开具→待审核→审核通过/驳回→已签名→已使用/已过期 |
| 3 | 商城订单状态机 | P0 | 待支付→已支付→待发货→已发货→运输中→已签收→已完成/售后中/已退款 |
| 4 | **分账与退款状态机** | P0 | 结算系统参考：分账状态（未分账/部分分账/全部分账）× 提现状态（待提现/提现中/已提现）× 退款场景（四场景路由） |
| 5 | 商家入驻状态机 | P1 | 已申请→资质初审→现场核查→终审→已入驻/已驳回/已冻结 |
| 6 | 会员状态机 | P1 | 普通→付费会员→已过期→续费中→已注销 |

### 结算体系关键参考（来自渠道分佣清结算系统UML）

SugarMate分账体系需设计以下机制：

1. **分账模式**：自营收入归平台 + 平台商品按比例分账（供应商/平台/分销员）
2. **保障金机制**：分账时从供应商货款扣留X%冻结，确认收货释放50%+售后期满释放50%，退款时保障金优先冲抵
3. **四种退款场景**：未分账(T+0直退) / 部分分账(T+0~T+1回拨) / 全额分账-未提现(T+1~T+3全回拨) / 全额分账-已提现(T+3~T+7+保障金+垫付+追缴)
4. **三种清分时机**：T+1快速清分(虚拟商品) / 微信发货管控清分(实物商品) / 微信非发货管控清分
5. **资金补偿优先级**：①保障金释放 → ②平台垫付 → ③追缴回收 → ④坏账核销
6. **风控规则**：提现冷却期T+1 + 保障金扣留比例按品类配置 + 垫付上限 + 挂账阈值熔断
7. **支付通道**：结合易宝支付领域知识设计分账接口

### 【P0-1】Q30：PASS审方系统升级（合规红线）

#### 行业标准与法规依据

| 来源 | 核心要求 |
|------|---------|
| 《医疗机构处方审核规范》（2018） | 所有处方**必须**经过审核才能调配，审核内容包括「规范性+适宜性」两大类 |
| 《互联网诊疗管理办法》（2022修订） | 互联网医院应建立在线处方审核制度，配备专职药师 |
| 2023专家共识《互联网医疗智能辅助审方系统》 | 标准模式为 **「智能筛查+人工复核」双重机制** |
| 美康PASS系统（行业事实标准） | 市占率超70%，包含11类强制拦截+12类风险提醒 |
| 《药品管理法》2019修订 | 对药师未审核处方即调配的，最高可吊销执业证书 |

#### 行业对标

| 平台 | 审方机制 |
|------|---------|
| 京东健康 | PASS系统+专职药师团队，7×24小时轮班，夜间自动路由 |
| 阿里健康 | 自研审方引擎+AI辅助，审方超时5分钟自动升级 |
| 微医 | PASS+区域审方中心，支持跨院处方互审 |
| 叮当快药 | 自有药师团队，处方药100%审方，超时15分钟自动驳回 |

#### 决策选项

**选项A：完整PASS审方（推荐✅）**

将FN-SUG-APP-014升级为完整「PASS智能审方」，包含：
- 23条规则引擎（11拦截+12提醒）
- 智能筛查→药师复核 双通道
- 审方超时自动流转
- 审方日志（留存≥3年，合规要求）
- 夜间/节假日排班机制
- PASS系统不可用降级策略（临时转人工兜底）

| 维度 | 评估 |
|------|------|
| 实施成本 | 中高（需对接PASS系统或自研审方引擎） |
| 合规必要性 | **必须**——处方未经审核调配属违法行为 |
| V1.0交付压力 | 中等（核心规则可V1.0先上，12条提醒可V1.1补充） |
| 竞争壁垒 | 高——审方质量直接影响医疗安全口碑 |

**选项B：简化审方（不推荐⚠️）**

审方规则简化为3~5条（仅做药物禁忌/过敏/剂量基础检查），药师手动审核其余。

| 维度 | 评估 |
|------|------|
| 实施成本 | 低 |
| 合规风险 | 高——无法满足《处方审核规范》的完整性要求 |
| 医疗安全风险 | 高——漏审可能导致用药事故 |

**选项C：外购PASS SaaS（轻量方案）**

直接采购美康/天际健康的SaaS审方服务，API对接。

| 维度 | 评估 |
|------|------|
| 实施成本 | 低（按处方量付费，约0.5~1元/次） |
| 上线速度 | 快（2~4周对接完成） |
| 长期成本 | 中等（量大后成本线性增长） |
| 定制化 | 有限 |

#### 🏆 推荐方案 → 🔒 **用户已确认：方案A**

**V1.0选A：基础审方（药师人审为主+基础拦截清单），V1.1对接专业审方系统**

> **📌 关于「为什么涉及SaaS」的备注**：
> PASS审方的核心不是写代码逻辑，而是需要**一个持续更新的药品知识库**（药物相互作用数十万条、数万种药品说明书、NMPA新批药品持续更新）。SugarMate自己建不了这个知识库——需要专业医药数据公司长期维护。"外购SaaS"是指对接成熟的第三方审方云服务API（如美康/天际健康），借用其专业药品数据库能力；"自研"也不是从零写代码，而是购买药品数据库授权后自建审方规则引擎。**两种方案都依赖外部数据源**，区别在于审方逻辑是调第三方API还是自己写。
>
> **V1.0方案A具体内容**：
> 1. 处方提交后 → 药师人工审核（主要手段）
> 2. 系统维护**基础拦截清单**（约5~8条硬规则）：药物过敏禁忌 / 超剂量预警 / 重复用药检测 / 给药途径错误 / 孕期哺乳期禁忌 / 儿童老年禁忌 / 药物-疾病禁忌 / 肝肾功能禁忌
> 3. 审方日志留存≥3年（合规硬要求）
> 4. 审方超时自动升级（如15分钟未审核自动提醒另一位药师）
> 5. PASS系统不可用时完全转人工兜底
>
> **V1.1升级方向**：处方量增大后，对接专业审方系统（自研或SaaS），补全23条完整规则引擎（11拦截+12提醒）+智能筛查+AI辅助
>
> **选择方案A的考量**：
> 1. V1.0处方量小，药师人审+基础规则足够保障安全底线
> 2. 避免V1.0为SaaS支付按量费用但无处方量的尴尬
> 3. V1.1根据实际处方数据和药品目录特征，再决定自研还是SaaS
> 4. 审方日志留存≥3年是**刚性合规要求**，V1.0就必须满足

### 【P0-3】Q33：精麻药品管制（合规红线）

#### 法规依据

| 来源 | 核心要求 |
|------|---------|
| 《麻醉药品和精神药品管理条例》（2025.1.20修订生效） | 明确药/非药用分类管理，处方必须使用专用处方笺，执业医师须经精麻药品培训考核合格 |
| 2026年卫健委征求意见稿 | 开处方时**须告知患者该药品可能涉毒**的法律属性，强化知情同意 |
| 互联网医院特殊限制 | 互联网医院开具精麻药品处方**存在重大法律争议**——多数地区要求面诊后开具 |

#### 糖友实际场景判断

糖尿病常用药中涉及精麻管制的极少：
- **胰岛素类**：不属于精麻药品
- **二甲双胍**：不属于精麻药品
- **SGLT-2/DPP-4/GLP-1**：不属于精麻药品
- 可能涉及的：**强效镇痛药**（糖尿病神经病变疼痛，如曲马多——二类精神药品）

#### 决策选项

**选项A：SugarMate不涉及精麻药品（推荐✅）**

V1.0商品库**禁止收录**任何精麻管制类药品。如果医生有开具需求（如神经病变疼痛），引导患者线下就诊开具。

| 维度 | 评估 |
|------|------|
| 合规风险 | 零 |
| 业务影响 | 极小——糖友常用药99%不在管制目录内 |
| 实施复杂度 | 极低——商品库维护时做品类过滤即可 |

**选项B：支持二类精神药品（如曲马多）**

需额外投入：面诊确认→专用处方→双因子认证→药监上报。

| 维度 | 评估 |
|------|------|
| 合规风险 | 高——互联网医院开具精麻药品法律灰色地带 |
| 执行成本 | 很高 |

#### 🏆 推荐方案 → 更符合商业实际

**选项A：V1.0~V2.0均不涉及精麻药品，但有替代方案让业务不受影响**

> **商业落地核心**：糖友神经病变疼痛需要镇痛药——但精麻药品（曲马多等二类精神药品）的合规成本远大于商业收益。真正的商业落地方案是：**不碰精麻药品，但提供合法替代品的供应**。

**替代药品清单**（全部非管制，可自由销售）：

| 替代药品 | 适应症 | 管制状态 | 糖友常用度 |
|----------|--------|---------|-----------|
| 加巴喷丁 | 神经病变疼痛一线药 | ✅ 非管制（中国） | ⭐⭐⭐⭐⭐ |
| 普瑞巴林 | 神经病变疼痛一线药 | ✅ 非管制（中国） | ⭐⭐⭐⭐⭐ |
| 甲钴胺 | 神经营养修复 | ✅ 非管制（OTC） | ⭐⭐⭐⭐⭐ |
| 硫辛酸 | 抗氧化/神经保护 | ✅ 非管制 | ⭐⭐⭐⭐ |
| 度洛西汀 | 神经病变疼痛（SNRI类） | ✅ 非管制 | ⭐⭐⭐ |

> **关键发现**：糖尿病神经病变疼痛的**一线治疗药物（加巴喷丁/普瑞巴林）在中国均不属于精麻管制**。这意味着SugarMate完全可以覆盖糖友99.9%的镇痛需求而无需触碰精麻红线。

**V1.0落地动作**：
1. 新增 **BR-SUG-020 精麻药品禁售规则**：商品库维护精麻管制目录→商品上架自动拦截→医生开方时精麻药品灰显+提示「本平台不经营精麻管制药品，请到线下医院开具」
2. **非管制品类优先上架**：加巴喷丁/普瑞巴林/甲钴胺/硫辛酸/度洛西汀 → 作为神经营养+疼痛管理专区
3. **内容侧同步教育**：科普文章覆盖「糖尿病神经病变疼痛的正确用药」→ 用户认知提升=购药转化提升

> **商业思考**：「不涉及精麻药品」不是功能缺失，而是**主动规避一个V1.0完全不需要的法律深水区**。把精力放在优化非管制替代药品的供应链和价格上，ROI远高于为精麻合规投资。

### 【P0-4】合规红线R2：首诊面诊判定（合规红线）

#### 法规依据

| 来源 | 核心要求 |
|------|---------|
| 《互联网诊疗管理办法（试行）》2018 | 互联网诊疗只能对**部分常见病、慢性病复诊**开展 |
| 《互联网医院管理办法》2022 | 接诊医生**应通过在线调阅患者就诊记录或根据患者提供的病历资料，判断是否符合复诊条件** |
| 2025两会动向 | 卫健委释放信号：**可能放开部分专科互联网首诊**（儿科先试点），但糖尿病目前不在放开范围 |
| 上海2025管理办法 | 明确「不得对首诊患者开展互联网诊疗」，复诊认定需「患者提供6个月内在实体医疗机构的病历资料」 |

#### 决策选项

**选项A：强制首诊/复诊判定+首诊引导线下（推荐✅）**

- 问诊入口增加**首诊/复诊询问**（首次使用=首诊）
- 首诊用户：显示「首次就诊请先到线下医院面诊」+ 推荐附近内分泌科医院（高德/百度地图）
- 复诊用户：可在线问诊，需上传6个月内就诊记录
- 后续通过健康档案有无历史就诊记录自动判断

| 维度 | 评估 |
|------|------|
| 合规 | ✅ 完全满足 |
| 用户体验 | 首诊用户会流失，但合规优先 |
| 实施成本 | 低——主要是流程判断+地图推荐 |

**选项B：弱化判定，让医生自行判断**

不设强制判定，由接诊医生在问诊过程中自行判断首诊/复诊。

| 维度 | 评估 |
|------|------|
| 合规风险 | 高——如果出事追查，平台承担责任 |
| 用户体验 | 好 |

#### 🏆 推荐方案 → 更符合商业实际

**选项A：强制判定——但把它做成获客引擎而非流失漏斗**

> **商业落地核心**：合规要求首诊用户不能在线问诊→表面上首诊用户流失了。但聪明的做法是：**把首诊面诊的强制引导变成线下→线上的获客闭环**。不是拦截用户，而是给用户一个「先线下确诊→再回来享受便捷复诊」的明确路径，同时在这个过程中收集用户数据、建立信任。

**V1.0具体落地设计**（4步转化漏斗）：

```
用户点击「在线问诊」
    ↓
Step1 智能判定（0摩擦）
    ├─ 系统自动检查：有没有历史就诊记录？
    │   ├─ 有 → 直接进入问诊（老用户无感知）
    │   └─ 无 → 进入Step2
    ↓
Step2 引导页（商业转化起点）
    ├─ 「为了您的用药安全，首次诊疗请先到正规医院面诊确诊」
    ├─ 【附近医院推荐】（高德/百度地图，筛选内分泌科）
    ├─ 【病情自查工具】（填写症状→生成就诊清单→打印带到医院）
    ├─ 【就诊清单】（应该挂什么科/带什么资料/问医生什么问题）
    └─ 【就诊回来后继续】（保存当前状态，回来后继续）
    ↓
Step3 线下就诊后回归
    ├─ 用户回来后上传：诊断证明/处方/病历（OCR识别）
    ├─ 系统自动录入健康档案（病种/用药方案/主治医生）
    ├─ 自动标记为「复诊用户」→ 后续无限次在线问诊
    └─ 触发「欢迎回来」引导：开始首次在线复诊
    ↓
Step4 复诊转化
    ├─ 医生接诊时自动显示：线下诊断结果+用药方案
    ├─ 医生确认病情稳定→开具电子处方
    └─ 首次复诊成功→标记「核心用户」→触发会员推荐
```

> **关键商业设计**：
> - Step2的「病情自查工具」和「就诊清单」是**信任钩子**——用户拿着你给的工具去医院，回来后会记住你的价值
> - Step3的OCR识别诊断证明是实现「线下→线上」转化闭环的**技术关键**——降低用户手动录入的摩擦
> - 转化率预估：首诊用户中约30~40%会在1~3个月内回归（糖尿病患者复诊频率高，每月1次是常态）
> - **这不是流失，是延时转化**

**实施成本**：
- 一次开发成本：约5~8人日（判定逻辑2天+引导页2天+OCR对接2天+回归流程2天）
- 地图API：高德/百度免费额度即可满足
- 无需新增独立FN，融入APP-004/005即可

**BR-SUG-023 首诊面诊规则**内容：判定规则（有无历史就诊记录/有无上传诊断证明）+ 首诊引导规则 + 复诊开放规则 + 6个月就诊记录有效期规则

### 【P0-5】合规红线R5：个人数据管理（个保法合规）

#### 法规依据

#### 决策选项

**选项A：完整数据管理（推荐✅）**

新增 **FN-SUG-APP-056 个人数据管理**（P0），包含：

- 数据删除：分级删除（基础资料/健康档案/全部数据）
- 合规保留期后物理删除（问诊记录≥3年，处方记录≥1年）
- 数据处理记录查询（谁在什么时间因为什么目的访问了你的数据）
- 账号注销（已有APP-003覆盖）

| 维度 | 评估 |
|------|------|
| 实施成本 | 中等（2周开发） |
| 合规必要性 | **必须**——PIPL 2021已生效，罚则严厉 |

**选项B：仅做账号注销，不做数据导出/删除**

| 维度 | 评估 |
|------|------|
| 合规风险 | 非常高——违反PIPL第45/47条 |

#### 🏆 推荐方案 → 更符合商业实际

**选项A：V1.0必须做，但用「最小合规成本」而非「大而全的用户体验」**

> **商业落地核心**：《个保法》要求必须有数据导出和删除功能——但V1.0不需要做成支付宝那种精美的「个人信息下载」体验。实际上，中国互联网医疗平台在数据管理上都做得**极简**——因为主动导出数据的用户<0.1%。商业上正确的做法是：**合规底线做到位（避免法律风险），体验做到够用（不投入过多资源）**。

**V1.0最小合规方案**（1个FN，1.5周开发）：

```
FN-SUG-APP-056 个人数据管理（P0）
├─ 功能1：数据导出（合规底线）
│   ├─ 用户申请→后台生成JSON压缩包→48小时内短信通知下载
│   ├─ 包含：健康档案+问诊记录+处方记录+订单记录
│   └─ 格式：JSON（机器可读，合规要求）+ PDF摘要（用户可读）
├─ 功能2：数据删除（合规底线）
│   ├─ 分级删除：基础资料 / 健康档案 / 全部数据
│   ├─ 合规保留期内数据暂不物理删除（问诊记录≥3年/处方≥1年）但停止使用
│   └─ 保留期满后自动物理删除
├─ 功能3：隐私授权管理
│   └─ 查看/撤回已授权的数据使用场景（融入已有APP-003）
└─ APP入口：「我的→设置→隐私管理」
```

> **为什么不做「实时导出」「精美报告」「数据可携带权转移」？**
> - V1.0用户量<1万，主动导出数据的用户预计<10人
> - 行业对标：京东健康的数据导出也是「提交申请→等待处理」，没有实时一键导出
> - 个保法要求的是「提供途径」，没有要求「即时响应」
> - **反过来想**：如果V1.0真因为数据导出被用户投诉或监管处罚，那说明产品已经成功了（有足够多用户）→那时候再优化也来得及
> - V1.0抢占的资源应该放在「让更多用户愿意把数据交给你」，而不是「帮现有用户把数据拿走」

**投入产出比**：
- 开发量：约6~8人日（导出逻辑3天+删除逻辑2天+授权管理2天+UI 1天）
- 合规价值：满足个保法第45/47条底线要求，避免最高5000万或营业额5%的罚款
- 用户体验价值：低（主动使用率<0.1%），但不做=违法

### 【P1-2】Q36：用户旅程引擎

#### 行业实践

这不是一个「要么做要么不做」的功能——所有头部产品都有某种形式的旅程阶段管理：

| 平台 | 实现方式 |
|------|---------|
| Keep | 新手引导→进阶训练→达人，首页动态变化 |
| 小红书 | 兴趣标签→内容推荐→社区参与，冷启动→活跃→贡献 |
| 平安好医生 | 健康档案→风险评估→个性化首页（风险人群推荐问诊，健康人群推荐科普） |
| 微医 | 按就诊频次自动调整首页模块优先级 |

#### 核心价值

对于SugarMate来说，旅程引擎解决一个**核心体验问题**：

> 同一用户在不同阶段的首页应该是不同的——
> - 刚注册（兴趣期）：应该优先引导完成健康档案、了解服务
> - 开始问诊（体验期）：优先展示医生推荐和问诊入口
> - 规律监测（使用期）：首页C位是血糖数据和用药提醒
> - 参与社区（忠诚期）：首页feed应该包含社区内容和课程

#### 决策选项

**选项A：V1.0硬编码→V1.1引擎化**

V1.0不做引擎，通过简单的if-else规则控制首页模块显示（如注册≤3天展示引导模块）；V1.1再做完整引擎。

**选项B：V1.0直接做引擎**

一次性投入建立完整的旅程阶段定义→识别→动态路由体系。

| 维度 | 选项A（渐进） | 选项B（一步到位） |
|------|------------|----------------|
| V1.0开发量 | 小（3~5条规则） | 大（引擎+5阶段定义+个性化路由） |
| V1.0体验 | 基本可用 | 优秀 |
| 远期扩展性 | 需重构 | 好 |

#### 🏆 推荐方案 → 更符合商业实际

**选项A：V1.0硬编码→V1.1引擎化——但V1.0的硬编码不是「随便写几个if」而是「基于4个关键商业事件的精准触发」**

> **商业落地核心**：旅程引擎的本质是**在正确的时间给正确的人看正确的内容以最大化转化率**。V1.0不需要复杂的ML引擎，但需要精准识别用户当前所处的「商业转化节点」。糖友用户有4个关键转化节点，每个节点触发不同的首页展示。

**V1.0硬编码方案**（不是「新用户看A/老用户看B」的粗糙二分，而是4事件驱动的精准路由）：

```
用户状态判断（基于数据而非猜测，约3~5人日开发）

┌──────────────────────────────────────────────────────┐
│ 事件1：首次完成血糖记录                              │
│ 触发条件：健康档案中血糖数据=1条                      │
│ 首页变化：                                          │
│   ├─ C位模块：「血糖趋势图」（鼓励持续记录）           │
│   ├─ 第二屏：「用药提醒设置」（血糖记录用户最需要）     │
│   └─ Banner：「饮食记录帮您控糖」（交叉引流APP功能）    │
│ 商业价值：血糖记录→用药提醒→购药转化率提升20~30%       │
├──────────────────────────────────────────────────────┤
│ 事件2：首次完成在线问诊                              │
│ 触发条件：问诊订单状态=「已完成」                     │
│ 首页变化：                                          │
│   ├─ C位模块：「我的处方」（有处方）/「健康报告」（无处方）│
│   ├─ 第二屏：「复诊提醒」（问诊7天后推送复诊入口）      │
│   └─ 医生卡片：「再次咨询XXX医生」                     │
│ 商业价值：复诊转化率提升40%+（糖尿病患者需每月复诊）    │
├──────────────────────────────────────────────────────┤
│ 事件3：首次完成购药                                  │
│ 触发条件：商城订单状态=「已完成」                     │
│ 首页变化：                                          │
│   ├─ C位模块：「用药日历」（按时吃药的视觉激励）        │
│   ├─ 第二屏：「续方提醒」（药品剩余天数倒计时）          │
│   └─ 交叉推荐：「您可能也需要...」（关联健康商品）       │
│ 商业价值：复购率提升25%+                              │
├──────────────────────────────────────────────────────┤
│ 事件4：连续7天未打开APP（沉默预警）                   │
│ 触发条件：last_active > 7天                          │
│ 首页变化：                                          │
│   ├─ C位模块：「您的血糖还好吗？」→ 引导记录血糖        │
│   └─ Push+企微双通道召回（已在SCRM-005设计）           │
│ 商业价值：沉默召回率15~20%                            │
└──────────────────────────────────────────────────────┘

默认状态（无任何事件触发）：标准首页（问诊入口+商城推荐+科普内容）
```

> **为什么这个方案优于简单的「新用户/老用户」二分？**
> - 「新用户/老用户」是按时间维度分——但一个注册30天但什么都没做的用户和他的第1天没有区别
> - 「4事件触发」是按行为维度分——用户做了什么就给他看什么，精准度远超时间二分
> - 事件之间可以叠加——同时触发了「完成购药」+「7天未打开」→首页展示用药日历+召回引导
> - 开发量只比简单二分多1~2人日，但转化提升效果可能翻倍

**V1.1引擎化升级方向**：
- 从4事件→N事件扩展（社区发帖/课程完成/家属绑定/CGM连接等）
- 从硬编码→可配置规则引擎（运营后台可调整触发条件和展示内容）
- 从单事件→事件组合（AB同时发生→自定义路由）
- 引入A/B实验（测试不同展示内容对转化的影响）

**不做的事**：
- ❌ 不做ML推荐模型（V2.0考虑）
- ❌ 不做全旅程6阶段自动识别（V1.1做简化版）
- ❌ 不做跨端旅程状态贯通（V1.0只做APP端）

### 【P1-3】Q38：渠道归因分析

#### 行业对标

| 平台 | 实现方式 |
|------|---------|
| 字节跳动 | UTM参数+自有归因引擎（巨量引擎） |
| 微信生态 | 小程序scene参数+wtag+二维码参数归因 |
| 行业标准 | 首次触达归因/末次触达归因/线性归因/时间衰减归因 |

#### 核心价值

支撑SugarMate战略目标：**获客成本≤30元/人**。没有归因意味着：
- 不知道哪个渠道来的用户质量好
- 不知道哪类内容转化率高
- 无法优化获客预算分配

#### 决策选项

**选项A：与PC-011数据看板合并（推荐✅）**

不独立为FN，作为PC-011「数据看板与报表」的分项指标，在数据看板中增加「渠道分析」板块。

**选项B：独立FN**

新增FN-SUG-PC-015「渠道归因分析」独立管理。

| 维度 | 选项A（合并） | 选项B（独立） |
|------|------------|-------------|
| 管理复杂度 | 低 | 高 |
| 功能深度 | 基础（渠道-注册-首单转化率） | 深度（多模型归因/LTV预测） |
| V1.0可行性 | 高 | 中 |

#### 🏆 推荐方案 → 更符合商业实际

**选项A：不独立FN，但用微信原生能力零成本实现归因——这才是最接地气的落地**

> **商业落地核心**：做渠道归因最忌讳的是「花3周做一个归因系统，结果发现小程序场景值（scene）就能搞定90%的需求」。在微信生态中，小程序自带完整的渠道追踪能力——不需要自建归因引擎，只需要**用好微信原生参数+UnionID映射**。

**V1.0零成本归因方案**（基于微信原生能力）：

```
渠道标识体系（零开发，纯配置）：
├─ 微信群：群二维码带参（微信原生支持）
│   └─ 用户扫码→小程序scene=1047（群聊会话）→自动记录来源群
├─ 公众号文章：文章内链接带?channel=xxx参数
│   └─ 用户点击→小程序scene+channel参数→记录来源文章
├─ 视频号直播：直播带小程序卡片（微信原生）
│   └─ 用户点击→小程序scene=1178（视频号直播）→自动记录来源直播间
├─ 朋友圈广告：广告落地页→小程序（微信广告原生归因）
│   └─ 用户点击→广告后台直接统计曝光/点击/转化（不需要自建）
├─ 地推活码：带参数的太阳码（微信原生支持）
│   └─ 用户扫码→小程序scene=1047+自定义参数→记录来源地推员
└─ 搜索：小程序搜索scene=1001→记录搜索来源
```

**PC-011数据看板「渠道分析」板块**（在已有FN上追加，约2人日）：

| 看板指标 | 数据来源 | 开发方式 |
|----------|---------|---------|
| 各渠道注册数 | 小程序scene参数+APP首次登录关联UnionID | SQL聚合 |
| 各渠道首单转化率 | 注册渠道×首单用户交集 | SQL JOIN |
| 各渠道用户LTV（30天） | 注册渠道×30天内GMV累计 | SQL窗口函数 |
| 各渠道获客成本 | 渠道费用手动录入 / 广告API自动拉取 | 混合 |
| 渠道质量评分 | (转化率×0.4 + LTV×0.4 + 留存率×0.2) | 计算公式 |

> **为什么不在V1.0做独立归因FN？**
> - 微信原生归因已经覆盖了SugarMate 90%的获客场景（社群/公众号/视频号/朋友圈广告）
> - 唯一需要自建的是「UnionID映射打通小程序→APP」，而MP-009正在做这个
> - 独立归因系统的核心价值（多触点归因模型/归因窗口自定义/离线归因）在V1.0根本不适用——因为用户量小到每个渠道只有几十上百人，任何归因模型都不具备统计显著性

- ⚠️ UnionID映射（MP-009）是跨端归因的**基础依赖**——MP-009延期=归因延期

### 【P1-4】Q39：医生结算双轨体系

#### 行业标杆对比

| 模式 | 代表平台 | 结算方式 |
|------|---------|---------|
| **纯签约医生**（底薪+绩效） | 微医（早期） | — |
| **纯入驻医生**（只分润） | 好大夫在线 | 问诊费平台抽成20~30%，可提现门槛100元 |
| **混合模式**（签约+入驻） | 京东健康 | 签约医生：底薪+问诊绩效+处方奖金；入驻医生：分润，T+7结算 |
| **医生集团模式** | 企鹅杏仁 | 医生按科室组成集团→平台与集团结算→集团内部分配 |

#### SugarMate的特殊性

SugarMate是**自营+平台混合**：
- 自营医生团队 = 签约医生（底薪+绩效）
- 平台入驻医生 = 分润模式

两套体系的结算逻辑、周期、审批流程完全不同。

#### 决策选项

**选项A：合并入PC-013「财务审核与对账」（推荐✅）**

不独立为FN，医生结算逻辑作为PC-013的子模块。

**选项B：独立FN**

新增FN-SUG-PC-016「医生结算管理」。

| 维度 | 选项A（合并） | 选项B（独立） |
|------|------------|-------------|
| V1.0医生规模 | 小（签约10~20人+入驻30~50人） | 合并足够 |
| 结算复杂度 | 较高（两套逻辑） | 合并后PC-013可能臃肿 |
| 财务统一性 | ✅ 统一财务管理 | ⚠️ 医生结算和商户结算分离 |

#### 🏆 推荐方案 → 更符合商业实际

**选项A：V1.0合并入PC-013——但结算方式不是「建系统」，而是「财务手动+系统记录」**

> **商业落地核心**：V1.0医生就10~30人（签约10~20+入驻10~20），月结算单不到30笔——为30笔结算建一个系统是不划算的。行业现实是：**大部分B轮前的互联网医疗平台，医生结算都是财务Excel+银行转账**。正确的产品策略是：系统做好**数据记录**（每个医生看了多少诊/开了多少方/卖了多少药），结算动作留给财务手动处理。

**V1.0务实方案**（系统做记录，财务做结算）：

```
PC-013「财务审核与对账」中新增「医生结算」子模块

系统负责（自动化）：
├─ 自动采集：每个医生的问诊量/处方量/满意度评分（来自订单系统）
├─ 自动计算：签约医生绩效工资（底薪+问诊提成×1.5元/单+处方提成×1元/单+满意度≥4.5奖金200元）
├─ 自动计算：入驻医生分润（问诊收入×平台抽成30%，结算周期月结）
├─ 生成「结算预览单」（Excel格式，含明细+汇总）
└─ 结算审批流（PC-013已有的审批流复用）

财务手动（每月1次，工作量≈2小时）：
├─ 审核结算预览单
├─ 手动打款（银行转账/微信转账）
├─ 在系统中标记「已结算」
└─ 归档结算单（PDF）
```

> **为什么不自建自动打款？**
> - V1.0 10~30个医生，财务手动打款每月2小时——建自动打款系统需2~3周
> - 自动打款需要对接银行代发工资接口——又是一笔接口费+合规审批
> - 只要系统记录了数据+生成了结算预览单，财务手动打款的出错概率极低（30笔vs300笔）
> - **批量打款的触发条件**：医生数>50人 or 月结算>100笔 → V1.1再上自动打款
> - **参考**：好大夫在线早期（医生<100人时）也是财务手动结算

**BR-SUG-022 医生结算规则**需明确：
- 签约医生：底薪（按月固定）+ 问诊绩效（按单）+ 处方绩效（按单）+ 满意度奖金（按评级）
- 入驻医生：问诊费×（1-平台抽成比例）×结算周期
- 结算周期：签约医生月结（次月10日），入驻医生月结（次月15日）
- 提现门槛：入驻医生累计可提现金额≥100元
- **V1.0不做**：个税代扣代缴（医生自行申报）、多级分佣、邀请奖励分润

**V1.1升级方向**（医生>50人）：
- 自动打款对接（银行代发API）
- 个税代扣代缴
- 医生结算看板（医生端查看自己的收入明细）
- 从PC-013拆分为独立FN-SUG-PC-016

### 【P1-6】Q43：CGM设备管理

#### 行业现状

| 品牌 | 市占率 | 连接方式 | 数据协议 |
|------|--------|---------|---------|
| 雅培瞬感 | **~50%** | NFC（传感器）+蓝牙（读取器） | 私有协议，有SDK |
| 硅基动感 | **~20%（国产第一）** | 蓝牙BLE | 开放API |
| 三诺爱看 | ~10% | 蓝牙BLE | 开放API |
| 微泰动泰 | ~8% | 蓝牙BLE | 开放API |
| 鱼跃安耐糖 | ~5% | 蓝牙BLE | 开放API |

**行业趋势**：国产CGM市占率快速提升（雅培从70%降至50%），多品牌协议适配是**必然需求**。

#### 决策选项

**选项A：融入APP-026血糖记录（推荐✅）**

不独立FN，在APP-026「血糖记录与监测」中增加设备管理子模块。

**选项B：独立FN**

新增FN-SUG-APP-053「CGM设备管理」。

| 维度 | 选项A（融入） | 选项B（独立） |
|------|------------|-------------|
| 用户心智 | ✅ 用户认为「设备配对」是「记录血糖」的一部分 | ⚠️ 需要两个入口 |
| 代码组织 | ⚠️ 血糖记录FN变大 | ✅ 职责分离 |

#### 🏆 推荐方案 → 更符合商业实际

**选项A：融入APP-026——但不做「万能协议适配层」，而是做「品牌深度合作+手动兜底」**

> **商业落地核心**：CGM设备对接的最大坑不是技术问题（蓝牙/NFC/API都不难），而是**商业谈判**——每个CGM品牌的SDK授权、数据使用协议、品牌露出要求都不同。正确的商业策略是：**V1.0深度绑定1个品牌（雅培或硅基），拿到最优商业条件，而非试图做万能适配**。

**V1.0务实方案**：

```
阶段0（上线前必须完成的商业动作）：
├─ 选择1家CGM品牌建立深度合作
│   ├─ 首选：硅基动感（国产第一，市占率20%，开放API，合作门槛低）
│   │   └─ 商业条件：渠道价优惠+CGM试纸赠送+联合品牌露出
│   ├─ 备选：雅培瞬感（市占率50%，但SDK授权费用高，合作门槛高）
│   │   └─ 商业条件：需承诺年销量>5000枚才能拿到优惠价
│   └─ 推荐首选硅基动感——理由：
│       ├─ 开放API，技术对接简单（1周可完成）
│       ├─ 国产政策支持，医保/集采倾斜
│       ├─ 合作意愿强（国产CGM急需渠道，谈判主动权在你）
│       └─ 市占率快速上升（从10%→20%仅用1年）
└─ 签订合作备忘录（数据使用协议+价格协议+联合推广方案）

APP-026「血糖记录与监测」中的设备管理子模块：
├─ 品牌页：「硅基动感 CGM 官方合作」
│   ├─ 引导购买（跳转商城硅基专区）
│   ├─ 蓝牙配对新设备
│   └─ 自动同步血糖数据（蓝牙BLE→APP→云端存储）
├─ 手动录入（兜底，覆盖其他品牌用户）：
│   ├─ 手动输入血糖值+时间
│   ├─ 拍照识别（OCR识别雅培/三诺/鱼跃等品牌读数界面）
│   └─ 手动导入历史数据（CSV上传）
└─ 设备状态卡（仅在绑定设备后显示）：
    ├─ 传感器剩余寿命（倒计时）
    ├─ 最近一次同步时间
    └─ 设备异常提醒（信号丢失/电量不足）
```

> **为什么不做万能适配层？**
> - 「支持多品牌」听起来很美，但V1.0的现实是：
>   - 雅培SDK：需签署NDA+商务谈判+授权费——周期3~6个月
>   - 硅基API：开放+免费——1周搞定
>   - 三诺API：开放+免费——1周搞定
>   - 鱼跃API：需商务对接——周期1~2个月
> - **最优策略**：V1.0只对接硅基1家（1周），其他品牌用户用手动录入兜底→V1.1根据用户数据决定下一个对接谁
> - 如果V1.0中硅基用户占比超60%，就验证了「深度绑定1家」策略→V1.1扩展第二品牌
> - 如果V1.0中手动录入用户超50%，说明用户分散→V1.1加速多品牌适配

**商业收益（绑定硅基的预期）**：
- CGM试纸/传感器 → 商城新增SKU，提升GMV
- 「购买CGM→自动记录血糖→精准用药推荐→购药」 → 一条龙商业闭环
- CGM用户LTV远高于非CGM用户（每天看血糖=每天打开APP=高粘性）
- 可能的联合推广费用（硅基在SugarMate投放广告/试纸赠品）

**手动录入的价值**（常被低估）：
- 手动录入不是「体验差」，而是「数据采集」——你在收集用户使用什么品牌
- 当手动录入数据中某个品牌占比>15%时，就是V1.1优先对接的品牌
- OCR识别能力（拍照识别其他品牌读数）让手动录入体验大幅提升

### 【P1-7】Q38补充：CRM召回机制完善（行业最佳实践）

> 注：此条来源于专家盲区审查YL-02，但用户未深入讨论，补充行业标准供决策。

#### 行业对标

| 平台 | 召回手段 | 优先级规则 |
|------|---------|-----------|
| 京东健康 | Push→短信→企微消息→AI外呼 | 按用户活跃度自动降级 |
| 微医 | 企微1v1→Push→短信 | 前3次Push无响应自动转短信 |
| 智云健康 | APP Push→短信→电话 | 按紧急程度（血糖异常→电话） |

#### 降级规则行业标准

```
Level 1: APP Push（免费，到到达率60~70%）
    ↓ 连续3次未点击
Level 2: 短信（成本0.03~0.05元/条，到达率95%+）
    ↓ 关键事件（血糖异常/处方即将过期）
Level 3: AI外呼电话（成本0.1~0.3元/次，到达率99%）
```

#### 🏆 推荐

**融入SCRM-005「流失预警与召回」**，增加：
- Push→短信→AI外呼 三级降级链路
- 按事件紧急程度选择起点（常规召回从Push开始，血糖异常直接短信+Push双发）
- 召回效果统计（触达率/打开率/回流率）
