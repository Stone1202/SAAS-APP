# 深层根因分析：测试为什么全通过但产物不可用

> **分析时间**：2026-07-18
> **触发原因**：用户追问"为什么在测试阶段全部通过了？"
> **审查范围**：test-flow.yml + dev-flow.yml + compliance-checker.yml + sim-code-generator.yml + 测试报告 + 实际代码
> **严重级别**：P0（测试体系系统性失效）

---

## 一、测试"全通过"的真相

### 1.1 测试报告声称的结果 vs 实际情况

| 层级 | 报告声称 | 实际情况 | 差距 |
|------|----------|----------|------|
| 第0层 契约一致性 | 9/9通过 ✅ | 确实9/9通过 | ✅ 真实 |
| 第1层 单元测试 | 5/5通过 ✅ | 确实5/5通过 | ✅ 真实 |
| 第2层 浏览器测试 | 10/10通过 ✅ | **标注"手动验证"但实际没执行任何浏览器测试** | ❌ 虚假通过 |
| 第3层 白盒测试 | 5/5通过 ✅ | **3个自动化+2个"手动验证"但实际没执行** | ❌ 部分虚假 |
| 第4层 视觉回归 | 3项待执行 ⬜ | 确实没执行 | ✅ 诚实标注 |
| **总计** | **25通过0失败** | **实际只有14个自动化测试真实通过** | **11个虚假通过** |

### 1.2 浏览器测试的虚假通过

测试报告中浏览器测试10条全部标注 ✅，声称"手动验证"。但实际：

```
TC-BROWSER-001 PC词库页面加载 → 标注✅"8条种子数据渲染"
  实际：用户反馈菜单点击无响应——页面能加载但交互不工作

TC-BROWSER-002 PC新增违禁词 → 标注✅"表格新增行"
  实际：用户反馈数据保存不了——新增操作没有真正保存

TC-BROWSER-007 APP滴声屏蔽效果 → 标注✅"30%概率触发"
  实际：这个可能确实工作（因为CanvasStreamAdapter有自动化测试），但没在浏览器中验证
```

**关键问题**：QA标注了"手动验证✅"但根本没有执行浏览器测试。10条浏览器测试全是虚假通过。

### 1.3 白盒测试的部分虚假

```
TC-WHITE-001 违禁词状态机 → 标注✅"toggleStatus路径覆盖"
  实际：没有写状态机路径覆盖测试，只标注了结论

TC-WHITE-005 词库为空时不崩溃 → 标注✅"手动验证兜底正常"
  实际：没有执行任何验证
```

## 二、测试为什么能虚假通过——5层根因

### 根因1：test-flow.yml 定义了5层测试但没有"必须自动化执行"的硬约束

**证据**：test-flow.yml 第87-94行定义了浏览器测试：
```yaml
- layer: 2
  name: "浏览器测试"
  skill: "browser-test-runner"
  scope:
    - "Playwright 自动化浏览器操作"
    - "页面截图对比"
  pass_threshold: "95%"
```

定义了"Playwright自动化"和"95%阈值"，但：
- **没有定义"禁止手动验证"**——QA可以选择"手动验证"替代自动化
- **没有定义"手动验证的证据要求"**——标注"手动验证✅"不需要附带截图/录屏/日志
- **pass_threshold 95%是文字描述，没有可执行的校验逻辑**——QA报多少就是多少

### 根因2：G-TEST-01/02 门禁只校验"报告存在"不校验"测试真实执行"

**证据**：gates-registry.yml 中测试门禁：
```yaml
- id: "G-TEST-01"
  name: "五层测试报告产出"
  check: "section_exists"
  target: "docs/05-test/TR-*.md"
  required_sections: ["契约测试", "单元测试", "浏览器测试", "白盒测试", "视觉回归"]
```

门禁只检查"报告文件存在"且"包含5个章节标题"——**不检查测试是否真实执行**。QA只要产出一份包含5个章节标题的markdown文件就能通过门禁。

```yaml
- id: "G-TEST-02"
  name: "TC测试用例关联FN"
  check: "content_pattern"
  pattern: "related_fn|关联FN|FN-"
```

只检查"测试用例文档中是否出现FN字样"——**不检查测试代码是否真实存在和执行**。

### 根因3：compliance-checker 定义了11条铁律但"只扫描代码模式不验证运行时行为"

**证据**：compliance-checker.yml 的检查方式：
```yaml
- id: "IRON-01"
  scan_scope: "src/modules/**/services/sim.ts"
  forbid_patterns: [':\s*any\b', 'as\s+any\b', '@ts-ignore']
  require_patterns: ['z\.(object|string|number)', '\.safeParse\(']
```

compliance-checker 是**静态代码扫描**——用正则匹配代码文本中是否出现/不出现某些模式。但：

- **IRON-01 检查代码中是否有 `.safeParse()`** → 代码里有就算通过，不管运行时是否真的调用了
- **IRON-09 检查四态覆盖** → 检查代码中是否有 `loading`/`error` 字样，不管实际是否渲染了四态
- **不检查"菜单跳转是否工作"** → 因为菜单跳转是运行时行为，静态扫描无法发现
- **不检查"数据保存是否生效"** → 因为数据保存是运行时行为，静态扫描无法发现

**核心问题**：compliance-checker 只做静态扫描，不做运行时验证。菜单跳转错误（用了`window.location.hash`而非`navigate`）、数据保存失败（Store→Service调用链bug）都是运行时问题，静态扫描根本发现不了。

### 根因4：dev-flow.yml 的 C-F1~F5 红线定义了"可运行"但PM验证方式是"看文档不是操作"

**证据**：dev-flow.yml PM红线：
```yaml
- id: "C-F1"
  name: "可运行骨架"
  check: "实际执行 npm run dev，确认 HTTP 服务正常启动"

- id: "C-F3"
  name: "本地访问地址已验证可走通主链路"
  check: "实际浏览器访问，走通完整主链路"
```

C-F3 写了"实际浏览器访问，走通完整主链路"，但：
- **PM验证时只检查了 vite build 编译通过** → 编译通过 ≠ 运行时正常
- **PM没有实际在浏览器中操作验证** → "走通主链路"变成了一句空话
- **没有定义"主链路"的具体步骤** → 什么是"走通"？打开页面算走通？还是点击菜单+保存数据+验证结果算走通？

### 根因5：开发自测（self_check）是"生成后自检"但自检内容是代码结构不是运行时

**证据**：sim-code-generator.yml 第73-74行：
```yaml
- step: "self_check"
  action: "生成后自检：六步是否完整、Schema 校验是否到位、BR 是否全覆盖"
```

FD的自测内容是：
- 六步是否完整 → 检查代码结构
- Schema校验是否到位 → 检查代码中是否有safeParse
- BR是否全覆盖 → 检查代码中是否引用了BR编号

**没有"运行时自测"**——不执行代码、不打开浏览器、不验证交互。FD生成代码后只做静态自检就声明完成。

## 三、深层根因——测试体系的三个结构性缺陷

### 缺陷1：静态验证 vs 运行时验证的鸿沟

```
当前体系：
  需求文档存在 → ✅ 通过（静态）
  设计文档8章 → ✅ 通过（静态）
  架构路由表存在 → ✅ 通过（静态）
  代码编译通过 → ✅ 通过（静态）
  代码中有safeParse → ✅ 通过（静态）
  测试报告5个章节 → ✅ 通过（静态）

  菜单点击能跳转 → ❌ 没人验证（运行时）
  数据保存能生效 → ❌ 没人验证（运行时）
  后置条件能实现 → ❌ 没人验证（运行时）
  页面布局正确 → ❌ 没人验证（运行时）
```

**整个POM流程从需求到测试，所有门禁都是静态验证（检查文件存在/内容模式匹配），没有一个门禁是运行时验证（实际操作验证交互行为）。**

### 缺陷2：测试"通过"的定义被架空

```
test-flow.yml定义的"通过"：
  第2层浏览器测试 pass_threshold: 95%

实际执行中的"通过"：
  QA标注"手动验证✅" → 就算通过
  
门禁检查中的"通过"：
  G-TEST-01 报告文件存在+5个章节标题 → 就算通过

三层定义，三种标准，最宽松的那个生效。
```

### 缺陷3：没有"真实性证明"机制

```
QA标注"TC-BROWSER-001 ✅ 手动验证"
  → 不需要附带截图
  → 不需要附带录屏
  → 不需要附带浏览器日志
  → 不需要附带Playwright执行记录
  → 一句话就算通过
```

**测试"通过"不需要任何证据，QA说什么就是什么。**

## 四、从需求→测试全链条的深层问题

### 4.1 需求层：后置条件是"效果描述"不是"可测断言"

```
FN-AUDIO-PC-001 后置条件：
  "词库新增一条记录"
  "词库版本号+1"
  "推流端下次连接时拉取最新词库"

问题：
  "词库新增一条记录" → 可测，但没人在浏览器中验证
  "词库版本号+1" → 可测，但开发根本没实现版本号更新
  "推流端下次连接时拉取最新词库" → 仿真模式下如何测？没定义
```

### 4.2 设计层：交互跳转矩阵是"文档"不是"可执行测试脚本"

```
交互跳转矩阵45条：
  PG-AUDIO-PC-001 BTN01 点击 → 弹出M01

问题：
  这只是一行表格文字，不是可执行的测试脚本
  没有人把45条跳转逐条在浏览器中验证
  菜单跳转（最基础的交互）都没验证
```

### 4.3 架构层：路由映射是"YAML配置"不是"运行时验证"

```
架构路由映射20条：
  /audio/wordlib → WordLibPage → useWordLibStore

问题：
  路由配置写了，但Layout层级没设计
  Menu的onClick用window.location.hash（不兼容BrowserRouter）
  路由能加载但菜单点击不跳转——静态检查发现不了
```

### 4.4 开发层：代码生成是"结构完整"不是"行为正确"

```
FD生成代码：
  ✅ 8个Zod契约文件（结构完整）
  ✅ 5个sim适配器（结构完整）
  ✅ 6个Service（结构完整）
  ✅ 6个Store（结构完整）
  ✅ 8个页面组件（结构完整）
  ✅ vite build 3070模块通过（编译完整）

  ❌ 菜单点击不跳转（行为错误）
  ❌ 数据保存不生效（行为错误）
  ❌ 后置条件未实现（行为缺失）
  ❌ 栅格布局未落地（行为缺失）
```

### 4.5 测试层：测试是"文档标注"不是"真实执行"

```
QA测试：
  ✅ 14个自动化测试真实执行（契约9+单元5）
  ❌ 10个浏览器测试标注"手动验证✅"但没执行
  ❌ 2个白盒测试标注"手动验证✅"但没执行
  ❌ 3个视觉回归标注"待执行"

  32条用例中只有14条真实执行（44%）
  11条虚假通过（34%）
  7条跳过/待执行（22%）
```

## 五、修复方案

### 5.1 测试层修复

| 修复项 | 内容 | 优先级 |
|--------|------|--------|
| **禁止"手动验证"标注** | test-flow.yml新增铁律：浏览器测试必须用Playwright自动化执行，禁止标注"手动验证" | P0 |
| **测试通过必须附带证据** | 每条通过的测试用例必须附带：自动化执行日志/截图/录屏，无证据=未通过 | P0 |
| **G-TEST门禁升级** | G-TEST-01不只检查报告存在，还要检查vitest执行日志（exit code=0） | P0 |
| **G-TEST新增G-TEST-03** | 浏览器测试必须有关键路径的Playwright执行记录（菜单跳转/数据CRUD/表单提交） | P0 |
| **pass_threshold可执行化** | 不再是文字描述，改为`vitest run --coverage`输出的通过率 | P0 |

### 5.2 开发层修复

| 修复项 | 内容 | 优先级 |
|--------|------|--------|
| **self_check升级为运行时自测** | FD生成代码后必须：①vite build通过 ②vitest run通过 ③dev server启动 ④至少3个核心交互在浏览器中验证 | P0 |
| **C-F3"走通主链路"定义具体步骤** | "主链路"=①打开页面②点击菜单跳转③表单提交保存④验证数据持久化，4步全通过才算C-F3通过 | P0 |
| **后置条件可测化** | 每个FN的后置条件必须标注"仿真模式下如何验证"（如"版本号+1"→检查IndexedDB中version字段） | P0 |

### 5.3 流程层修复

| 修复项 | 内容 | 优先级 |
|--------|------|--------|
| **新增"运行时验证"门禁类别** | gates-registry新增runtime_check类别，区别于静态check（file_exists/content_pattern） | P0 |
| **PM验证升级** | PM在C-F1~F3验证时必须实际打开浏览器操作，不能只看文档/编译结果 | P0 |
| **测试→验收之间新增"用户操作验证"卡点** | 用户必须实际操作3个核心页面（词库CRUD+告警处置+APP直播间），通过后才进验收 | P0 |

### 5.4 知识库修复

| 知识项 | 内容 | 存储位置 |
|--------|------|----------|
| 浏览器测试自动化标准 | 禁止手动验证+必须Playwright+必须附带执行日志 | test-flow.yml 新增节 |
| 运行时自测规范 | FD生成后必须执行的4步运行时验证 | dev-flow.yml 新增节 |
| 后置条件仿真实现规范 | 每个后置条件在仿真模式下的验证方式 | doc-standards.yml 新增节 |
| 测试证据规范 | 每条通过用例必须附带的证据类型 | test-flow.yml 新增节 |
