# POM流程输入输出深度优化分析

> **分析日期**：2026-07-20
> **分析维度**：输入链路 / 输出产物 / 流程串并行 / 反馈闭环
> **基于**：V5.1.0大脑体系落地+Skill瘦身后的当前流程状态

---

## 二、维度1：输入优化（7项）

### 问题1：大PRD全量传递——下游Agent被迫加载全部17章

**现状**：BA产出17章PRD，UX/Arch/FD/QA/AC全部加载完整PRD
**问题**：UX只需要FN/UC/状态机/系统类型/业务操作矩阵；Arch只需要接口契约初稿/外部依赖/系统类型；QA只需要BR/状态机/验收标准/业务操作矩阵

**优化方案：产物视图化（PRD-View）**

```
BA产出完整PRD后，自动生成3个下游视图：

PRD-View-UX（~3K Token，vs 完整PRD ~15K Token）：
  - system_declaration（系统类型+密度+终端）
  - FN/UC清单（按业务系统×终端组织）
  - 状态机+状态过渡操作表
  - 业务操作矩阵
  - 多端差异矩阵

PRD-View-Arch（~2K Token）：
  - 接口契约初稿
  - 外部依赖清单
  - system_declaration
  - ENT数据实体
  - CONFIG清单

PRD-View-QA（~2K Token）：
  - BR业务规则清单
  - 状态机+状态过渡操作表
  - 验收标准（SC场景+GWT矩阵）
  - 业务操作矩阵
  - METRIC清单
```

**降耗**：UX/Arch/QA各减少~10K Token加载量，全流程减少~30K Token

### 问题2：知识库全量加载——每个stage加载30+知识库文件

**现状**：knowledge/common/下30+文件总计~8000行(~120K Token)，各stage不区分地加载
**问题**：stage-2(BA)不需要设计系统知识库；stage-3(UX)不需要metrics-standards

**优化方案：stage级知识库路由表**

```yaml
# config.yml 新增 knowledge_routing
knowledge_routing:
  stage-2_ba:
    must_load: [doc-standards, metrics-standards, system-blueprints, api-learner, brain-memory-spec]
    skip: [design-system, ui-components, ux-guidelines, tech-stack, version-timeline-standards]
  stage-3_ux:
    must_load: [design-system, ui-components, ux-guidelines, design-output-standards, design-review-criteria]
    skip: [metrics-standards, api-learner, tech-stack, brain-evolution-engine]
  stage-4_arch:
    must_load: [tech-stack, brain-memory-spec, brain-evolution-engine, api-learner]
    skip: [design-system, ui-components, ux-guidelines, metrics-standards]
  # ...每个stage都有明确的load/skip清单
```

**降耗**：单stage从加载~120K Token降至~20K Token（只加载5个必需文件）

### 问题3：大脑记忆全量加载——9个Agent记忆全部加载

**现状**：/init时加载上版本全部9个Agent大脑记忆
**问题**：BA不需要加载FD/QA的大脑记忆；UX不需要加载QA/AC的大脑记忆

**优化方案：大脑记忆按Agent相关性加载**

```
BA加载：BA自身记忆 + QA Bug模式（QA→BA的brain_sync_export）
UX加载：UX自身记忆 + BA的to_ux导出
Arch加载：Arch自身记忆 + BA的to_arch导出 + UX的to_arch导出
FD加载：FD自身记忆 + Arch的to_fd导出 + UX的to_fd导出
QA加载：QA自身记忆 + BA/Arch/FD的brain_sync_export
```

**降耗**：从加载9个记忆文件降至2-4个，减少~50%大脑记忆加载量

### 问题4：脑暴→PO→BA的信息衰减

**现状**：脑暴确认稿→PO规划→BA需求分析，信息经过3次转译
**问题**：脑暴讨论的细节在PO规划时可能丢失，PO的Sprint拆解在BA需求分析时可能不完整继承

**优化方案：参数路由包增强**

```
当前参数路由包含9项上下文，新增：
- brainstorm_essence: 脑暴核心决策摘要（≤500字，BS Agent产出）
- po_decisions: PO关键决策清单（Backlog优先级top5+Sprint拆解策略）
- domain_keywords: 领域知识关键词清单（直接传递，不重新匹配）
```

### 问题5：上游产物以完整文档传递——下游解析成本高

**现状**：UX交互文档9章完整传递给Arch/FD
**问题**：Arch只需要路由信息（哪些页面→哪些组件→哪些数据依赖），不需要完整的交互行为清单

**优化方案：产物摘要层（Product-Summary-Layer）**

```
每个stage产出后，自动生成"摘要层"（≤1K Token）：

UX摘要层 → Arch/FD加载摘要而非完整文档：
  - 页面清单（PG编号+名称+端）
  - 组件清单（组件名+复杂度评分）
  - 路由结构（页面跳转矩阵浓缩版）
  - Design Token清单（Token名+类型）

Arch摘要层 → FD/QA加载摘要：
  - 路由映射表（路由→组件→Store→数据字段）
  - 接口清单（接口名+method+path+简述）
  - 仿真开关清单
```

### 问题6：review反馈回流输入冗余

**现状**：defect-reflow依次上传到每个stage，每个stage都要重新审视反馈
**问题**：一个设计问题可能被BA/UX/Arch/FD/QA全部审视一遍，但只有UX需要修改

**优化方案：反馈直达归属stage**

```
当前：反馈→BA审视→UX审视→Arch审视→FD审视→QA审视（5次审视）
优化：feedback-processor(mode=reflow)的ai3阶段归属判断→直达归属stage
     反馈→AI判断归属=UX→只UX审视+修改（1次审视）
     其他stage只收到"通知"（≤100字摘要），不做 full review
```

### 问题7：handoff阶段重复输入

**现状**：handoff时需要重新读取PRD+仿真原型+用例卡片
**问题**：这些产物在前面stage已经产出过，handoff阶段重新加载是冗余

**优化方案：handoff产物缓存**

```
handoff阶段不重新读取完整产物，而是使用前面stage的"摘要层"：
- PRD摘要层（FN/UC清单）→ 标注覆盖度检查
- 仿真原型摘要层（页面路由清单）→ 标注页面入口
- 用例卡片摘要层（UC编号+标题）→ 标注卡片位置
```

## 三、维度2：输出优化（6项）

### 问题8：BA产出17章PRD——大量章节下游不直接使用

**现状**：BA产出17章PRD+17个附属产物
**问题**：章节1(版本历史)/2(目录)/3(背景)/6(与既有模块关系)下游Agent几乎不直接使用；章节11(CONFIG)/13(METRIC)只有特定场景需要

**优化方案：PRD分层产出**

```
PRD-Core（必产出，~8K Token）：5/7/8/9/10/12/14/15章
  - 范围 / 业务目标映射 / 用户故事 / FN-UC / BR / ENT / 验收标准 / 五图
  
PRD-Extended（按需产出，~5K Token）：4/11/13/16/17章
  - 目标度量 / CONFIG / METRIC / 外部接口 / 需求深度分析摘要
  - 触发条件：§0.5c判断有可配置项→产CONFIG；有统计需求→产METRIC

PRD-Context（背景信息，~2K Token）：1/2/3/6章
  - 版本历史 / 目录 / 背景 / 与既有模块关系
  - 可从脑暴文档+参数路由包自动生成，不需BA手写
```

### 问题9：UX产出9章交互文档——部分章节可自动化

**现状**：UX产出9章交互文档，每章都需手写
**问题**：第⑥章(交互一致性检查清单)和第⑨章(PRD UC一致性追溯)是检查项，可自动化生成

**优化方案：检查类章节自动化**

```
第⑥章（交互一致性检查清单）→ 由 design-contract-aligner 自动生成
第⑨章（UC一致性追溯）→ 由 AI 自动对比PRD的UC清单和交互文档的UI映射
UX只手写第①②③④⑤⑦⑧章（7章），检查类章节自动生成
```

### 问题10：7-8份Review报告——产出冗余

**现状**：每个stage都有Review报告，共7-8份
**问题**：Review报告格式相似，内容有重叠（如版本概述、范围确认等）

**优化方案：Review报告合并**

```
当前：7-8份独立Review报告（每份~2K Token = ~16K Token总量）
优化：1份Review汇总报告（~5K Token）+ 各stage的Review问题清单（~500字/stage）

Review汇总报告结构：
  - 版本概述（1份，不重复）
  - 各stage Review结论（通过/有条件通过/不通过 + 问题数）
  - 各stage问题清单（按严重度分组）
  - 跨stage追溯（上游问题→下游影响）
```

**降耗**：~16K → ~8K Token

### 问题11：版本沉淀8步——过程过于复杂

**现状**：knowledge-sedimentation.yml有8步（创建目录→需求沉淀→Review沉淀→经验提炼→追溯链快照→版本索引→沉淀摘要→Journal记录）
**问题**：8步中有些可以合并或自动化

**优化方案：版本沉淀精简为3步**

```
Step 1 自动沉淀（PM自动执行）：
  - 创建版本沉淀目录
  - 自动复制需求/Review/追溯链产物（脚本化）
  - 自动更新VERSION-INDEX.yml

Step 2 AI经验提炼（AI执行）：
  - AI分析本次版本的Review问题+Bug模式+大脑进化数据
  - 产出lessons-learned.md（≤1K Token，3-5条可复用经验）
  - 追加到common/经验库/

Step 3 沉淀摘要（PM执行）：
  - 产出沉淀摘要（≤500字）
  - Journal记录
```

### 问题12：五层测试全部执行——原型项目过度测试

**现状**：test-flow.yml五层测试（契约+单元+浏览器+白盒+视觉回归）
**问题**：对于高保真原型项目（非生产代码），白盒测试（状态覆盖/路径覆盖/边界注入）投入产出比低

**优化方案：测试分层策略**

```
原型项目（type=新增/迭代）：三层测试
  - 契约一致性（必做）
  - 浏览器测试（必做，含视觉回归）
  - 单元测试（必做，sim.ts函数级）
  → 跳过白盒测试

生产级项目（type=变更，且有released_baseline）：五层测试
  - 全部五层执行
```

### 问题13：大脑同步导出字段过多——部分字段下游未使用

**现状**：brain_sync_export每个方向导出3-5个字段
**问题**：部分字段（如BA→UX的"交互密度预估"）UX大脑可能并未实际使用

**优化方案：大脑导出字段精简**

```
每个brain_sync_export字段标注 usage_verification：
  - usage: "consumed"（下游大脑已使用）→ 保留
  - usage: "unverified"（下游大脑未确认使用）→ 标记为候选，不强制导出
  - usage: "deprecated"（下游大脑已不需要）→ 删除

定期审计：每2个版本清理一次unverified字段
```

## 四、维度3：流程串并行优化（4项）

### 问题14：UX→Arch串行——可以并行

**现状**：stage-3(UX) → stage-4(Arch) 串行执行
**问题**：UX关注页面设计（栅格/组件/交互），Arch关注技术架构（路由/契约/骨架）。两者输入都来自BA，不需要互相等待

**优化方案：UX和Arch并行**

```
当前：BA → UX → Arch → FD（串行，3个等待）
优化：BA → UX ─┐
              ├→ FD（并行，1个等待）
         BA → Arch ┘

条件：UX和Arch的brain_sync_export改为不互相依赖
     UX的to_arch改为"设计完成后补充"而非"Arch开始前必须"
     Arch的to_fd仍需等待Arch完成
```

**提速**：减少1个stage的等待时间（~30%整体流程提速）

### 问题15：handoff是独立stage——可以并入close

**现状**：stage-7.5 handoff是独立stage（3步+4级标注+回传）
**问题**：handoff本质上是对已有产物的标注+回传，不需要作为独立stage

**优化方案：handoff并入close**

```
当前：AC验收 → handoff(3步) → close(版本快照+沉淀+进化)
优化：AC验收 → close(含handoff标注+回传+版本快照+沉淀+进化)

close流程调整：
  Step 1 handoff标注（自动标注+AI回传分析）← 原handoff 3步合并为1步
  Step 2 版本快照+差异报告
  Step 3 版本沉淀（精简为3步）
  Step 4 大脑进化
```

### 问题16：5个checkpoint——用户确认过多

**现状**：requirement/design/arch/test/accept 5个checkpoint，用户每次都需确认
**问题**：design和test的checkpoint可以自动流转，只有requirement/arch/accept需要用户确认

**优化方案：checkpoint精简**

```
当前5个checkpoint：
  requirement ✋ → design ✋ → arch ✋ → test ✋ → accept ✋

优化3个checkpoint：
  requirement ✋ → design（自动流转）→ arch ✋ → test（自动流转）→ accept ✋

设计自动流转条件：C-D1~D9全部通过 + 联合评审通过
测试自动流转条件：五层测试无Critical/High Bug
```

### 问题17：defect-reflow依次上传——可以跳过无关stage

**现状**：反馈回流时依次上传到每个stage（BA→UX→Arch→FD→QA）
**问题**：一个UI问题只需要UX修改，不需要BA/Arch/FD/QA都审视

**优化方案：智能路由回流**

```
当前：反馈 → BA审视 → UX审视 → Arch审视 → FD审视 → QA审视
优化：反馈 → feedback-processor(mode=reflow)的ai3判断归属
     → 直达归属stage（如UX）→ UX修改
     → 其他stage收到"通知"（非full review）
     → 修改后只重跑受影响的下游stage（如UX修改→重跑Arch/FD，不重跑BA）
```

## 五、维度4：反馈闭环优化（3项）

### 问题18：反馈到修改的周期太长

**现状**：用户/feedback → AI分析(6维) → 依次上传(5个stage) → 修改 → 重跑下游 → 验收
**问题**：整个回流周期可能需要重新走3-5个stage

**优化方案：增量回流**

```
反馈分析后只重跑受影响的stage：
  - 影响范围=需求 → 重跑BA→UX→Arch→FD→QA→AC（全链）
  - 影响范围=设计 → 重跑UX→FD→QA→AC（跳过BA）
  - 影响范围=代码 → 重跑FD→QA→AC（跳过BA/UX/Arch）
  - 影响范围=测试 → 重跑QA→AC（跳过BA/UX/Arch/FD）
```

### 问题19：大脑进化结果未验证——下版本可能用到错误权重

**现状**：/close时大脑进化引擎调整权重，但未验证调整后的权重是否提升了准确率
**问题**：如果进化方向错误，下版本的大脑推理质量会下降

**优化方案：大脑进化A/B验证**

```
/close时：
  1. 保留旧权重作为baseline
  2. 计算新权重
  3. 对比新旧权重在本次版本prediction vs actual的准确率
  4. 如果新权重准确率 > 旧权重 → 采用新权重
  5. 如果新权重准确率 ≤ 旧权重 → 回退旧权重 + 标记"进化失败"
```

### 问题20：跨版本经验复用不足

**现状**：版本沉淀产出经验库，但下版本/init时只加载"经验库"作为低优先级输入
**问题**：经验库的内容是静态文本，没有被结构化为"可执行的建议"

**优化方案：经验库结构化为Brain Pattern**

```
当前：经验库 = Markdown文本（lessons-learned.md）
优化：经验库 = 结构化Brain Pattern

每个经验条目结构：
  pattern_id: "EXP-{version}-{NNN}"
  pattern_type: "bug_prevention | design_tip | arch_decision | test_strategy"
  trigger_condition: "当FN涉及xxx时"
  recommended_action: "建议xxx"
  confidence: 0.8
  source_version: "v1.0.0"
  verification_count: 3  # 被多少个版本验证过

/init时BA/UX/Arch/FD/QA大脑自动匹配trigger_condition → 注入recommended_action
```
