# POM 门禁治理与铁律统一管理架构方案

> **方案编号**：GOVERNANCE-2026-07-17-002
> **触发原因**：需求文档"半成品"通过 Review 进入设计阶段，暴露门禁形同虚设
> **审查范围**：15个 workflow.yml + 10个 agent.md + config.yml + redlines.yml + doc-standards.yml
> **严重级别**：P0（流程级架构缺陷，影响全流程产物质量保障）

---

## 二、根因总结

| # | 问题 | 本质 | 后果 |
|---|------|------|------|
| **P1** | requirement-flow.yml §7 没有产物完整性门禁 | 铁律BA-11只是文字"缺一不可"，无可执行校验 | BA可跳过核心步骤产出半成品通过Review |
| **P2** | 门禁/铁律分散管理，无统一注册中心 | 15个workflow各自定义，10个agent各自描述，config.yml不注册 | 无法全局审计、版本升级遗漏、跨流程引用断裂 |
| **P3** | agent.md铁律编号混乱，与workflow映射断裂 | ba-agent编号11~14重复，bs/fd铁律数量不一致，4个Agent无编号铁律 | Agent执行时无法精确映射铁律到workflow检查项 |

## 三、治理方案：三层统一管理

### 架构

```
第一层：统一注册中心（config.yml 注册引用）
├── gates-registry.yml     （门禁注册中心，新建）
├── iron-rules-registry.yml（铁律注册中心，新建）
└── redlines.yml           （红线补充清单，已有，补注册）

第二层：各workflow.yml 引用注册中心（不再内联定义）
第三层：各agent.md 引用注册中心 + 强化执行
```

### 3.1 新建 gates-registry.yml

全流程产物完整性门禁的单一事实源。每个阶段的"必须产出什么、怎么校验、缺失怎么办"全部在此定义。

核心门禁（Stage-2 需求分析，14条硬门禁）：

| 门禁ID | 名称 | 校验方式 | 缺失后果 |
|--------|------|----------|----------|
| G-REQ-01 | FN功能编号存在 | content_pattern: FN-{系统}-{终端}-{NNN} | 阻止进入设计 |
| G-REQ-02 | UC用例编号存在 | content_pattern: UC-{系统}-{终端}-{NNN} | 阻止进入设计 |
| G-REQ-03 | 业务泳道图存在 | content_pattern: swimlane/泳道 | 阻止进入设计 |
| G-REQ-04 | 跨系统信息流转图存在 | content_pattern: 信息流转/信息流图 | 阻止进入设计 |
| G-REQ-05 | 状态机+过渡操作表存在 | content_pattern: stateDiagram/状态机/状态过渡操作表 | 阻止进入设计 |
| G-REQ-06 | 业务操作矩阵存在 | content_pattern: 业务操作矩阵/operation_matrix | 阻止进入设计 |
| G-REQ-07 | BR业务规则编号存在 | content_pattern: BR-{系统}-{NNN} | 阻止进入设计 |
| G-REQ-08 | ENT数据实体编号存在 | content_pattern: ENT-{系统}-{NNN} | 阻止进入设计 |
| G-REQ-09 | CONFIG清单存在 | content_pattern: CONFIG-{系统}-{NNN} | 阻止进入设计 |
| G-REQ-10 | METRIC清单存在 | content_pattern: METRIC-{系统}-{NNN} | 阻止进入设计 |
| G-REQ-11 | 系统类型声明存在 | content_pattern: system_declaration | 阻止进入设计 |
| G-REQ-12 | 五类图齐全 | section_exists: 5个必选章节 | 阻止进入设计 |
| G-REQ-13 | BO/BG映射存在 | content_pattern: BG-/BO- | 阻止进入设计 |
| G-REQ-14 | 验收标准双层矩阵存在 | content_pattern: SC-/Given-When-Then | 阻止进入设计 |

其他阶段门禁：G-DES-01~05（设计5条）、G-ARCH-01~04（架构4条）、G-DEV-01~02（开发2条）、G-TEST-01~02（测试2条）、G-ACC-01~02（验收2条）、G-CLOSE-01~04（关闭4条）。

### 3.2 新建 iron-rules-registry.yml

所有Agent铁律的单一事实源，统一编号统一管理。

修复 ba-agent 编号冲突：
- BA-01~BA-13：保留原有
- BA-14~BA-17：V3.1.0新增（§0.5/领域知识/CONFIG/METRIC）保留
- BA-18~BA-24：原V3.0.0的11~17重新编号（BR依赖/接口初稿/优先级/系统类型/PRD组织/操作矩阵/视觉设计）

每条铁律标注：enforcement（hard/soft）+ workflow_check（在哪个workflow哪个步骤有可执行检查）。

补全缺失铁律：QA（当前1条→补全）、AC（当前0条→补全）、PO（当前0条→补全）。

### 3.3 config.yml 注册

```yaml
configs:
  gates_registry: ".codebuddy/knowledge/common/gates-registry.yml"
  iron_rules_registry: ".codebuddy/knowledge/common/iron-rules-registry.yml"
  redlines: ".codebuddy/knowledge/common/redlines.yml"
```

### 3.4 各workflow.yml 引用

```yaml
workflow:
  gates_reference: ".codebuddy/knowledge/common/gates-registry.yml#stages.requirement"
  iron_rules_reference: ".codebuddy/knowledge/common/iron-rules-registry.yml#agents.ba_agent"
```

### 3.5 各agent.md 引用

铁律章节改为引用注册中心 + 表格化展示编号/强制级别/workflow检查点。

### 3.6 PM completion_criteria 升级

```yaml
completion_criteria:
  - "终端已冻结"
  - "gates-registry.yml#stages.requirement 全部G-REQ-01~14 通过（PM逐条校验）"
  - "版本规划文档产出"
  - "用户确认范围无误"
```

## 五、预期效果

### 修复前
BA产出半成品 → PM completion_criteria只是文字 → Review"通过" → 进入设计（基于不完整需求）

### 修复后
BA产出文档 → PM按gates-registry G-REQ-01~14逐条校验 → G-REQ-01 FN缺失→驳回BA → 14条全通过才放行

### 统一管理效果
新增/修改铁律→只改iron-rules-registry.yml（1处）→所有agent.md和workflow.yml自动生效
新增/修改门禁→只改gates-registry.yml（1处）→所有workflow.yml和project-lifecycle.yml自动生效
