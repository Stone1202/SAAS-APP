# POM体系全面深度整改方案：流程重构+知识库重构+AI边界定义

> **讨论时间**：2026-07-18
> **核心命题**：全面整改所有流程机制，同时重构知识库体系，定义AI边界，防止AI"胡来"
> **基础**：基于对15个workflow.yml + 10个Agent + 30+个Skill + 三类知识库的全面扫描
> **参与专家**：11位专家联合

---

## 一、全景扫描发现：当前体系的三个根本性问题

### 问题1：流程是"线性流水线"不是"敏捷迭代"

**当前流程**：
```
脑暴→PO→需求→设计→架构→开发→测试→验收→handoff→close
  → 每个阶段一次性产出 → Review → 下一阶段
  → 问题在最后才发现 → 回流要重走全流程
```

**用户描述的真实流程**：
```
需求探索→设计磨合→架构→开发→Demo跑流程→测试→验收→发布
  → 迭代循环（Spring）→ 每个迭代Demo验证 → 开发进入下一迭代
  → 问题在Demo时就发现 → 当前迭代内修复
```

**差距**：当前流程是"瀑布式流水线"，用户需要的是"敏捷迭代循环"。

### 问题2：知识库三类知识边界模糊、引用断裂

**扫描发现的三类知识**：

| 知识类型 | 位置 | 定位 | 当前问题 |
|----------|------|------|----------|
| **通用知识** | `common/` | 跨项目共享的流程规范/标准/模板 | ①流程规范和知识规范混在一起 ②ba/qa/ops目录全是TODO空文件 ③arch/ux知识库存在但Agent不一定引用 |
| **领域知识** | `domains/` | 行业标准/第三方API文档 | ①DOMAIN-INDEX.yml定义了44个领域但只学习了1个 ②领域知识是静态的不会随项目进化 ③领域知识只被BA/BS引用，FD/QA不引用 |
| **项目知识** | `{project}/` | 当前项目的业务场景/已有交互/已有PRD | ①项目知识只有learn-project学习产出的PRD ②没有"项目交互规范"（已有页面长什么样/已有组件库是什么） ③没有"项目经验库"（之前犯过什么错） |

**引用断裂**：
```
BA引用领域知识 → 但BA不引用UX知识库（design-system.yml）→ BA不知道系统类型对应什么栅格
UX引用设计系统 → 但UX不引用领域知识 → UX不知道行业标准交互是什么
FD引用架构知识 → 但FD不引用UX知识库 → FD不知道Design Tokens怎么用
QA不引用任何知识库 → QA不知道业务规则/状态机/操作矩阵 → QA测试用例凭空编写
```

### 问题3：AI没有边界——规则是"建议"不是"约束"

**当前AI的边界问题**：

| AI行为 | 应该的边界 | 当前实际情况 |
|--------|-----------|-------------|
| BA产出需求 | 受doc-standards约束 | doc-standards是"模板"不是"约束"——BA可以不按模板产出，没有机器校验 |
| UX产出设计 | 受design-output-standards约束 | 同上——UX可以不按8章结构产出，没有校验 |
| FD生成代码 | 受11条铁律约束 | compliance-checker是"扫描模式"只报告不阻断——FD可以忽略违规 |
| QA测试通过 | 受pass_threshold约束 | pass_threshold是"文字描述"——QA可以报任何数字，没有可执行校验 |

**本质问题**：所有规则都是"建议性"的——写在yml文件中但不可执行、不阻断、不验证。AI可以遵守也可以不遵守，没有差别。

### 2.3 知识库的AI引用规则

```yaml
# AI读取知识库的统一规则（所有Agent适用）
knowledge_priority:
  1st: "项目知识库（项目特有）→ 最高优先级，项目特有的交互/技术/经验"
  2nd: "领域知识库（行业标准）→ 第二优先级，行业标准做法和第三方API"
  3rd: "通用知识库（通用规范）→ 第三优先级，通用流程/技术/设计规范"

knowledge_boundary:
  rule: "AI必须在知识库边界内行动，超出边界时必须请求人确认"
  examples:
    - "BA产出需求时，系统拆分必须参考互联网模式知识库，不能自行发明模式"
    - "UX产出设计时，栅格必须参考设计标准知识库，不能自行决定列数"
    - "FD生成代码时，组件必须参考技术标准知识库，不能自行选择组件库"
    - "AI遇到知识库未覆盖的情况→标注'知识库未覆盖'→请求人决策→人决策后更新知识库"
```

## 三、流程机制全面重构

### 3.1 从"线性流水线"到"敏捷迭代循环"

**当前流程（线性）**：
```
脑暴→需求→设计→架构→开发→测试→验收→close
  每个阶段一次性产出 → Review → 下一阶段
  问题在最后才发现 → 回流重走全流程
```

**重构后流程（敏捷迭代）**：
```
Sprint 0: 需求探索（AI辅助+人决策）
  → AI分析需求→识别互联网模式→建议系统拆分→建议终端
  → AI验证端到端闭环→标注边界模糊点
  → AI生成用例→AI验证用例贯穿
  → 人确认场景/边界/系统/端
  → 产出：需求规格（不是17章文档而是结构化的需求模型）

Sprint 1-N: 增量交付（每个Sprint交付1-3个页面）
  每个Sprint内部：
    → AI生成可交互原型（HTML组件，不是ASCII草图）
    → AI生成代码骨架（基于原型增强，不是从零写）
    → AI实现后置条件（自动翻译后置条件为代码）
    → AI运行时自测（build+test+dev启动+浏览器验证+行为验证）
    → AI Demo验证（自动跑核心流程+截图+报告）
    → 人确认体验/调优交互
    → AI自动化测试（Playwright执行+证据生成）
    → 人确认是否进入下一Sprint

Final Sprint: 集成验证
  → AI串联所有Sprint产出→跑端到端流程
  → AI可用性检查（布局/导航/视觉层次/任务完成率）
  → AI生成发布报告
  → 人确认发布
```

### 3.2 流程分层（AI动态选择）

```yaml
# AI根据项目特点动态选择流程级别
process_selection:
  input:
    - page_count: 页面数
    - module_count: 模块数
    - terminal_count: 终端数
    - project_type: 新项目/存量迭代/Bug修复
    - has_thirdparty_api: 是否有第三方接口
    - has_existing_design_system: 是否有已有设计系统

  rules:
    - condition: "page_count <= 3 && project_type == Bug修复"
      process: "lite"  # 3步：需求确认→AI生成→AI验证
      stages: ["require_confirm", "ai_generate", "ai_verify"]
      
    - condition: "page_count <= 15 && project_type == 存量迭代"
      process: "standard"  # 5步：需求→设计+代码→Demo→测试→确认
      stages: ["require_explore", "design_and_dev", "demo_verify", "auto_test", "confirm"]
      
    - condition: "page_count > 15 || project_type == 新项目"
      process: "full"  # 7步：需求→设计→架构→开发→Demo→测试→验收
      stages: ["require_explore", "design", "arch", "dev", "demo_verify", "test", "accept"]
```

### 3.3 每个阶段的重构

#### 需求阶段重构

```
当前：BA按§0.5六维分析→产出17章文档→PM Review文档结构

重构后：
  AI辅助：
    1. 场景识别——AI根据需求描述+互联网模式知识库→识别模式→建议系统拆分
    2. 闭环验证——AI自动检查端到端流程闭环→标注断点
    3. 用例贯穿——AI自动检查用例前后置对接→标注断点
    4. 后置条件标注——AI自动为每个FN标注仿真实现方式
  
  人决策：
    1. 确认场景理解
    2. 确认系统/终端拆分
    3. 确认边界归属
    4. 确认需求范围
  
  产出变化：
    从"17章markdown文档"→"结构化需求模型(YAML)"
    包含：系统/终端/角色/流程/FN/UC/BR/状态机/后置条件/验收标准
    每项都有AI验证标记（闭环✅/贯穿✅/后置✅）
```

#### 设计阶段重构

```
当前：UX按8章模板→产出markdown文档+ASCII草图

重构后：
  AI辅助：
    1. 布局生成——AI根据需求模型+设计标准知识库→自动生成布局(ProLayout/Tab导航)
    2. 栅格分配——AI根据页面内容→自动分配grid columns占比
    3. 可交互原型——AI生成真实HTML组件(不是ASCII草图)→dev server可访问
    4. Design Tokens——AI根据系统类型→自动生成Token→注入CSS变量
    5. 交互验证——AI自动验证菜单跳转/表单提交/弹窗操作/栅格落地
  
  人决策：
    1. 视觉调性确认
    2. 交互体验调优
    3. 品牌一致性确认
  
  产出变化：
    从"8章markdown+ASCII草图"→"可交互原型(HTML)+设计规格(YAML)"
    原型就是代码的初始版本，人调优后直接成为最终产物
```

#### 开发阶段重构

```
当前：FD按模板生成代码结构→compliance-checker静态扫描

重构后：
  AI辅助：
    1. 代码增强——AI基于设计阶段的可交互原型继续增强(原型已有布局/组件，开发补充数据/逻辑)
    2. 后置条件自动实现——AI读取FN后置条件→自动翻译为代码
    3. 运行时自测——AI自动执行8步验证：
       ①vite build ②vitest run ③dev server启动 ④浏览器打开核心页面
       ⑤菜单点击跳转 ⑥表单提交保存 ⑦后置条件检查 ⑧流程跑通
    4. 自修复——自测不通过→AI自动修复→重新自测→直到通过
  
  人决策：
    1. 复杂边界处理
    2. 性能优化方向
    3. 代码review
  
  产出变化：
    从"代码结构(可能不工作)"→"可运行代码(已通过8步验证)"
```

#### 测试阶段重构

```
当前：QA标注"手动验证✅"→测试报告

重构后：
  AI辅助：
    1. 测试用例生成——AI从需求模型自动生成(功能/流程/交互/状态/可用性)
    2. 自动化执行——AI用Playwright执行(打开→点击→输入→验证→截图)
    3. 证据生成——AI生成截图/录屏/执行日志
    4. 禁止手动验证——任何测试必须有自动化执行证据
  
  人决策：
    1. 测试策略确认
    2. 风险评估
    3. 发布决策
  
  产出变化：
    从"测试报告(可能虚假)"→"测试证据(截图+录屏+日志)"
```

## 四、AI边界定义

### 4.1 AI可以自主做的（不需要人确认）

| 行为 | 边界 | 知识库依赖 |
|------|------|-----------|
| 识别互联网模式 | 必须依据internet-patterns知识库 | 通用知识库 |
| 验证流程闭环 | 必须依据需求模型中的流程图 | 项目知识库 |
| 生成布局/栅格 | 必须依据design-standards知识库 | 通用知识库 |
| 生成代码骨架 | 必须依据tech-standards知识库 | 通用知识库 |
| 实现后置条件 | 必须依据post-condition-specs知识库 | 通用知识库 |
| 运行时自测 | 8步验证必须全部执行 | 无 |
| 自动化测试 | 必须用Playwright执行+生成证据 | 无 |
| 学习优化 | 从过程日志学习→输出建议 | 项目经验库 |

### 4.2 AI必须请求人确认的

| 行为 | 原因 | 人需要决策什么 |
|------|------|---------------|
| 系统拆分建议 | 可能不符合客户组织架构 | 确认拆分方案 |
| 终端选择建议 | 可能不符合实际设备需求 | 确认终端方案 |
| 边界模糊点 | 边界归属需要业务决策 | 确认边界归属 |
| 视觉调性 | 品牌一致性需要人判断 | 确认视觉方向 |
| 技术选型 | 可能不符合团队技术栈 | 确认技术方案 |
| 流程断点修复 | 断点修补方式需要业务决策 | 确认修复方案 |
| 发布决策 | 最终产物是否可用需要人判断 | 确认发布 |

### 4.3 AI不能做的（知识库边界外）

| 行为 | 原因 | 如果AI做了怎么办 |
|------|------|-----------------|
| 自行发明互联网模式 | 模式必须依据知识库 | 标注"知识库未覆盖"→请求人决策 |
| 自行决定栅格列数 | 列数必须依据设计标准 | 标注"标准未覆盖"→请求人决策 |
| 自行选择组件库 | 组件库必须依据技术标准 | 标注"标准未覆盖"→请求人决策 |
| 跳过运行时验证 | 验证是硬约束不可跳过 | 强制阻断 |
| 标注"手动验证✅" | 测试必须有自动化证据 | 强制阻断 |
| 修改知识库内容 | 知识库变更需人确认 | 标注"建议更新知识库"→人确认 |

### 核心改变总结

| 维度 | V4.x（当前） | V5.0（目标） |
|------|-------------|-------------|
| 流程 | 固定10阶段线性 | AI动态选择3-7步敏捷迭代 |
| 知识库 | 三类边界模糊引用断裂 | 三类清晰边界+优先级+AI边界 |
| AI角色 | 规则执行器 | 能力增强器（思考+验证+学习） |
| 验证 | 静态检查文件存在 | 运行时验证行为正确 |
| 设计产物 | ASCII草图 | 可交互HTML原型 |
| 开发自测 | 结构自检 | 行为自测(8步验证) |
| 测试 | 标注✅ | 自动化证据(截图+录屏) |
| 后置条件 | 人工实现 | AI自动实现 |
| 规则 | 人工硬编码 | AI学习后自主优化 |
| 经验 | 不积累 | 跨项目学习复用 |
