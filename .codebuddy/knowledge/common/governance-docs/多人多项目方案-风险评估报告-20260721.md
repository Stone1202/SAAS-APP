## 🔴 P0 严重风险（必须解决才能实施）

### P0-1：项目缺少 .gitignore 文件

**发现**：整个工作空间没有 .gitignore 文件。

**影响**：
- `node_modules/`（数千文件）、`dist/`（构建产物）、`.codebuddy/reports/` 等都会被 Git 跟踪
- 迁移和部署时仓库膨胀灾难
- 多人协作时频繁冲突

**缓解措施**：实施前先创建 .gitignore，排除：
```
node_modules/
dist/
.codebuddy/reports/
.codebuddy/_backup/
*.log
.DS_Store
```

**状态**：❌ 阻断，必须先解决

---

### P0-2：{project} 占位符影响面巨大，批量替换风险极高

**发现**：经实际搜索，`{project}` 占位符分布在 **69个文件、数百处**：

| 目录 | 文件数 | 匹配最多的文件 |
|------|--------|---------------|
| `.codebuddy/configs/` | 44个 | brainstorm.yml(30处)、project-lifecycle.yml(20处)、learn-project.yml(18处) |
| `.codebuddy/knowledge/common/` | 25个 | command-spec.yml、gates-registry.yml、doc-standards.yml 等 |

**影响**：
- 简单全局替换 `{project}` → `{owner}/{project}` 会误改不该改的地方（如文档中的描述性文字、示例代码等）
- 遗漏替换会导致路径断裂
- 改动量巨大，验证困难

**缓解措施**：**放弃全局替换策略，改为"向后兼容"策略**：
- `ensure-project.sh` 升级时解析 `{project}` 时自动补全 `{owner}/{project}`（即 `{project}` 仍然有效，脚本内部拼接 owner 前缀）
- 现有 YML 文件中的 `projects/{project}/` 路径模板**不修改**，由 ensure-project.sh 和运行时逻辑处理 owner 维度
- 只有**新增的**配置（.access-control.yml、DEPLOY-MANIFEST.yml 等）使用 `{owner}/{project}` 格式
- 这样改动量从"69个文件数百处"降到"1个脚本+几个新文件"

**状态**：❌ 阻断，需修改方案策略

### P0-3：knowledge/ 目录结构与方案不一致

**发现**：现有 knowledge/ 下有**多种并存的项目知识组织方式**：

```
.codebuddy/knowledge/
├── 百货商城/          ← 直接在 knowledge/ 下（12个md文件）
├── 群管易/            ← 直接在 knowledge/ 下
├── AI-SCRM/           ← 直接在 knowledge/ 下（business-topology.json）
├── SAAS/              ← 直接在 knowledge/ 下（36个文件）
├── projects/
│   └── AI-SCRM/       ← 在 projects/ 子目录下
├── common/            ← 通用知识
└── domains/           ← 领域知识
```

方案中设计的是 `knowledge/projects/{owner}/{project}/`，但现有结构是：
1. 部分项目知识直接在 `knowledge/{项目名}/` 下
2. 部分在 `knowledge/projects/{项目名}/` 下
3. 没有 owner 维度

**影响**：
- 迁移目标不明确——哪些该迁、哪些保留
- `knowledge-sedimentation.yml` 引用 `knowledge/{project}/版本沉淀/`（无 owner）
- 迁移可能导致知识库路径断裂

**缓解措施**：
1. 现有项目知识**暂不迁移**（保持原位），仅新增项目使用新结构 `knowledge/projects/{owner}/{project}/`
2. `knowledge-sedimentation.yml` 中的路径改为兼容两种格式（优先查 `{owner}/{project}/`，回退查 `{project}/`）
3. 后续逐步迁移旧项目知识

**状态**：❌ 阻断，需修改方案策略

### P0-4：经验库路径不一致（方案 vs 实际配置）

**发现**：
- 方案中写的是 `knowledge/experience/`（英文目录名，.yml 文件）
- `knowledge-sedimentation.yml` 实际引用的是 `knowledge/common/经验库/`（中文目录名，.md 文件）
- 具体文件：`common/经验库/最佳实践库.md`、`common/经验库/踩坑避雷库.md`、`common/经验库/Review模式库.md`

**影响**：
- 方案与实际配置不一致，实施时会产生分歧
- 审核机制设计（_pending/ 目录）需要基于实际路径

**缓解措施**：统一为实际配置路径 `knowledge/common/经验库/`：
- 方案中的 `knowledge/experience/` 改为 `knowledge/common/经验库/`
- `_pending/` 目录改为 `knowledge/common/经验库/_pending/`
- 领域知识的 _pending 保持 `knowledge/domains/_pending/`

**状态**：❌ 阻断，需修改方案

### P0-5：EdgeOne Pages 配置格式未验证

**发现**：方案中的 `deploy/edgeone-pages.json` 配置格式是基于 Vercel 的经验推测的，未实际验证。

4. 如果 EdgeOne Pages 能力不足，回退到备选方案（腾讯云COS+CDN）

**状态**：❌ 阻断，需先验证

## 🟡 P1 重要风险（需预案）

### P1-1：ensure-project.sh 硬编码严重

**发现**：
- 第31行：`proj_dir = os.path.join(root, f"projects/{proj}")` — 无 owner 维度
- 第217行：`server: { port: 3333, host: true }` — 端口硬编码
- 所有 `ensure_dir` 调用都是 `projects/{proj}/...` 格式

**影响**：升级改动量大，容易遗漏

**缓解措施**：采用 P0-2 的"向后兼容"策略，脚本内部处理 owner 拼接，减少改动量

---

### P1-2：state.json 迁移

**发现**：`projects/AI-SCRM/.codebuddy/state.json`（5.76KB）包含完整流状态，其中 `"project": "AI-SCRM"` 字段。

**影响**：迁移到 `projects/jojo/AI-SCRM/` 时需要保留状态，但路径引用可能断裂

**缓解措施**：
1. state.json 随项目目录一起迁移（`projects/AI-SCRM/` → `projects/jojo/AI-SCRM/`）
2. state.json 内的 `"project": "AI-SCRM"` 字段保持不变（项目名不变，只是路径变了）
3. 运行时逻辑兼容：读 state.json 时不依赖完整路径，只依赖项目名

---

### P1-3：indexedDB.databases() 浏览器兼容性

**发现**：旧数据迁移方案依赖 `indexedDB.databases()` API，当前代码未使用此 API。

**影响**：
- Chrome 71+ 支持，Safari 16+ 支持
- 旧版浏览器（如 Safari 15 及以下）不支持，迁移会失败

**缓解措施**：添加降级方案：
```typescript
async function checkOldDBExists(oldName: string): Promise<boolean> {
  // 优先使用 databases() API
  if (indexedDB.databases) {
    const dbs = await indexedDB.databases();
    return dbs.some(db => db.name === oldName);
  }
  // 降级：尝试打开旧库，成功则存在
  try {
    await openDB(oldName);
    return true;
  } catch {
    return false;
  }
}
```

### P1-4：CODEOWNERS 只是软约束

**发现**：成员克隆仓库后本地能看到所有文件（包括流程引擎 configs/、scripts/、knowledge/common/）。

**影响**：流程引擎"不可见"的目标在 Git 协作模式下无法通过 CODEOWNERS 完全实现

**缓解措施**：
1. 第一阶段：逻辑约束（.access-control.yml + AI 不加载）+ CODEOWNERS + 使用规范
2. 第二阶段（可选）：Git 子模块物理隔离——流程引擎拆为私有子模块

---

### P1-5：_pending/ 目录的 Git 可见性

**发现**：待审核的知识库内容如果在仓库中，其他成员通过 git 能看到。

**影响**：审核机制失效——成员能看到其他人的待审核内容

**缓解措施**：
1. `_pending/` 目录加入 .gitignore（不提交到仓库）
2. 成员的待审核内容只在本地，通过 PR 提交时管理员审核
3. 或者：`_pending/` 提交到仓库但通过 CODEOWNERS 限制只有 admin + 贡献者可读

## 🟢 P2 次要风险（实施中解决）

### P2-1：端口池容量
- 4000-4099 共100个端口，足够当前使用
- 如不够可扩展到 4000-4199
- 需检测端口被系统其他程序占用的情况

### P2-2：迁移并发问题
- 多浏览器标签页同时打开时，迁移可能重复执行
- 用 `migrationDone` 标志位控制，但跨标签页不共享
- 缓解：迁移函数加幂等检查（新库已有数据则跳过）

### P2-3：版本号一致性
- config.yml v4.0.0、PROJECT-INDEX.yml v2.0.0、project-lifecycle.yml v4.3.0 等版本号需同步
- 实施时统一更新流程版本变更总账

### P2-4：.env 文件缺少新变量
- 现有 .env.development 只有4个变量（VITE_MODE/VITE_API_BASE/VITE_WS_URL/VITE_AUTH_MODE）
- 需新增 VITE_PROJECT_ID 和 VITE_DEV_PORT
- 改动简单，风险低

1. ❌ 缺 .gitignore → 先创建
