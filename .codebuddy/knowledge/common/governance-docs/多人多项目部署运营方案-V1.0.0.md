# 多人多项目部署运营方案（V1.0.0）

> **文档定位**：将 POM 工作流从"单人单项目"升级为"多人多项目多版本多终端"的协作部署运营体系。
> **版本**：V1.0.0 | **日期**：2026-07-21
> **对齐**：POM V5.1.4
> **核心原则**：流程引擎是管理员私有资产（成员不可见不可改），知识库是团队共享资产。
> **已确认决策**：部署目标=EdgeOne Pages（国内CDN） | 端口路由=单域名+路径路由 | 目录结构=按成员隔离 | IndexedDB=数据库名加项目标识隔离

---

## 一、问题与目标

### 1.1 当前痛点

| 症状 | 根因 |
|------|------|
| 工作流/Agent/Skill/指令配置对所有人可见可改，成员可能误改流程引擎 | `.codebuddy/` 无角色权限隔离，所有文件对全员平等 |
| 多人各自有项目，但 `projects/` 是扁平结构，项目名可能冲突 | `projects/{project}/` 无 owner 维度，PROJECT-INDEX.yml 无成员归属 |
| 成员学习产出的领域知识无法跨成员复用 | 学习产物散落在各自项目目录，无统一共享层 |
| `/close` 只做 Git Tag + build:sim 归档到本地，无远端部署 | stage-8 快照后流程终止，缺少 stage-9 部署运营阶段 |
| 多项目多终端访问端口冲突，vite 硬编码 `port: 3333` | 无端口池分配机制，无统一网关路由 |
| 成员不知道自己的版本部署在哪、如何访问 | 无 DEPLOY-MANIFEST，无访问入口聚合页 |
| 多项目部署到同一域名，IndexedDB 数据会串 | `db.ts` 数据库名写死为 `ai-scrm-sim`，不区分项目 |

### 1.2 设计目标

```
① 权限隔离：流程引擎（configs/scripts/workflows/agents/skills）管理员私有，成员不可见不可改
② 知识共享：领域知识库（domains/）+ 经验库（experience/）全员共享可贡献
③ 项目隔离：projects/{owner}/{project}/ 按成员隔离，互不干扰
④ 数据隔离：IndexedDB 数据库名加项目标识，不同项目数据不串
⑤ 自动部署：/close 后自动 build → 推送 EdgeOne Pages → 路径路由 → 生成访问入口
⑥ 端口统一：单域名 + 路径路由（/{owner}/{project}/{version}/），成员无需关心端口
```

### 1.3 两大核心诉求（用户明确强调）

| 诉求 | 内容 | 可见性 |
|------|------|--------|
| 🔒 流程引擎私有 | 工作流、Agent、指令、Skill、铁律、门禁、方法论标准 | 成员**不可见、不可修改** |
| 🌐 知识库共享 | 领域知识（/learn-domain 产出）、经验库（版本沉淀提炼） | 全员**可读、可贡献** |

## 二、角色与权限模型

### 2.1 角色定义

| 角色 | 标识 | 职责 | 权限边界 |
|------|------|------|----------|
| **管理员** | `admin` | 维护流程引擎、管理成员、管理部署配置 | 全权访问所有目录，可读写 `.codebuddy/` 全部内容 |
| **成员** | `member` | 使用流程命令、学习项目知识、开发自己的项目 | 可读共享知识库；可读写自己的 `projects/{owner}/`；**不可见** `configs/scripts/knowledge/common/` |

### 2.2 权限矩阵

```
目录                                    | admin | member
───────────────────────────────────────|───────|-------
.codebuddy/configs/   (流程引擎)        |  RW   |  ---    🔒 私有
.codebuddy/scripts/   (脚本工具)        |  RW   |  ---    🔒 私有
.codebuddy/knowledge/common/ (方法论)   |  RW   |  ---    🔒 私有（流程的一部分）
.codebuddy/knowledge/domains/ (领域)        |  RW   |  R+    🌐 共享（可读+可贡献）
.codebuddy/knowledge/common/经验库/ (经验)  |  RW   |  R+    🌐 共享（可读+可贡献）
.codebuddy/knowledge/projects/{owner}/      |  RW   |  自己RW/他人---
.codebuddy/knowledge/PROJECT-INDEX.yml  |  RW   |  R     🌐 只读（知道自己和别人的项目存在）
projects/{owner}/{project}/             |  RW   |  自己RW/他人---
deploy/                (部署配置)        |  RW   |  ---    🔒 私有
.access-control.yml    (访问控制)        |  RW   |  ---    🔒 私有
```

> **R+** = 可读 + 可通过 `/learn-domain`、`/close` 等流程**追加贡献**（由流程引擎代写，成员不直接编辑文件）。

### 2.3 访问控制配置（新增 `.access-control.yml`）

```yaml
# .access-control.yml — 访问控制配置（管理员维护）
# CodeBuddy 启动时读取此文件，确定当前用户的角色和权限边界
version: "1.0.0"

# 当前用户识别方式（优先级从高到低）
user_identification:
  - env_var: "CODEBUDDY_USER"       # 环境变量指定用户ID
  - git_config: "user.name"         # git user.name 匹配 members[].git_name
  - fallback: "admin"               # 默认管理员（单开发场景兼容）

members:
  - id: "jojo"
    name: "Jojo"
    git_name: "jojo"
    role: "admin"
    active_project: "AI-SCRM"
  - id: "zhangsan"
    name: "张三"
    git_name: "zhangsan"
    role: "member"
    active_project: "erp-portal"

# 权限边界定义
permission_boundary:
  admin:
    can_read: ["**"]
    can_write: ["**"]
    can_execute: ["**"]
  member:
    can_read:
      - ".codebuddy/knowledge/domains/**"       # 共享领域知识
      - ".codebuddy/knowledge/experience/**"     # 共享经验库
      - ".codebuddy/knowledge/PROJECT-INDEX.yml" # 项目注册表（只读）
      - ".codebuddy/knowledge/projects/{self_owner}/**"  # 自己的项目沉淀
      - "projects/{self_owner}/**"               # 自己的项目
    can_write:
      - "projects/{self_owner}/**"               # 只能写自己的项目
      # 知识库贡献通过流程命令间接写入，不直接编辑
    can_execute:
      - "/brainstorm"
      - "/init"
      - "/learn-project"
      - "/learn-domain"
      - "/test"
      - "/accept"
      - "/feedback"
      - "/close"
      - "/report"
      - "/handoff"
    forbidden:
      - ".codebuddy/configs/**"        # 不可见流程引擎
      - ".codebuddy/scripts/**"        # 不可见脚本
      - ".codebuddy/knowledge/common/**" # 不可见方法论
      - "deploy/**"                    # 不可见部署配置
      - ".access-control.yml"          # 不可见访问控制本身
```

### 2.4 权限执行机制

**物理层面**（Git 仓库权限）：
- `.codebuddy/configs/`、`.codebuddy/scripts/`、`.codebuddy/knowledge/common/`、`deploy/`、`.access-control.yml` → 在单独的 `engine` 分支或私有子模块，成员分支不可见
- 成员分支只包含：`projects/{owner}/` + 共享知识库的只读快照

**逻辑层面**（AI 行为约束）：
- CodeBuddy 启动时读取 `.access-control.yml`，确定当前用户角色
- 成员角色的 AI 助手：
  - 不加载 `configs/` 下的 YML 内容到上下文（只通过命令执行间接引用）
  - 拒绝成员尝试读写 `forbidden` 路径的请求
  - 执行命令时由流程引擎代为读写共享知识库（成员不直接编辑文件）

> **关键设计**：成员使用 `/learn-domain`、`/close` 等命令时，流程引擎会自动将产出写入共享知识库，成员无需（也无法）手动编辑知识库文件。这保证了知识库的**结构一致性**——所有人贡献的知识都经过流程引擎校验。

## 四、多人多项目组织机制

### 4.1 成员入驻流程

```
管理员操作：
  ① 在 .access-control.yml 注册成员（id/name/git_name/role）
  ② 在 PROJECT-INDEX.yml members[] 添加成员条目
  ③ 分配端口池中的一个端口
  ④ 通知成员：使用 /init --owner=zhangsan --project=erp-portal 开始

成员首次使用：
  ① CodeBuddy 读取 .access-control.yml → 识别为 member 角色
  ② /init --owner=zhangsan --project=erp-portal --type=新增 --desc=...
  ③ ensure-project.sh 在 projects/zhangsan/erp-portal/ 创建骨架
     → 分配端口 4001，写入 .env.development
     → 生成 VITE_PROJECT_ID=zhangsan-erp-portal，写入 .env
  ④ 成员开始需求分析流程
```

### 4.2 命令参数升级

所有命令新增 `--owner` 可选参数（缺省时从 `.access-control.yml` 识别当前用户）：

```bash
# 管理员操作自己的项目
/init --project=AI-SCRM --type=新增 --desc=...

# 成员操作自己的项目（owner 自动识别）
/init --project=erp-portal --type=新增 --desc=...

# 显式指定 owner（跨成员协作时）
/init --owner=zhangsan --project=erp-portal --type=新增 --desc=...
```

### 4.3 知识库贡献与共享

```
成员执行 /learn-domain → 产出写入：
  .codebuddy/knowledge/domains/{category}/{domain}.yml    🌐 全员可读

成员执行 /close → 经验提炼写入：
  .codebuddy/knowledge/experience/lessons-learned.yml     🌐 全员可读
  .codebuddy/knowledge/experience/best-practices.yml      🌐 全员可读
  .codebuddy/knowledge/experience/pitfalls.yml            🌐 全员可读

成员的项目沉淀写入：
  .codebuddy/knowledge/projects/{owner}/{project}/版本沉淀/  🔒 仅自己可读
```

**关键约束**：知识库文件由流程引擎代写（成员执行命令时 AI 按 YML 规范写入），成员不能手动编辑知识库文件。这保证了：
- 结构一致性：所有人贡献的知识都经过流程引擎校验
- 格式规范：YML 结构统一，可被所有 Agent 解析
- 权限安全：成员无法绕过流程直接改文件

### 4.4 跨成员协作场景

| 场景 | 机制 |
|------|------|
| 成员A引用成员B的领域知识 | 直接读 `knowledge/domains/`（共享层） |
| 成员A参考成员B的项目经验 | 读 `knowledge/experience/`（共享经验库） |
| 成员A查看成员B的项目PRD | 需管理员授权（读 `knowledge/projects/{B}/{project}/`） |
| 管理员接手成员的项目 | 管理员有全权，直接操作 `projects/{B}/{project}/` |

## 五、IndexedDB 数据隔离方案

### 5.1 问题分析

高保真仿真架构使用 IndexedDB 存储本地数据（`src/adapters/sim/db.ts`）。IndexedDB 按 **Origin（协议+域名+端口）** 隔离，**不按路径隔离**。

在"单域名+路径路由"方案下，所有项目版本共享同一 Origin：
```
https://{domain}/jojo/AI-SCRM/v1.0.0/         → Origin 相同 → 同一个 IndexedDB
https://{domain}/zhangsan/erp-portal/v1.0.0/   → Origin 相同 → 同一个 IndexedDB
https://{domain}/jojo/AI-SCRM/v2.0.0/          → Origin 相同 → 同一个 IndexedDB
```

当前代码 `db.ts` 第7行数据库名写死：
```typescript
const DB_NAME = 'ai-scrm-sim';  // ← 所有项目共用同一个数据库，数据会串
```

### 5.2 隔离策略

| 场景 | 是否隔离 | 原因 |
|------|---------|------|
| **不同项目**（AI-SCRM vs erp-portal） | ✅ 必须隔离 | 不同项目数据结构不同，混在一起会冲突 |
| **同一项目不同版本**（v1.0.0 vs v2.0.0） | ❌ 不隔离（数据延续） | 版本升级时用户数据自动延续，不需重新初始化，这是优势 |

### 5.3 解决方案：数据库名加项目标识

**`db.ts` 升级**（1行代码改动）：

```typescript
// 升级前
const DB_NAME = 'ai-scrm-sim';

// 升级后
// 构建时注入项目标识（vite 环境变量）
const PROJECT_ID = import.meta.env.VITE_PROJECT_ID || 'ai-scrm';
const DB_NAME = `${PROJECT_ID}-sim`;
// jojo/AI-SCRM     → "jojo-ai-scrm-sim"
// zhangsan/erp-portal → "zhangsan-erp-portal-sim"
```

**环境变量注入**（`ensure-project.sh` 创建骨架时自动写入）：

`.env.development`：
```bash
VITE_DEV_PORT=4001
VITE_MODE=sim
VITE_PROJECT_ID=jojo-ai-scrm          # 🆕 项目标识
```

`.env.production`：
```bash
VITE_MODE=sim
VITE_PROJECT_ID=jojo-ai-scrm          # 🆕 部署态也注入
```

`.env.sim`（build:sim 专用）：
```bash
VITE_MODE=sim
VITE_PROJECT_ID=jojo-ai-scrm
```

### 5.4 效果

```
浏览器 IndexedDB 数据库列表：
  ├── jojo-ai-scrm-sim           ← jojo 的 AI-SCRM（所有版本共用，数据延续）
  ├── zhangsan-erp-portal-sim    ← 张三的 erp-portal（独立隔离）
  └── ...
```

- ✅ 不同项目数据**完全隔离**（不同的数据库）
- ✅ 同一项目不同版本数据**自动延续**（版本升级不丢数据）
- ✅ 改动量极小（1行代码 + 环境变量）
- ✅ 向后兼容（未设置 VITE_PROJECT_ID 时回退到 `ai-scrm-sim`）

### 5.5 数据库迁移说明

现有 `projects/AI-SCRM/` 迁移到 `projects/jojo/AI-SCRM/` 时：
- 浏览器中已有 `ai-scrm-sim` 数据库（旧数据）
- 升级后数据库名变为 `jojo-ai-scrm-sim`
- 旧数据不会自动迁移（新数据库为空，首次访问时触发种子数据初始化）
- 如需保留旧数据，可在首次启动时检测旧库 `ai-scrm-sim` 并迁移到 `jojo-ai-scrm-sim`（一次性迁移逻辑，可选）

## 六、远端部署链路（EdgeOne Pages）

### 6.1 为什么选 EdgeOne Pages

| 对比项 | EdgeOne Pages | Vercel | Gitee Pages |
|--------|--------------|--------|-------------|
| 国内访问速度 | ⚡ 快（腾讯云CDN） | 🐢 慢（海外节点） | ⚡ 快 |
| 免费额度 | ✅ 有 | ✅ 有 | ✅ 完全免费 |

## 七、端口路由策略（单端口+路径路由）

### 7.1 双态端口策略

| 状态 | 策略 | 说明 |
|------|------|------|
| **开发态**（`vite dev`） | 端口池自动分配 | 每个项目分配独立端口（4000-4099），写入 `.env.development` |
| **部署态**（`/close` 后） | 单域名+路径路由 | EdgeOne Pages 天然支持路径路由，无需端口 |

### 7.2 开发态端口池

```yaml
# config.yml 新增 port_pool 配置
port_pool:
  range: [4000, 4099]          # 端口池范围
  allocation: "auto"           # auto（自动分配空闲端口）| manual（手动指定）
  reserved:                    # 已分配端口（ensure-project.sh 自动维护）
    - { owner: "jojo", project: "AI-SCRM", port: 3333 }      # 管理员保留原端口
    - { owner: "zhangsan", project: "erp-portal", port: 4001 }
```

**vite.config.ts 升级**（读取环境变量）：
```typescript
export default defineConfig(({ mode }) => ({
  plugins: [react()],
  resolve: {
    alias: {
      "@": path.resolve(__dirname, "src"),
      "@contracts": path.resolve(__dirname, "src/contracts"),
      "@adapters": path.resolve(__dirname, "src/adapters"),
      "@services": path.resolve(__dirname, "src/services"),
    },
  },

    port: parseInt(process.env.VITE_DEV_PORT || '3333'),

  },

```

**ensure-project.sh 升级**：创建项目骨架时从端口池分配空闲端口，写入 `.env.development`：
```bash
VITE_DEV_PORT=4001
VITE_MODE=sim
VITE_PROJECT_ID=zhangsan-erp-portal
```

### 7.3 部署态路径路由

部署态完全不需要端口——EdgeOne Pages 用路径路由：

```
https://{domain}/{owner}/{project}/{version}/    →  该版本静态产物
https://{domain}/{owner}/{project}/latest/       →  最新版本（重定向）
https://{domain}/                                →  访问门户聚合页
```

**版本切换器**（与 V5.0 版本差异能力对齐）：
- 访问门户提供版本切换器（single / diff_highlight / side_by_side 三模式）
- 切换版本时 URL 路径变化，页面重新加载对应版本产物

### 7.4 IndexedDB 在路径路由下的数据隔离

路径路由下所有项目版本共享同一 Origin（域名），IndexedDB 默认会串数据。通过第五章的数据库名隔离方案解决：

```
同一 Origin 下：
  ├── jojo-ai-scrm-sim           ← jojo 的数据（所有版本共用）
  ├── zhangsan-erp-portal-sim    ← 张三的数据（独立）
  └── ...
```

**数据不互通是设计预期**：不同成员的项目数据互相隔离，同成员同项目的不同版本数据自动延续。

### 10.5 旧数据迁移：需要迁移

**迁移机制**（db.ts 首次启动自动检测）：
```typescript
// db.ts 升级后的 getDB() 逻辑
export async function getDB(): Promise<IDBPDatabase> {
  const PROJECT_ID = import.meta.env.VITE_PROJECT_ID || 'ai-scrm';
  const DB_NAME = `${PROJECT_ID}-sim`;
  
  // 1. 检查旧数据库是否存在（仅 jojo-ai-scrm 场景）
  if (DB_NAME === 'jojo-ai-scrm-sim') {
    await migrateOldDB('ai-scrm-sim', DB_NAME);
  }
  
  // 2. 正常打开新数据库
  dbInstance = await openDB(DB_NAME, DB_VERSION, { ... });
  return dbInstance;
}

// 一次性迁移函数
async function migrateOldDB(oldName: string, newName: string) {
  const oldExists = await indexedDB.databases?.().then(dbs => 
    dbs.some(db => db.name === oldName)
  );
  if (!oldExists) return;  // 无旧库，跳过
  
  // 打开旧库 → 读取所有 objectStore 数据 → 写入新库 → 删除旧库
  const oldDB = await openDB(oldName);
  const newDB = await openDB(newName, DB_VERSION, { upgrade });
  
  for (const storeName of oldDB.objectStoreNames) {
    const allData = await oldDB.getAll(storeName);
    const tx = newDB.transaction(storeName, 'readwrite');
    for (const item of allData) {
      await tx.store.put(item);
    }
    await tx.done;
  }
  
  oldDB.close();
  indexedDB.deleteDatabase(oldName);  // 迁移完成后删除旧库
  console.log(`[数据迁移] ${oldName} → ${newName} 完成`);
}
```

## 附录G：旧数据迁移方案

### G.1 迁移场景

现有 `projects/AI-SCRM/` 迁移到 `projects/jojo/AI-SCRM/` 后：
- 浏览器中已有旧数据库 `ai-scrm-sim`（含种子数据 + 用户操作数据）
- 升级后数据库名变为 `jojo-ai-scrm-sim`
- 需要将旧库数据迁移到新库

### G.2 迁移逻辑（db.ts 内置）

```typescript
// src/adapters/sim/db.ts 升级

const OLD_DB_NAME = 'ai-scrm-sim';
const PROJECT_ID = import.meta.env.VITE_PROJECT_ID || 'ai-scrm';
const DB_NAME = `${PROJECT_ID}-sim`;
const DB_VERSION = 1;

let dbInstance: IDBPDatabase | null = null;
let migrationDone = false;

export async function getDB(): Promise<IDBPDatabase> {
  if (dbInstance) return dbInstance;

  // 1. 一次性迁移（仅 jojo-ai-scrm 场景）
  if (!migrationDone && DB_NAME !== OLD_DB_NAME) {
    await migrateOldDBIfNeeded();
    migrationDone = true;
  }

  // 2. 正常打开新数据库
  dbInstance = await openDB(DB_NAME, DB_VERSION, {
    upgrade(db) { /* 原有 objectStore 创建逻辑不变 */ },
  });

  return dbInstance;
}

async function migrateOldDBIfNeeded(): Promise<void> {
  // 检测旧库是否存在
  const databases = await indexedDB.databases();
  const oldExists = databases.some(db => db.name === OLD_DB_NAME);
  if (!oldExists) {
    console.log('[数据迁移] 无旧数据库，跳过迁移');
    return;
  }

  console.log(`[数据迁移] 检测到旧数据库 ${OLD_DB_NAME}，开始迁移到 ${DB_NAME}...`);

  // 打开旧库（只读）
  const oldDB = await openDB(OLD_DB_NAME);

  // 打开新库（带 schema 初始化）
  const newDB = await openDB(DB_NAME, DB_VERSION, {
    upgrade(db) { /* 原有 objectStore 创建逻辑不变 */ },
  });

  // 逐个 objectStore 迁移数据
  const storeNames = [
    'customers', 'tagGroups', 'tags', 'communicationRecords',
    'scripts', 'todos', 'segments', 'tenants',
    'versionFeatures', 'subscriptionOrders', 'aiScriptSuggestions',
  ];

  let totalMigrated = 0;
  for (const storeName of storeNames) {
    if (!oldDB.objectStoreNames.contains(storeName)) continue;

    const allData = await oldDB.getAll(storeName);
    if (allData.length === 0) continue;

    const tx = newDB.transaction(storeName, 'readwrite');
    for (const item of allData) {
      await tx.store.put(item);
    }
    await tx.done;
    totalMigrated += allData.length;
    console.log(`[数据迁移] ${storeName}: ${allData.length} 条`);
  }

  // 关闭并删除旧库
  oldDB.close();
  await indexedDB.deleteDatabase(OLD_DB_NAME);

  console.log(`[数据迁移] 完成！共迁移 ${totalMigrated} 条数据，旧库已删除`);
}
```

### G.3 迁移触发时机

- **自动触发**：用户首次访问升级后的 `jojo/AI-SCRM` 原型时，`getDB()` 自动检测并迁移
- **一次性**：迁移完成后 `migrationDone = true`，后续不再触发
- **安全删除**：迁移成功后才删除旧库，迁移失败保留旧库（可重试）
