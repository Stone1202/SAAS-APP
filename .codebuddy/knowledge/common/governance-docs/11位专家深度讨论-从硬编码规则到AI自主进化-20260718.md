# 11位专家深度讨论：从硬编码规则到AI自主进化——POM体系的根本性重构

> **讨论时间**：2026-07-18
> **核心命题**：用户描述了过去人工项目流程的真实形态（场景→流程→角色→系统→端→用例→设计→架构→开发→Demo→测试→验收→发布），提出AI能否帮人处理重复思考/验证，而非只执行硬编码规则；AI能否定期学习项目过程日志，持续优化流程/Agent/Skill/Rule
> **参与专家**：项目流程管理专家 / 专业项目经理 / 产品专家 / 需求分析专家 / UI设计专家 / 交互设计专家 / 专业架构专家 / 技术经理 / 全栈开发工程师 / 测试专家 / 可用性测试专家

## 序言：用户描述的真实流程 vs 当前POM流程的本质差异

### 用户描述的真实人工流程

```
1. 需求分析：和客户聊→找场景/流程/参与人/角色→按B2B/B2C/F2B2C/C2C/O2O拆分业务系统→呈现端
   →端到端/系统到系统闭环→反复确认边界→每端每系统梳理业务流程/信息流/状态/时序
   →整理用例→用例通过系统/页面/角色/前置/后置贯穿→最怕单个功能可以但流程跑不通

2. 设计：拿到PRD（含流程/草图/说明）→按业务系统/端确定信息布局/间距/ICON/按钮→视觉设计
   →反复磨合交互→可能推翻需求分析产物

3. 架构：根据需求业务框架/系统/端→结合服务器资源/公共性/一致性/并发→架构

4. 技术经理：基于架构→输出开发标准

5. 开发：根据拆解任务→单个任务开发

6. Demo：迭代完成→大家一起Demo跑流程→没问题→测试进入/开发进入下一迭代→循环往复

7. 测试：集成测试

8. 验收：可用性/流程性/易用性

9. 发布
```

### 当前POM AI流程的根本问题

```
当前POM：
  1. 硬编码10个阶段→每个阶段硬编码子步骤→每个步骤硬编码产物→每个产物硬编码门禁
  2. AI执行方式：读取yml规则→按规则产出文档→按规则检查文档→标注通过
  3. AI不做"思考"只做"执行"——不找场景、不磨合、不反复确认、不跑流程、不Demo
  4. AI不学习——每次项目都是从零开始按同一套硬编码规则执行，不会因为上次犯的错而改变

真实人工流程：
  1. 人通过"对话"找场景/边界/流程——这是探索性思考不是执行规则
  2. 人通过"反复磨合"验证设计——这是迭代式思考不是一次性产出
  3. 人通过"Demo跑流程"验证产物——这是运行时验证不是静态检查
  4. 人通过"经验"避免重复犯错——这是学习进化不是固定规则
```

**本质差异**：人工流程是**探索性+迭代性+验证性+学习性**的，当前POM AI是**执行性+一次性+静态性+固定性**的。

## 一、项目流程管理专家：流程应该是"骨架"不是"模具"

### 核心观点

当前POM把流程做成了"模具"——每个项目都必须按同一个模具注塑成型。但真实项目中流程是"骨架"——提供基本结构，但具体怎么走取决于项目特点。

### 用户描述的流程特征分析

| 特征 | 用户描述 | 当前POM | 差距 |
|------|----------|---------|------|
| **探索性** | "和客户聊找场景"——需求不是一次性产出而是探索发现 | BA按§0.5六维分析一次性产出 | POM不探索只执行 |
| **迭代性** | "反复确认边界""反复磨合交互""Demo跑流程循环往复" | 每阶段一次性产出→Review→下一阶段 | POM不迭代只流水线 |
| **验证性** | "Demo跑流程""集成测试""可用性验收" | 静态检查文档+标注通过 | POM不验证只标注 |
| **学习性** | "最怕单个功能可以但流程跑不通"——经验驱动避免重复犯错 | 每次项目从零开始同一套规则 | POM不学习只重复 |
| **弹性** | 小功能不跑全流程，大版本才跑全流程 | 10个阶段每个项目都走全流程 | POM不弹性只僵化 |

### 专家建议：流程分层+AI辅助决策

**流程不应该硬编码为"10个阶段都必须走"，而应该AI根据项目特点动态决定走哪些阶段：**

```yaml
# 不是硬编码的流程，而是AI判断的流程
process_decision:
  input:
    - 需求描述
    - 项目规模（页面数/模块数/终端数）
    - 项目类型（新项目/存量迭代/Bug修复）
  
  ai_decision:
    # AI根据输入判断走哪个流程级别
    - if 规模≤3页面 && 类型=Bug修复:
        → 轻量流程：需求确认→开发→验证（3步）
    - if 规模≤10页面 && 类型=存量迭代:
        → 标准流程：需求→设计→开发→Demo→测试（5步）
    - if 规模>10页面 || 类型=新项目:
        → 全流程：脑暴→需求→设计→架构→开发→Demo→测试→验收（8步）
    
    # AI根据项目特点决定哪些步骤可以简化
    - if 单终端:
        → 跳过多端适配设计/跨端一致性测试
    - if 无第三方接口:
        → 跳过接口契约设计/接口时序图
    - if 存量项目已有设计系统:
        → 跳过Design Tokens定义，复用已有
```

**关键改变**：流程从"硬编码必须走10阶段"变成"AI根据项目特点动态决定走几个阶段"。

## 二、专业项目经理：AI应该是"项目伙伴"不是"流程执行器"

### 核心观点

真实的项目经理做的不是"按流程推进"而是"持续判断+协调+验证"。AI PM应该做的是：

### 2.1 持续判断（当前POM不做）

```
真实PM的日常：
  - 开发说"完成了"→PM不会直接相信，会问"你自己在浏览器里试了吗？菜单能点吗？"
  - 设计师说"设计好了"→PM会问"这个交互在移动端能用吗？你试过吗？"
  - 测试说"全通过了"→PM会问"你在浏览器里实际操作了吗？给我看看执行日志"

当前AI PM：
  - FD说"vite build通过"→PM标注"开发完成✅"
  - QA说"32用例25通过"→PM标注"测试通过✅"
  - 从不问"你实际试了吗？"
```

**AI PM应该具备的能力**：对每个"完成"声明进行**信任度评估**——如果是自动化执行的证据（vitest日志/build日志），信任度高；如果是人工标注（"手动验证✅"），信任度低，必须要求补充证据或自己验证。

### 2.2 协调磨合（当前POM不做）

```
真实PM的协调：
  - 设计师画的交互和开发的实现不一致→PM拉双方对齐
  - 需求的后置条件开发没实现→PM要求开发补充
  - 测试发现的问题需要回流→PM判断回流到哪个阶段

当前AI PM：
  - 每个阶段独立执行，不协调跨阶段一致性
  - 后置条件没实现→没有人发现（因为PM不验证产物）
  - 测试问题→按硬编码路由表回流，不判断实际根因
```

**AI PM应该具备的能力**：**跨阶段一致性校验**——需求定义的后置条件是否在开发中实现？设计定义的交互跳转是否在代码中工作？架构定义的路由是否与设计页面一一对应？

### 2.3 Demo验证（当前POM完全没有）

```
用户描述的Demo：
  "迭代完成了，大家一起Demo运行跑一遍流程"
  → 这是最有效的验证方式——不是检查文档，而是实际跑流程

当前POM：
  没有Demo环节。开发完成后直接进测试，测试只跑自动化测试+标注手动验证。
  没有人"跑一遍流程"。
```

**AI PM应该具备的能力**：每个迭代完成后，AI PM自动执行**流程跑通验证**——从用户打开系统→导航到目标页面→执行操作→验证结果，完整跑一遍核心流程。这不是测试用例执行，而是**端到端流程验证**。

## 三、产品专家：需求分析不是"写文档"而是"找场景定边界"

### 核心观点

用户描述的需求分析过程是**探索性+迭代性**的——"和客户聊找场景""反复确认边界"。当前BA Agent做的是**执行性**的——按§0.5六维分析一次性产出17章文档。

### 3.1 AI应该帮需求分析做什么

| 真实BA做的事 | AI能帮的 | AI不能替的 |
|-------------|---------|-----------|
| 和客户聊找场景 | AI根据需求描述+领域知识**自动识别场景模式**（如"直播+音频审核"→识别为B2B2C模式+内容审核场景） | 和客户对话确认场景理解是否准确 |
| 按互联网模式拆分系统 | AI根据场景模式**自动建议业务系统拆分**（如B2C→前台+后台+中台） | 确认拆分是否符合客户实际组织架构 |
| 端到端闭环验证 | AI**自动验证端到端流程闭环**——检查每个系统的输入输出是否对接、每个角色的操作是否有始有终 | — |
| 反复确认边界 | AI**自动识别边界模糊点**——标注"这里A系统和B系统的边界不清楚，需要确认" | 和客户确认边界归属 |
| 用例贯穿 | AI**自动检查用例贯穿性**——每个用例是否有系统/页面/角色/前置/后置，用例之间是否能串成流程 | — |
| **最怕流程跑不通** | AI**自动跑流程验证**——把所有用例串成端到端流程，检查是否存在断点 | — |

### 3.2 关键AI能力：流程闭环验证

用户说"最怕单个功能可以但流程跑不通"——这正是AI最该做的事：

```
AI流程闭环验证：
  1. 从用例中提取所有操作节点（角色A在系统B页面C做操作D）
  2. 按业务流程图串联操作节点
  3. 检查每个节点的：
     - 前置条件是否被上游节点的后置条件满足
     - 输出是否被下游节点的输入接收
     - 状态变化是否与状态机一致
  4. 标注流程断点："运营新增违禁词→词库下发推流端→推流端检测违禁词→静音处理→审核记录→看板展示"
     如果其中"词库下发推流端"没有对应的用例→流程断点
```

**这是AI比人更擅长的事**——人很难手动检查50个用例的贯穿性，但AI可以自动检查。

## 四、需求分析专家：用例不是"零散列表"而是"贯穿的流程"

### 核心观点

用户说"用例是零散了，用例的通过所属系统、页面、参与角色、前置条件和后置条件进行贯穿"——这说明用例的本质不是单个功能描述，而是**流程中的节点**。

### 4.1 当前POM的用例问题

当前POM的FN/UC是按"功能"组织的——FN-AUDIO-PC-001新增违禁词、FN-AUDIO-OBS-002违禁词检测...每个FN独立描述，用"关联FN"字段松散关联。

**问题**：用例之间没有强制的流程贯穿——没有检查"FN-001的后置条件是否被FN-002的前置条件接收"。

### 4.2 AI应该做的用例贯穿验证

```
AI用例贯穿验证：
  输入：所有FN/UC + 业务流程图 + 状态机
  
  AI自动构建用例流程图：
    FN-PC-001(新增违禁词) 
      →后置：词库新增+版本更新
      →FN-OBS-002(违禁词检测)的前置：词库已加载
      →✅ 贯穿
    
    FN-OBS-002(违禁词检测) 
      →后置：滴声替换+审核记录入库
      →FN-CTRL-001(接收告警)的前置：云端检测到违禁
      →⚠️ 断点！FN-OBS-002的后置是"推流端检测+静音"，但FN-CTRL-001的前置是"云端检测"
         →推流端检测和云端检测是两个不同的事件源，需要明确"推流端漏检→云端兜底检测→告警"的衔接
  
  AI输出：流程贯穿报告（哪些用例串联完整，哪些有断点）
```

### 4.3 AI辅助需求分析的核心能力清单

| 能力 | 描述 | 当前POM是否具备 |
|------|------|----------------|
| 场景模式识别 | 根据需求描述识别B2B/B2C/F2B2C等模式 | ❌ |
| 业务系统拆分建议 | 根据场景模式建议系统拆分 | ❌ |
| 端到端闭环验证 | 检查流程是否端到端闭环 | ❌ |
| 边界模糊点识别 | 标注系统间/角色间边界不清的地方 | ❌ |
| 用例贯穿验证 | 检查用例间前置后置是否对接 | ❌ |
| 流程断点检测 | 串联用例检查是否存在断点 | ❌ |
| 互联网模式知识库 | B2B/B2C/F2B2C/C2C/O2O的标准模式参考 | ❌ |

**当前POM的BA只会按六维分析+17章模板产出文档，不会做上述任何一项"分析思考"工作。**

## 五、UI设计专家+交互设计专家：设计不是"画草图"而是"反复磨合"

### 核心观点

用户描述的设计过程是"反复磨合整个交互，有可能推翻需求分析的产物"——这说明设计是**迭代式+反馈式**的，不是一次性产出。

### 5.1 AI应该帮设计做什么

| 真实设计师做的事 | AI能帮的 | AI不能替的 |
|----------------|---------|-----------|
| 确定信息布局/间距/ICON/按钮 | AI根据系统类型(B端/C端)+终端自动**建议布局规范**（B端PC=24列高密度=Ant Design ProLayout） | 确认布局是否符合品牌调性 |
| 视觉设计 | AI根据Design Tokens**自动生成CSS**（Token→CSS变量→组件样式） | 视觉细节调优 |
| 反复磨合交互 | AI**自动验证交互一致性**——检查所有按钮四态/所有弹窗关闭行为/所有表单校验是否统一 | 判断交互是否"好用" |
| 推翻需求产物 | AI**自动检查设计是否能覆盖需求**——设计页面是否覆盖所有FN/设计交互是否覆盖所有UC | 判断是否需要推翻需求 |

### 5.2 设计阶段缺失的关键环节：栅格系统落地

用户反馈"后台UI很丑，菜单占据空间太大"——根因是设计声明了栅格但没有落地。

**AI应该做的栅格落地**：

```
AI栅格落地验证：
  输入：设计草图 + 栅格系统声明(PC=24列)
  
  AI自动检查：
    1. 草图中每个区域是否标注了grid columns占比
    2. 占比总和是否=24（或合理留白）
    3. FD代码中是否用了Row/Col实现栅格
    4. 代码中Col span值是否与草图标注一致
  
  AI输出：
    ✅ B01工具栏区=24列（全宽）
    ✅ B02表格区=18列（75%）
    ✅ B03侧边区=6列（25%）
    ❌ 草图未标注grid columns占比 → 要求UX补充
    ❌ FD代码中未使用Row/Col → 要求FD重构布局
```

### 5.3 交互设计专家补充：跨终端导航设计

用户反馈"不同终端是独立URL没有统一入口"——这是交互设计阶段的缺失。

**AI应该做的跨终端导航验证**：

```
AI跨终端导航验证：
  输入：终端冻结 + 页面树 + 交互跳转矩阵
  
  AI自动检查：
    1. 同一SPA内的页面是否有统一的导航菜单
    2. 跨终端是否有导航入口（PC后台→中控室的入口在哪里？）
    3. 菜单点击是否能跳转到对应路由
    4. 菜单激活状态是否与当前路由同步
  
  AI输出：
    ❌ PC后台3个页面(/audio/wordlib, /audio/dashboard, /audio/config)没有共享Layout → 无法统一菜单
    ❌ PC后台与中控室(/ctrl/alerts)之间没有导航入口 → 用户无法跨系统跳转
    → 要求UX补充全局导航设计 + 要求Arch补充Layout路由
```

## 六、专业架构专家+技术经理：架构不是"画图"而是"定标准"

### 核心观点

用户描述"架构结合服务器资源/公共性/一致性/并发"→"技术经理基于架构输出开发标准"→"开发根据拆解任务开发"——这是**标准驱动开发**的流程。

### 6.1 当前POM架构的问题

当前POM的Arch产出了路由映射+Zod契约+五维可插拔+三段回溯——这些是"架构设计文档"但不是"开发标准"。

**缺失的开发标准**：

| 标准 | 描述 | 当前POM是否有 |
|------|------|--------------|
| **Layout标准** | PC后台用ProLayout / APP用底部Tab / 共享Layout的规则 | ❌ Arch只画了路由没定Layout标准 |
| **组件标准** | 表格用Ant Design Table / 表单用Ant Design Form / 弹窗用Modal | ❌ FD自己决定用什么组件 |
| **状态管理标准** | Store四态(loading/error/empty/success)的统一实现方式 | ❌ IRON-09要求四态但没给标准实现 |
| **数据流标准** | UI→Store→Service→Adapter的调用规范+异步初始化时序 | ❌ factory.ts有时序bug但没人发现 |
| **栅格落地标准** | Row/Col怎么用 / span怎么分配 / gutter怎么设 | ❌ 声明了24列但没说怎么分配 |

### 6.2 AI应该帮架构做什么

```
AI架构标准生成：
  输入：需求(系统/终端) + 设计(栅格/组件) + 技术栈
  
  AI自动生成开发标准：
    1. Layout标准：
       - PC后台：Ant Design ProLayout，侧边栏180px可折叠，面包屑
       - APP：底部Tab导航，全屏沉浸式直播间
       - CTRL：独立路由，右侧栏常驻告警面板
    
    2. 路由标准：
       - PC后台：嵌套路由 <Route path="/audio" element={<PcLayout/>}>
       - 跨终端：PC后台菜单含"中控室"入口
    
    3. 组件标准：
       - 表格：Ant Design Table，行高48px，分页10条/页
       - 表单：Ant Design Form + Modal 480px
       - 状态：loading=骨架屏 / empty=Empty组件 / error=Result组件
    
    4. 数据流标准：
       - 初始化：App.tsx中initAdapters()完成后再渲染
       - Store：create<T>()返回{data, loading, error, action}
       - 后置条件：每个action成功后触发后置效果
```

### 6.3 技术经理视角：开发标准必须可执行

```
当前POM的"开发标准"：
  IRON-01~11写在yml文件中 → FD读yml → FD按理解执行 → 结果不可预测

真实技术经理的"开发标准"：
  1. 写成代码模板（不是yml规则）→ FD直接用模板
  2. 写成ESLint规则 → 代码不符合标准时自动报错
  3. 写成CI管道 → 提交时自动验证
  4. 写成Code Review Checklist → review时逐条检查

AI应该做的：
  1. 把yml规则转成可执行的ESLint规则/代码模板/CI脚本
  2. 自动生成符合标准的脚手架代码（Layout/Store/Service/Adapter模板）
  3. 自动检查代码是否符合标准（不只是正则匹配，还有类型检查+运行时验证）
```

## 七、全栈开发工程师：开发不是"生成代码"而是"实现行为"

### 核心观点

用户描述"开发根据拆解任务进行单个任务开发"——开发做的是**实现行为**不是**生成代码结构**。

### 7.1 当前POM开发的问题

当前POM的FD生成了：契约✓ + 适配器✓ + Service✓ + Store✓ + 页面✓ + vite build通过✓

但生成的代码：
- 菜单用window.location.hash → 行为错误
- 数据保存调用链有bug → 行为错误
- 后置条件没实现 → 行为缺失
- 栅格没用Row/Col → 行为缺失

**根因**：FD只做了"生成结构正确的代码"没做"验证行为正确的代码"。

### 7.2 AI应该帮开发做什么

```
AI辅助开发的核心能力：

1. 代码生成后自动验证（不是只生成不验证）
   - vite build → 编译验证
   - vitest run → 单元验证
   - dev server启动 → 运行时验证
   - 浏览器打开核心页面 → 交互验证
   - 菜单点击跳转 → 导航验证
   - 表单提交保存 → 数据验证
   - 后置条件检查 → 业务验证

2. 后置条件自动实现
   - FN-PC-001后置"词库新增+版本更新" → AI在createWord成功后自动追加version+1逻辑
   - FN-OBS-002后置"审核记录入库" → AI在mute事件后自动追加auditEvent写入
   - FN-CTRL-002后置"告警状态更新+审核记录" → AI在handleAlert后自动追加状态更新+记录写入

3. 代码自检（不只是结构自检还有行为自检）
   - "我生成的菜单点击能跳转吗？" → AI自动在浏览器中点击验证
   - "我生成的表单提交能保存吗？" → AI自动提交表单检查IndexedDB
   - "我生成的后置条件实现了吗？" → AI自动检查后置条件是否生效
```

## 八、测试专家+可用性测试专家：测试不是"标注通过"而是"证明可用"

### 核心观点

用户描述"Demo跑流程""集成测试""可用性/流程性/易用性验收"——测试的本质是**证明产物可用**不是**标注用例通过**。

### 8.1 AI应该帮测试做什么

| 真实测试做的事 | AI能帮的 | 当前POM是否具备 |
|---------------|---------|----------------|
| 自动化浏览器测试 | AI用Playwright自动执行浏览器操作（打开→点击→输入→验证） | ❌ 只标注"手动验证✅" |
| 集成测试（流程跑通） | AI自动串联用例跑端到端流程 | ❌ 只跑单个单元测试 |
| 可用性测试 | AI模拟用户操作验证核心任务完成率 | ❌ 完全没有 |
| 回归测试 | AI每次修复后自动回归受影响模块 | ❌ 完全没有 |
| 测试证据生成 | AI自动截图/录屏/日志作为通过证据 | ❌ 只有一句话标注 |

### 8.2 可用性测试专家补充

```
可用性测试的核心不是"功能能不能用"而是"用户能不能用"：
  - 功能测试：菜单点击能跳转吗？ → 能/不能
  - 可用性测试：用户能在3秒内找到目标菜单吗？菜单名称是否清晰？ → 好用/不好用

当前POM完全缺少可用性维度：
  - 后台菜单200px太宽 → 可用性问题（占据太多内容空间）
  - 没有面包屑导航 → 可用性问题（用户不知道自己在哪）
  - 页面间没有导航入口 → 可用性问题（用户无法跨系统跳转）

AI可用性测试应该做的：
  1. 布局可用性检查：菜单宽度/间距/字号是否符合标准
  2. 导航可用性检查：用户能否在3步内到达任何页面
  3. 任务完成率：模拟用户完成核心任务的成功率
  4. 视觉层次检查：信息是否有层次（标题/正文/辅助）
```

## 十、总结：11位专家的共识

### 10.1 根本问题

**当前POM是用"管理文档的方式"管理"工程开发"——文档上什么都有，运行时什么都没有。**

### 10.2 根本方向

**从"硬编码规则执行"转向"AI思考+验证+学习"：**

| 维度 | 从 | 到 |
|------|-----|-----|
| AI角色 | 规则执行器 | 思考伙伴 |
| 规则 | 人工硬编码 | AI学习后自主优化 |
| 验证 | 静态检查文件 | 运行时验证产物 |
| 用例 | 零散功能列表 | 贯穿的流程闭环 |
| 设计 | 一次性产出草图 | 反复磨合+栅格落地 |
| 开发 | 生成代码结构 | 实现行为+运行时自测 |
| 测试 | 标注通过✅ | 证明可用（证据+自动化） |
| 流程 | 10阶段固定走 | AI根据项目特点动态调整 |
| 学习 | 不学习 | 从项目日志中学习进化 |

### 10.3 行动路径

| 阶段 | 内容 | 时间 |
|------|------|------|
| **立即** | 修复当前SAAS项目代码（菜单/数据/Layout/栅格/UI）→ 在浏览器中验证 | 1天 |
| **短期** | 增加"运行时验证"能力——开发自测清单+浏览器测试自动化+PM运行时验证 | 1周 |
| **中期** | 增加"AI思考"能力——流程闭环验证+用例贯穿检查+栅格落地验证+后置条件自动实现 | 2-4周 |
| **长期** | 增加"AI学习进化"能力——过程日志结构化+AI学习分析+自主优化输出 | 1-3个月 |

### 10.4 核心原则

**POM不应该是"规则越多越好"而应该是"验证越真实越好"。**

一行运行时验证 > 一百条纸面规则。

**AI不应该替代人思考，而应该帮人做重复的思考/验证/学习，让人专注在创造性的决策上。**
