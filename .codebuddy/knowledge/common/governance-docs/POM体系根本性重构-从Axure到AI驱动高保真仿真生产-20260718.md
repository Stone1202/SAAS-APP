# POM体系根本性重构：从Axure人工模式到AI驱动的高保真仿真生产体系

> **讨论时间**：2026-07-18
> **核心命题**：用AI替代Axure人工方式，解决效率（人耗时）和质量（人思考不足）问题，产出可投入生产的高保真仿真系统
> **前提**：忽略SAAS项目，专注体系层面深入讨论
> **参与专家**：11位专家联合

---

## 序言：问题的本质

### 用户的核心诉求

```
过去：Axure + 人工
  - 人耗时（效率问题）
  - 人的思考会有不足（质量问题）
  - 产出的是静态原型（不能投入生产）

目标：AI驱动 + 高保真仿真
  - AI替代重复思考（效率提升）
  - AI补充人的思考不足（质量提升）
  - 产出可投入生产的高保真仿真系统（不只是原型）
```

### 当前POM的根本矛盾

```
当前POM试图用AI替代人，但做法是：
  把人的工作流程硬编码为yml规则 → AI按规则执行 → 产出文档/代码
  
问题：
  1. 人的思考过程无法硬编码——"和客户聊找场景""反复磨合交互"这些是创造性思考不是规则执行
  2. 硬编码的规则变成了纸面合规——文档上什么都有运行时什么都没有
  3. AI只执行不验证不学习——每次从零开始同一套规则，不因经验而进化

本质矛盾：
  POM试图用"固化规则"模拟"人的思考"——但人的思考不是规则执行而是探索+验证+迭代+学习
```

## 一、重新定义：AI在流程中应该扮演什么角色

### 1.1 从"规则执行器"到"能力增强器"

| 维度 | Axure人工模式 | 当前POM AI模式 | 目标AI模式 |
|------|-------------|---------------|-----------|
| 需求 | 人和客户聊→人找场景→人写PRD | AI按六维分析产出17章文档 | **AI辅助人找场景+AI自动验证流程闭环+人做关键决策** |
| 设计 | 人画Axure原型→人反复调整 | AI按模板产出8章设计文档 | **AI根据需求自动生成可交互原型+人调优关键交互** |
| 开发 | 人手写代码 | AI按模板生成代码结构 | **AI生成可运行代码+AI自动验证行为正确+人处理复杂边界** |
| 测试 | 人手动测试 | AI标注"手动验证✅" | **AI自动执行浏览器测试+AI生成测试证据+人判断风险** |
| 验证 | 人Demo跑流程 | AI检查文档完整 | **AI自动跑端到端流程+AI可用性检查+人确认体验** |

### 1.2 AI的三个层次能力

```
第一层：执行能力（当前POM已具备但不完善）
  - 按规则产出文档/代码
  - 按模板生成结构
  - 按检查清单验证

第二层：思考能力（当前POM完全缺失）
  - 理解业务意图（不只是执行规则而是理解为什么这么做）
  - 分析流程闭环（不只是产出用例而是验证用例能否串成流程）
  - 验证行为正确（不只是检查代码结构而是验证运行时行为）
  - 识别风险点（不只是检查完整性而是预判哪里可能出问题）

第三层：进化能力（当前POM完全缺失）
  - 从项目过程中学习（哪些规则无效、哪些检查遗漏）
  - 自主优化规则/技能/知识库（不需要人手动改yml）
  - 跨项目经验复用（A项目的教训自动应用到B项目）
```

### 1.3 核心原则

**AI不替代人做决策，AI增强人做重复思考/验证/学习。**

- 人决策：场景确认、边界划分、视觉调性、技术选型、风险判断
- AI增强：流程闭环验证、用例贯穿检查、栅格落地验证、行为正确性验证、测试自动化、经验学习

## 二、流程重构：从"固定10阶段"到"敏捷迭代+AI验证"

### 2.1 用户描述的真实流程 vs 重构后的AI流程

```
用户描述的真实流程：
  1.需求分析(找场景/流程/角色/系统/端) → 2.设计(布局/视觉/交互磨合) 
  → 3.架构(系统/端/服务器/并发) → 4.技术标准 → 5.开发(单任务) 
  → 6.Demo(跑流程) → 7.测试(集成) → 8.验收(可用性) → 9.发布

重构后的AI流程：
  Sprint 0: 需求探索（AI辅助+人决策）
    → AI分析需求描述→识别互联网模式(B2B/B2C/F2B2C)→建议系统拆分→建议终端
    → AI自动验证端到端流程闭环→标注边界模糊点
    → 人确认场景/边界/系统/端
    
  Sprint 1: 设计+架构+开发（AI生成+人调优）
    → AI根据需求自动生成：交互原型(可点击)+栅格布局+Design Tokens+路由架构+代码骨架
    → AI自动验证：设计覆盖需求?路由与设计一致?栅格已落地?
    → 人调优：视觉细节/交互体验/技术选型
    
  Sprint 2: 验证（AI自动+人确认）
    → AI自动执行：浏览器测试(菜单跳转/数据CRUD/流程跑通)+可用性检查
    → AI生成证据：截图/录屏/执行日志
    → 人确认：体验是否OK/流程是否跑通/是否可以发布
    
  循环往复直到版本完成
```

### 2.2 关键改变：Demo环节的AI化

用户说"迭代完成了大家一起Demo运行跑一遍流程"——这是最有效的验证方式。AI应该自动化这个环节：

```
AI Demo验证（替代人工Demo）：
  1. AI自动打开dev server
  2. AI自动执行核心流程（模拟用户操作）：
     - 运营人员：登录→词库管理→新增违禁词→验证保存→查看看板
     - 主播：推流→ASR检测→违禁词→滴声屏蔽
     - 观众：打开APP→进入直播间→听到滴声
     - 中控室：收到告警→处置→验证状态更新
  3. AI验证每步的结果（不只是"能点击"而是"结果正确"）
  4. AI生成Demo报告（截图+流程图+通过/失败+问题清单）
  5. 人看Demo报告确认是否可以进入下一迭代
```

### 2.3 流程分层（用户提到的敏捷理念）

```
AI根据项目规模自动选择流程级别：

轻量级（1-3页面/Bug修复）：
  需求确认 → AI生成代码 → AI验证 → 人确认
  （3步，1天内完成）

标准级（4-15页面/存量迭代）：
  需求探索 → AI生成设计+代码 → AI Demo验证 → 人确认 → AI测试
  （5步，1周内完成）

完整级（15+页面/新项目）：
  需求探索 → 设计磨合 → 架构标准 → 开发 → Demo验证 → 测试 → 验收
  （7步，2-4周完成）
```

## 三、需求分析重构：从"写17章文档"到"找场景定边界验闭环"

### 3.1 当前问题

当前BA按§0.5六维分析→产出17章文档——这是"写文档"不是"做分析"。真正的需求分析是用户描述的：

> "和客户聊找场景，流程，参与人，角色，依据B2B/B2C/F2B2C/C2C/O2O等互联网模式拆分业务系统，呈现端；然后将场景、流程、参与人、角色进行端到端、系统到系统的闭环，这个就是不断地去找边界，反复确认后"

### 3.2 AI应该怎么辅助需求分析

```
AI需求分析辅助流程：

Step 1: 场景识别（AI辅助）
  输入：用户需求描述
  AI分析：
    - 识别互联网模式（B2B/B2C/F2B2C/C2C/O2O）
    - 识别业务场景（直播审核/电商订单/社群运营...）
    - 识别参与角色（运营/商家/消费者/主播/观众...）
    - 识别核心流程（推流→审核→静音→告警→处置）
  AI输出：场景模式建议+角色清单+流程草图
  人确认：场景理解是否准确

Step 2: 系统拆分（AI辅助）
  输入：场景模式+角色清单
  AI分析：
    - 根据互联网模式建议业务系统拆分
      B2C → 前台(消费者) + 后台(运营) + 中台(服务)
      B2B2C → 平台 + 商家 + 消费者
    - 根据角色建议终端
      运营 → PC后台
      消费者 → APP/小程序
      主播 → OBS/移动端
  AI输出：系统拆分建议+终端映射
  人确认：拆分是否符合实际组织架构

Step 3: 闭环验证（AI自动）
  输入：系统拆分+流程草图+角色清单
  AI自动验证：
    - 端到端闭环：每个角色的操作是否有始有终
    - 系统间衔接：A系统的输出是否被B系统接收
    - 边界清晰度：标注边界模糊点
  AI输出：闭环验证报告+边界模糊点清单
  人确认：边界归属

Step 4: 用例贯穿（AI自动）
  输入：所有FN/UC + 流程图 + 状态机
  AI自动验证：
    - 用例串联：所有用例能否串成完整流程
    - 前后置对接：FN-A的后置是否被FN-B的前置接收
    - 流程断点：串联用例检查断点
  AI输出：用例贯穿报告+流程断点清单
  人确认：断点如何修补
```

### 3.3 核心AI能力清单

| 能力 | 描述 | 解决什么问题 |
|------|------|-------------|
| 互联网模式识别 | B2B/B2C/F2B2C/C2C/O2O模式自动识别 | 人可能不熟悉所有模式 |
| 场景模式库 | 各行业的标准场景参考 | 人可能不知道行业标准做法 |
| 端到端闭环验证 | 自动检查流程是否端到端闭环 | "最怕单个功能可以但流程跑不通" |
| 用例贯穿验证 | 自动检查用例前后置是否对接 | 零散用例无法串联的问题 |
| 边界模糊点识别 | 自动标注系统间/角色间边界不清 | 反复确认边界的效率问题 |

## 四、设计重构：从"画8章文档"到"生成可交互原型+验证落地"

### 4.1 当前问题

当前UX按8章模板产出设计文档+ASCII草图——这是"画文档"不是"做设计"。真正的设计是用户描述的：

> "拿到PRD，上面有流程、有草图、有说明；然后根据业务系统、根据端，先确定整个信息布局间距ICON按钮等，然后视觉设计，反复磨合整个交互"

### 4.2 AI应该怎么辅助设计

```
AI设计辅助流程：

Step 1: 信息布局生成（AI自动）
  输入：需求(系统/终端/页面) + 互联网模式
  AI生成：
    - 根据系统类型自动选择布局框架
      B端PC → Ant Design ProLayout（侧边栏180px可折叠+面包屑）
      C端APP → 底部Tab导航+全屏沉浸
    - 根据页面内容自动分配栅格
      表格页 → 工具栏(24列全宽) + 表格(18列) + 侧边(6列)
      看板页 → 指标卡片(4×6列) + 图表(24列全宽)
    - 自动生成Design Tokens（色彩/字体/间距/圆角/阴影/图标）
  AI输出：布局框架+栅格分配+Design Tokens
  人调优：视觉调性/品牌一致性

Step 2: 可交互原型生成（AI自动）
  输入：布局+需求FN/UC+交互跳转矩阵
  AI生成：
    - 可点击的交互原型（不是ASCII草图而是真实的HTML组件）
    - 菜单可点击跳转
    - 表单可填写提交
    - 弹窗可弹出关闭
    - 数据可展示（Mock数据）
  AI输出：可交互原型（dev server可访问）
  人调优：交互体验/细节打磨

Step 3: 设计验证（AI自动）
  输入：可交互原型+需求FN/UC
  AI自动验证：
    - 设计覆盖：每个FN是否有对应页面/每个UC是否有对应交互
    - 栅格落地：代码中是否用了Row/Col+span值是否与设计一致
    - 交互完整：菜单能否跳转/表单能否提交/弹窗能否弹出
    - 一致性：按钮四态/弹窗关闭/表单校验是否统一
  AI输出：设计验证报告+问题清单
  人确认：问题修复方向
```

### 4.3 核心改变：从"草图"到"可交互原型"

```
过去Axure：人画静态原型 → 人手动添加交互 → 人手动调整
当前POM：AI画ASCII草图 → FD按草图写代码 → 代码和草图不一致
目标AI：AI直接生成可交互原型(HTML组件) → 人调优 → 原型即代码

关键区别：
  Axure草图和最终代码是两套东西（草图→开发重新写代码）
  AI可交互原型和最终代码是同一套东西（原型就是代码的初始版本，人调优后直接成为最终产物）
```

## 五、开发重构：从"生成代码结构"到"实现行为+运行时自测"

### 5.1 当前问题

当前FD生成代码结构（契约/适配器/Service/Store/页面）但行为不正确（菜单不跳转/数据保存不了/后置条件没实现）。

### 5.2 AI应该怎么辅助开发

```
AI开发辅助流程：

Step 1: 代码生成（AI自动）
  输入：可交互原型(设计阶段产出) + 架构标准 + 需求FN/UC
  AI生成：
    - 基于原型代码继续增强（原型已有布局/组件/交互，开发补充数据/逻辑/后置条件）
    - 自动实现后置条件（每个FN的后置条件自动翻译为代码）
    - 自动实现状态管理（Store四态+异步处理+错误处理）
  AI输出：可运行代码

Step 2: 运行时自测（AI自动）—— 这是最关键的改进
  AI自动执行：
    1. vite build → 编译验证
    2. vitest run → 单元测试
    3. dev server启动 → 运行时验证
    4. 浏览器打开核心页面 → 交互验证
    5. 菜单点击跳转 → 导航验证
    6. 表单提交保存 → 数据验证（检查IndexedDB）
    7. 后置条件检查 → 业务验证（版本号+1?记录入库?）
    8. 流程跑通 → 端到端验证
  AI输出：自测报告（每项通过/失败+截图证据）
  
  如果自测不通过 → AI自动修复 → 重新自测 → 直到通过

Step 3: 交付验证（AI自动+人确认）
  AI生成Demo报告：
    - 核心流程截图（运营操作/主播推流/观众观看/中控处置）
    - 流程跑通证明（端到端操作录屏/日志）
    - 问题清单（如果有）
  人确认：是否可以进入测试
```

### 5.3 核心改变：后置条件自动实现

```
当前POM：
  FD生成createWord() → 只调用adapter.create() → 完了
  后置条件"版本号+1+下发推流端"→ 没人实现

目标AI：
  FD生成createWord() → AI读取后置条件 → 自动追加：
    await adapter.create('wordlib', data)           // 基础CRUD
    await adapter.update('configs', 'version', +1)  // 后置：版本号+1
    await transport.publish('wordlib_update', {})   // 后置：模拟下发
    await adapter.create('audit_records', {...})    // 后置：审核记录入库
```

```
AI测试辅助流程：

  AI输出：可用性报告
  人确认：体验是否OK
```

## 七、架构+技术标准重构

### 7.1 AI应该怎么辅助架构

```
AI架构辅助流程：

Step 1: 架构生成（AI自动）
  输入：需求(系统/终端) + 设计(布局/栅格) + 技术栈基线
  AI自动生成：
    - Layout标准（PC用ProLayout/APP用Tab导航/共享Layout规则）
    - 路由标准（嵌套路由/跨终端导航）
    - 组件标准（表格/表单/弹窗用什么组件+什么尺寸）
    - 数据流标准（UI→Store→Service→Adapter+异步初始化时序）
    - 栅格落地标准（Row/Col怎么用+span怎么分配）
  
Step 2: 开发标准输出（AI自动）
  AI不只是产出文档，而是产出可执行的标准：
    - 代码模板（Layout模板/Store模板/Service模板）
    - ESLint规则（禁止硬编码颜色/禁止window.location.hash）
    - CI脚本（build→test→dev启动→浏览器验证）
  
Step 3: 架构验证（AI自动）
  AI自动验证：
    - 路由层级化（PC后台是否共享Layout）
    - 多终端聚合（哪些终端同SPA/哪些独立）
    - 适配器初始化时序（是否有null检查）
```
