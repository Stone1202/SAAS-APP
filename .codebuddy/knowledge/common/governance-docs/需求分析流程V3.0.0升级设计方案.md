### 2.2 interactive_flow 定位（V3.0.0 重新定义）

**原则**：保留参数说明展示 + 必填项缺失指引，取消"新项目/存量项目"交互式问答。

```yaml
interactive_flow:
  description: |
    V3.0.0 重新定义：参数输入后自动展示参数说明；
    必填项缺失时给予指引说明；
    不再交互式询问"新项目/存量项目"——改为自动检测。
  flow:
    - step: "param_display"
      trigger: "用户输入 /init 命令后"
      action: "自动展示 /init 全部参数说明（必填+可选），含参数名、类型、示例值、可选值"
    - step: "missing_guide"
      trigger: "必填参数缺失"
      action: "对缺失的必填参数展示引导提示（参数名+说明+示例值+可选值+默认值建议）"
    - step: "auto_detect"
      trigger: "参数齐全"
      action: |
        自动检测项目性质（新/存量），无需用户回答：
        - 扫描 projects/{--project}/ 是否存在 → 存在=存量，不存在=新项目
        - 存量项目：自动加载骨架+知识库PRD+版本沉淀+领域知识+PO Backlog
        - 新项目：构建骨架
        - 检测结果作为「参数路由包」传递给 BA
```

### 3.3 §0.5 需求深度分析整合（BA 负责，核心新增）

#### §0.5a 需求描述AI深度分析

BA 对全部输入源（--desc/--file/--api/--source）进行6维深度分析：

**维度1：语义提取**
从 --desc/--file 中提取：核心业务概念、操作动词、角色主体、状态变化、约束条件

**维度2：意图识别**
识别表面意图 vs 深层意图。示例：--desc="会员积分兑换商品"
- 表面意图：积分扣减+商品发放
- 深层意图：积分体系+商品库存+兑换限流+防刷+退换货+积分过期

**维度3：业务概念抽取**
抽取实体概念（积分账户/兑换订单/商品库存）、流程概念（兑换/审核/退换）、规则概念（兑换限制/有效期/扣减规则）、角色概念

**维度4：隐含需求挖掘**
基于业务逻辑推导未提及但必须有的需求。示例：
- 有"积分兑换" → 隐含"积分账户管理""积分流水""积分有效期"
- 有"商品发放" → 隐含"库存扣减""库存预警""缺货处理"
- 有"兑换限流" → 隐含"频率控制""防刷机制""异常监控"
- 有"退换货" → 隐含"积分退回""库存回补""状态回滚"

**维度5：领域知识深度结合**
加载领域知识库，将需求与领域知识深度交叉匹配：

| 匹配维度 | 说明 | 示例 |
|---|---|---|
| 需求概念 × 领域知识业务流程 | 需求涉及的流程参考行业标准 | 需求"积分兑换" → 营销/积分兑换标准流程 |
| 需求概念 × Part12 API参数字典 | 需求涉及的接口参数对齐 | 需求"提现" → 易宝API-PAY-010入参(merchantNo/amount/bankAccountNo) |
| 需求概念 × Part13 参数流转图 | 需求接口链路的参数流转 | 需求"商户入网后提现" → 易宝Part13(merchantNo从入网通知→提现API) |
| 需求概念 × 领域知识业务规则BR | 需求涉及的规则参考标准 | 需求"退款" → 退款领域BR-PAY-001(商户入网须先开户绑卡) |
| 需求概念 × 领域知识状态机 | 需求涉及的状态参考标准 | 需求"商户管理" → 易宝商户入网状态机(INIT→PENDING→ACTIVE) |

**维度6：外部接口融合**
对 --api 提供的外部接口文档，与领域知识 Part12/Part13 对齐：
- 接口路径对齐：--api 接口 vs 领域知识 api_chain 接口
- 参数对齐：--api 参数 vs Part12 参数字典
- 参数流转对齐：--api 调用顺序 vs Part13 参数流转图
- 缺口识别：--api 有但领域知识没有的接口（需补充学习）
- 产出：接口参数×业务流程映射表

**产出：需求深度分析报告**（demand_analysis_report）
```yaml
demand_analysis_report:
  semantic_extraction: { concepts, operations, roles, states, constraints }
  intent_analysis: { surface_intent, deep_intent }
  business_concepts: { entities, processes, rules, roles }
  implicit_requirements: [{ requirement, derivation, priority }]
  domain_knowledge_fusion:
    matched_domains: ["marketing/points-exchange.yml"]

    param_flow_references:       # Part13 引用
      - { domain, flow, matched_concept }
    br_references: [...]
    state_machine_references: [...]
  external_api_fusion:
    api_alignment: [{ external_api, domain_api, alignment, gaps }]
```

#### §0.5b 项目影响广度深度分析

**条件**：存量项目（有已学PRD/topology/state.json）；新项目跳过

V3.0.0 从单维 topology 对比升级为 **8维影响扫描**：

| 维度 | 类型 | 说明 |
|---|---|---|
| 1. 模块拓扑影响 | 广度 | （V2.0.0保留）对比topology，受影响模块+级别 |
| 2. 数据实体影响 | 深度 | 扫描ENT，新增/修改/删除实体+字段级变更 |

#### §0.5c 融合分析（需求全景图）

将 §0.5a 需求深度分析 和 §0.5b 项目影响分析 进行融合，产出**需求全景图**——后续 §1旅行地图/§2场景挖掘/§3业务流程的输入基础。

**融合逻辑**：

1. **需求×影响交叉**：
   - 需求深度分析中每个概念 → 在项目影响中找到对应受影响产物
   - 隐含需求 → 检查项目存量是否已有实现（已有→标注复用，没有→标注新增）

2. **需求×领域知识×项目存量三方对齐**：
   - 领域知识标准流程 vs 项目存量实现 vs 新需求
   - 找出差异：领域标准有但项目没有的→建议补充；项目有但领域标准不同的→标注差异

3. **全景图结构**：

## 四、新增产物设计

### 4.1 CONFIG：集中配置清单

#### 4.1.1 什么是CONFIG

CONFIG 是需求中涉及的、需要统一管理的可配置项清单。当前 PRD 里这些配置散落在各个 FN/BR 中，没有集中管理。开发时 Arch 需要设计配置中心、FD 需要实现配置项，如果需求阶段没有集中识别，容易遗漏。

#### 4.1.2 CONFIG类型

| 类型 | 编号前缀 | 说明 | 示例 |
|---|---|---|---|
| 全局参数 | CONFIG-{系统}-{NNN} | 运营可调的业务参数 | 最低提现金额=100元、最大退款天数=30天、默认费率=0.6% |
| 全局开关 | CONFIG-{系统}-{NNN} | 开/关控制业务行为 | 是否开启自动提现、是否允许跨商户转账、是否开启风控 |
| 控制器 | CONFIG-{系统}-{NNN} | 频率/金额/数量控制 | 每日转账限额=50万、每分钟API调用=100次、单商户最多绑卡=5张 |
| 规则引擎 | CONFIG-{系统}-{NNN} | 规则引擎驱动的动态规则 | 风控规则：单笔>5万触发人工审核；分账规则：按比例分给平台和供应商 |
| 枚举字典 | CONFIG-{系统}-{NNN} | 枚举值统一定义 | 商户类型：企业/个体/小微；支付渠道：微信/支付宝/银联 |

#### 4.1.3 CONFIG产物结构

```yaml
# 编号：CONFIG-{系统缩写}-{NNN}（与FN/BR同系统缩写体系）
configs:
  - id: "CONFIG-PAY-001"
    name: "最低提现金额"
    type: "global_param"          # global_param/switch/controller/rule_engine/enum_dict
    default: 100
    unit: "元"
    scope: "global"               # global/module/tenant
    description: "商户提现的最低金额限制"
    affects:                      # 影响的FN/API
      - "FN-PAY-PC-005(提现下单)"
      - "API-PAY-010(提现下单)"
    business_rule: "BR-PAY-005"   # 关联的业务规则
```

### 4.2 METRIC：统计指标清单

#### 4.2.1 什么是METRIC

METRIC 是需求中涉及的统计指标清单，每个指标定义计算公式、数据来源、维度、粒度。BA 分析需求时，从 common/metrics-standards.yml 匹配行业标准指标定义，确保口径一致。

#### 4.2.2 METRIC产物结构

```yaml
# 编号：METRIC-{系统缩写}-{NNN}
metrics:
  - id: "METRIC-PAY-001"
    name: "商户日均交易额"
    industry_standard: "METRIC-TRADE-001(GMV)"   # 引用common/metrics-standards.yml
    type: "aggregate"               # count/sum/avg/aggregate/ratio
    entity: "交易订单"               # 统计实体
    formula: "SUM(交易金额) WHERE 状态=成功 GROUP BY 商户ID, 日期"
    dimensions: ["商户ID", "日期", "支付渠道"]  # 统计维度
    granularity: "daily"            # realtime/hourly/daily/weekly/monthly
    source_apis:                    # 数据来源API
      - "API-PAY-004(充值查询)"
      - "API-PAY-020(付款查询)"
    source_entities:                # 数据来源实体
      - "ENT-PAY-001(交易订单)"
    display_on:                     # 展示页面
      - "PG-DAS-PC-001(商户概览)"
      - "PG-DAS-PC-005(交易报表)"
    related_br: "BR-PAY-008"
    related_bg: "BG-ACRM-001"       # 关联业务目标
    alert_threshold: "日均<1000元触发预警"  # 预警阈值（如有）
    
  - id: "METRIC-PAY-002"
    name: "支付成功率"
    industry_standard: "METRIC-PAY-001(支付成功率)"
    type: "ratio"
    entity: "交易订单"
    formula: "成功支付笔数 / 发起支付笔数 × 100%"
    dimensions: ["商户ID", "日期", "支付渠道"]
    granularity: "realtime"
    source_apis: ["API-PAY-004(充值查询)", "API-AGG-001(聚合支付下单)"]
    display_on: ["PG-DAS-PC-001(商户概览)"]
    related_br: "BR-PAY-009"
    alert_threshold: "<95%触发预警"
```

## 五、common/metrics-standards.yml 设计

### 5.1 定位

行业统计指标通用规则库，类似 `doc-standards.yml` 的定位，供 BA 分析需求时引用标准指标定义，确保跨项目指标口径一致。

### 5.2 覆盖行业

| 行业 | 编号前缀 | 覆盖范围 |
|---|---|---|
| 电商 | METRIC-EC-NNN | GMV/客单价/转化率/复购率/退货率 |
| 财务 | METRIC-FN-NNN | 营收/成本/利润/应收账款/应付账款 |
| 物流 | METRIC-LG-NNN | 发货量/到货率/妥投率/物流时效 |
| 仓库 | METRIC-WH-NNN | 库存量/库存周转率/缺货率/入库量/出库量 |
| 直播 | METRIC-LV-NNN | 观看人数/互动率/带货GMV/转化率 |
| AARRR | METRIC-AR-NNN | 获取/激活/留存/变现/推荐五阶段指标 |
| 广告 | METRIC-AD-NNN | 曝光量/点击率/转化率/ROI/CPM/CPC |
| CRM | METRIC-CR-NNN | 客户数/活跃度/流失率/LTV/转化漏斗 |
| SaaS | METRIC-SA-NNN | MRR/ARR/Churn Rate/NPS/续费率/试用转化率 |
| 教育 | METRIC-ED-NNN | 完课率/到课率/退费率/续报率/NPS/学习时长 |
| 医疗 | METRIC-MD-NNN | 就诊量/复诊率/满意度/预约取消率/平均候诊时间 |

```yaml
ecommerce:

    name: "GMV（商品交易总额）"

    granularity: [实时, 日, 周, 月, 季, 年]

    granularity: [日, 周, 月]
    notes: "仅统计成功订单"

    name: "转化率"
    formula: "成功支付订单数 / 访问UV × 100%"
    dimensions: [时间, 页面, 渠道, 终端]
    granularity: [实时, 日, 周, 月]
    
  - id: "METRIC-EC-004"
    name: "复购率"
    formula: "周期内购买≥2次的用户数 / 周期内购买≥1次的用户数 × 100%"
    dimensions: [时间, 品类, 渠道]
    granularity: [月, 季, 年]
    
  - id: "METRIC-EC-005"
    name: "退货率"
    formula: "退货订单数 / 成功订单数 × 100%"

    granularity: [日, 周, 月]

    granularity: [日, 周, 月]
    
  - id: "METRIC-LG-002"
    name: "妥投率"

    dimensions: [时间, 物流商, 目的省]
    granularity: [日, 周, 月]
    
  - id: "METRIC-LG-003"
    name: "物流时效（小时）"
    formula: "AVG(签收时间 - 发货时间) WHERE 状态=已签收"
    dimensions: [时间, 物流商, 目的省, 仓库]
    granularity: [日, 周, 月]

# ========== 仓库指标 ==========
warehouse:
  - id: "METRIC-WH-001"

    dimensions: [时间, 仓库, 品类]
    granularity: [日, 周, 月]

# ========== 直播指标 ==========
live:
  - id: "METRIC-LV-001"
    name: "最高同时在线人数（PCU）"
```

### 11.1 CONFIG与BR边界规则（详细说明）

```
BR（业务规则）= 规则逻辑
  定义：业务规则的触发条件和行为逻辑
  示例：BR-PAY-005 "提现金额须≥最低提现金额限制，否则拒绝"
  关注：规则是否正确、是否完整、是否冲突

CONFIG（集中配置）= 可配置参数值
  定义：规则中涉及的、需要统一管理的、可动态调整的参数值
  示例：CONFIG-PAY-001 "最低提现金额，默认100元，运营管理员可配置，数值>0"
  关注：参数值是什么、谁可配、怎么校验、影响哪些FN/API/PG

判定规则：
  如果用例(FN/UC)中明确描述了一个可调整的参数值/开关/限制/规则 → CONFIG
  如果只是业务逻辑约束（不可配置的固定规则） → BR
  如果是可配置的规则（如风控规则引擎） → CONFIG(rule_engine) + BR（引用CONFIG）
```
