## 一、敏捷治理定位

### 1.1 核心定义

敏捷治理由**SM Agent（敏捷教练/Scrum Master）**负责，在POM V5.0三级把关机制中担任**Sprint级总体把关人**。

| 层级 | 把关人 | 职责 |
|------|--------|------|
| 项目级 | PO Agent | 做对的事（战略对齐） |
| 版本级 | PM Agent | 把事做对（交付闭环） |
| **Sprint级** | **SM Agent** | **做对每个增量（敏捷交付）** |

### 1.2 对齐Scrum 334框架

| Scrum要素 | POM V5.0对应 |
|-----------|-------------|
| **3角色** | |
| 产品负责人(PO) | PO Agent |
| 敏捷教练(SM) | **SM Agent（V5.0新增）** |
| 开发团队 | BA/UX/Arch/FD/QA Agent |
| **3工件** | |
| 产品待办列表 | PROD-BACKLOG.yml（PO管理） |
| Sprint待办列表 | SPRINT-BACKLOG.yml（SM+团队管理） |
| 产品增量 | 每Sprint交付1-3页面+运行时验证+Demo报告（必须可演示） |
| **4事件** | |
| Sprint计划会 | Sprint启动会（SM主持） |
| 每日立会 | AI每日立会（SM每阶段自动生成） |
| Sprint评审会 | Sprint Review（SM主持） |
| Sprint回顾会 | Sprint Retrospective（SM主持） |

### 1.3 敏捷核心原则

| 原则 | POM V5.0体现 |
|------|-------------|
| 拥抱变化≠随意变更 | 变更需人确认（human-confirm-protocol） |
| 轻文档≠零文档 | 三位一体交付物（PRD+仿真原型+用例卡片） |
| 增量必须可用 | Sprint DoD含运行时验证+可演示 |
| Sprint Backlog不可变 | 启动后不加项，变更走change-request |
| 团队无头衔之分 | BA/UX/FD/QA协作无层级，SM是facilitator |
| 自我迭代更新 | Sprint Retrospective实现自我迭代 |

## 二、SM Agent角色

### 2.1 角色定义

SM Agent是**敏捷教练（Scrum Master）**，是Sprint级的总体把关人。

**核心职责**：把控BA/UX/FD/QA在本次Sprint的交付是否符合敏捷交付条件，保障Scrum事件，移除障碍。

**不做的事**：不做需求分析(BA)/设计(UX)/开发(FD)/测试(QA)/项目战略(PO)/版本范围(PM)——只守护Sprint流程和团队。

### 2.2 SM Agent 5项核心职责

| 职责 | 描述 |
|------|------|
| sm1 Sprint守护人 | 把控BA/UX/FD/QA交付符合敏捷条件（DoD+可演示+依赖+验证+Review） |
| sm2 Scrum事件保障 | 保障4个Scrum事件执行（计划会/立会/评审会/回顾会） |
| sm3 障碍移除 | 识别+升级+处理障碍，1天未解升级PM |
| sm4 团队协作促进 | 促进BA/UX/FD/QA跨职能协作，冲突仲裁 |
| sm5 Sprint学习记录 | Retrospective报告+经验提炼+Velocity记录 |

### 2.3 SM与其他Agent协作边界

| 协作场景 | SM | 对方 |
|---------|-----|------|
| Sprint启动会 | 主持 | PO讲解Backlog，BA/UX/FD/QA认领 |
| 阶段Review | 旁观+障碍识别 | 各Agent专业审视 |
| 障碍升级 | 识别+升级 | PM决定调整 |
| Sprint评审会 | 主持 | PO审视，团队演示 |
| Sprint回顾会 | 主持 | 团队回顾 |
| /close | 不参与 | PM版本沉淀，PO验收 |

## 三、Sprint规划

### 3.1 Sprint拆解5种策略

| 策略 | 描述 | 适用场景 |
|------|------|---------|
| 按业务流程闭环拆 | 一个Sprint完成一个端到端闭环 | 业务流程清晰且闭环独立 |
| 按终端拆 | 一个Sprint完成一个终端核心功能 | 多终端项目，终端间独立 |
| 按模块拆 | 一个Sprint完成一个业务模块 | 模块间耦合低 |
| MVP优先拆 | S1做MVP，后续增量增强 | 新项目首版本，需快速验证 |
| 混合拆 | 组合以上策略 | 复杂项目 |

### 3.2 拆解约束

- 每Sprint页面数≤5（超过则拆分）
- 每Sprint必须包含至少1个场景闭环（SC）
- Sprint间依赖必须显式声明
- Sprint 1通常做MVP或核心闭环
- 跨Sprint共享组件放在依赖它的第一个Sprint

### 3.3 项目规模与Sprint数量

| 规模 | Sprint数 | 流程层级 |
|------|---------|---------|
| 小项目 | 1-2 | lite(3步) |
| 中项目 | 3-5 | standard(5步) |
| 大项目 | 6+ | full(7步) |

## 四、Sprint执行

### 4.1 Sprint执行流程

```
Sprint启动会（SM主持）
  ├─ PO讲解本Sprint的Backlog项
  ├─ BA/UX/FD/QA认领并拆解任务
  └─ 产出 SPRINT-BACKLOG.yml
       │
       ▼
阶段执行（SM旁观+障碍识别）
  ├─ BA需求分析 → SM旁观+障碍识别
  ├─ UX设计 → SM旁观+障碍识别
  ├─ Arch架构 → SM旁观+障碍识别
  ├─ FD开发 → SM旁观+障碍识别
  ├─ QA测试 → SM旁观+障碍识别
  └─ 每阶段SM自动生成AI每日立会报告
       │
       ▼
人确认（按human-confirm-protocol）
       │
       ▼
Sprint评审会（SM主持）
  ├─ AI Demo演示（截图+流程跑通+问题清单）
  ├─ PO商业价值审视
  └─ 产出 Sprint Review报告
       │
       ▼
Sprint回顾会（SM主持）
  ├─ 团队回顾本Sprint问题
  ├─ 讨论改进方案
  └─ 产出 Sprint Retrospective报告
       │
       ▼
Sprint把关校验（G-SM-01~06）
  └─ 产出Sprint把关报告 + 下一Sprint启动/版本集成
```

### 4.2 Scrum 4事件

| 事件 | 时机 | 主持 | 产出 |
|------|------|------|------|
| Sprint启动会（计划会） | Sprint第一天 | SM | SPRINT-BACKLOG.yml |
| AI每日立会 | 每阶段开始时 | SM自动生成 | Sprint进度报告 |
| Sprint评审会 | Sprint最后一天 | SM | Sprint Review报告 |
| Sprint回顾会 | 评审会后 | SM | Sprint Retrospective报告 |

## 五、DoD（Definition of Done）

### 5.1 DoD 6项

| DoD项 | 检查内容 | 校验方 |
|-------|---------|--------|
| DoD-1 代码可运行 | npm run build通过 | SM |
| DoD-2 运行时验证通过 | build+test+dev启动+页面访问+菜单跳转+数据保存+后置条件+流程跑通 全通过 | SM |
| DoD-3 测试通过 | 五层测试通过（契约+单元+集成+E2E+可用性） | QA |
| DoD-4 后置条件实现 | FN后置条件全部翻译为代码并生效 | FD+SM |
| DoD-5 人确认 | 人确认通过（按human-confirm-protocol） | PM |
| DoD-6 Demo报告生成 | AI Demo报告含截图+流程跑通证据+问题清单 | SM |

### 5.2 DoD铁律

**SM-01：Sprint DoD不可降级**——DoD 6项不可跳过任何一项，不达标必须返工。

## 六、Sprint间依赖管理

### 6.1 依赖类型

| 类型 | 描述 | 处理 |
|------|------|------|
| data_dependency | S2需要S1的数据结构/Store | S1 DoD含数据契约定义；S2启动前SM校验契约存在 |
| component_dependency | S2需要S1的通用组件 | S1开发时抽取共享组件；S2启动前SM校验组件可用 |
| scenario_dependency | S2的场景闭环依赖S1的场景 | S1场景必须跑通验收；S2启动前SM运行S1场景前置验证 |

### 6.2 阻塞处理

- 若S1未达DoD，S2不得启动（G-SM-03阻塞）
- 若S1部分完成，PO重新评估是否拆分S2或调整S2范围
- 阻塞超过2天，SM触发defect-reflow流程

---

## 七、障碍管理

### 7.1 障碍类型与处理

| 障碍类型 | 处理方式 |
|---------|---------|
| 技术障碍（FD遇技术问题） | 升级到Arch |
| 需求障碍（BA需求不明确） | 升级到PO确认 |
| 设计障碍（UX设计有分歧） | 升级到PM协调 |
| 依赖障碍（Sprint间依赖未就绪） | 升级到PM调整Sprint顺序 |
| 工具障碍（构建/测试环境问题） | SM直接处理 |

### 7.2 升级规则

**SM-03：障碍1天未解必须升级**——障碍超过1天未解决必须升级到PM（版本守护人），不可隐瞒。

## 十、Sprint学习与Velocity

### 10.1 Sprint Retrospective

SM主持回顾会，产出：
- 本Sprint问题清单
- 改进方案
- 上次问题改进检视
- 经验提炼（追加到lessons-learned）

### 10.2 Velocity记录

| 指标 | 说明 |
|------|------|
| 实际交付页面数 | 计划vs实际 |
| 实际工时 | 计划vs实际 |
| 阻塞时长 | 影响交付的阻塞总时长 |
| DoD达标率 | 6项达标比例 |

Velocity记录用于下一版本PO规划时的Sprint拆解参考。

## 十二、三级把关升级机制

```
Sprint级问题（3次DoD未达标/连续2次验证失败/依赖阻塞>2天/Demo含P0/障碍>1天）
  ↓ 升级到
版本级（PM介入，决定调整Sprint范围或触发defect-reflow）
  ↓ 升级到
项目级（PO介入，决定调整路线图或重新规划）
  ↓ 升级到
人决策（PO请求人确认，按human-confirm-protocol）
```
