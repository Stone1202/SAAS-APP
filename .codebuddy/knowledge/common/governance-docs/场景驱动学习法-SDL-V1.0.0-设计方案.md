# 场景驱动学习法（Scenario-Driven Learning）V1.0.0 设计方案

> 版本：V1.0.0 | 日期：2026-07-20 | 作者：PM Agent + BA Agent

---

## 一、为什么需要 SDL？

### 1.1 传统 learn-domain 的局限

learn-domain V3.4.0 的流程是：

```
源文档 → 抓取 → 主题提取 → 场景提取 → 7部分产物 → API学习 → Review → 存储
```

这个流程的核心问题是 **"先有内容，后有场景"**——场景是从抓取到的内容中被动提取的，而非主动定义。导致：

| 问题 | 表现 | 根因 |
|------|------|------|
| **场景碎片化** | 场景清单散乱，缺乏主干逻辑 | 场景来源于文档结构，非业务逻辑 |
| **业务问题失焦** | 知识库描述了"有什么"而非"解决什么" | 缺少「商业问题→场景→API」的推导链 |
| **跨域割裂** | 不同领域知识相互独立，不知如何协作 | 缺少跨域衔接的显式建模 |
| **角色视角缺失** | 只看接口不看人，同一场景不同角色需求不同 | 缺少按角色的场景细分 |
| **BA难以消费** | BA加载后不知道这个知识在什么情况下用 | 缺少「触发条件→场景地图→API调度」的导航 |

### 1.2 SDL 的核心理念

```
传统学习：源文档 → 提取知识 → 知识库（被动，文档驱动）
SDL学习：商业问题 → 场景定义 → 能力映射 → 知识库（主动，场景驱动）
```

**SDL 的三个根本转变：**

1. **问题先行**：不先问"这个领域有什么？"，而先问"这个领域解决什么商业问题？"
2. **场景为纲**：以完整的业务场景为组织单元，API/规则/状态机都是场景的附属品
3. **可消费性优先**：BA加载领域知识后，应该能立刻回答"我的需求属于哪个场景？"
   而非"我该用哪个API？"

## 二、SDL V1.0.0 核心架构

### 2.1 五层结构

```
┌─────────────────────────────────────────────────────┐
│                 Layer 0: 商业问题                    │
│  "这个领域帮企业解决什么痛点和商业目标？"              │
│  每个问题：痛点 → 价值主张 → 证据/数据                │
├─────────────────────────────────────────────────────┤
│                 Layer 1: 场景地图                    │
│  "要实现这个商业价值，需要经过哪些业务场景？"           │
│  每个场景：触发条件 → 参与者 → API链 → 结果          │
├─────────────────────────────────────────────────────┤
│                 Layer 2: 跨域衔接                    │
│  "这个领域的场景和哪些其他领域有数据/流程/状态联动？"   │
│  每个衔接：from场景 → to场景 → 传递内容 → 触发方式    │
├─────────────────────────────────────────────────────┤
│                 Layer 3: 角色视角                    │
│  "同一个场景，不同角色看到什么、操作什么、关心什么？"   │
│  每个视角：角色 → 可执行操作 → 关注的指标/KPI         │
├─────────────────────────────────────────────────────┤
│                 Layer 4: 能力映射                    │
│  "支撑这些场景需要哪些API/规则/状态机/信息流？"        │
│  （传统learn-domain的7部分+API学习产物，按场景索引）   │
└─────────────────────────────────────────────────────┘
```

### 2.2 与传统 learn-domain 的映射

| SDL 层 | 对应传统产物 | 变化 |
|--------|-------------|------|
| Layer 0: 商业问题 | **新增** | 从"描述是什么"升级为"解决什么" |
| Layer 1: 场景地图 | 主题清单 + 场景清单（增强） | 场景从被动提取→主动定义，含触发条件+参与者+完整API链 |
| Layer 2: 跨域衔接 | **新增** | 显式建模领域间的数据/流程/状态联动 |
| Layer 3: 角色视角 | 业务操作矩阵（增强） | 矩阵从静态→动态，含每个角色的KPI/关注点 |
| Layer 4: 能力映射 | Part1-13产物（索引增强） | 每项产物标注关联场景ID，可场景化加载 |

### 2.3 SDL vs 传统学习 差异对比

| 维度 | 传统 learn-domain V3.4.0 | SDL V1.0.0 |
|------|--------------------------|------------|
| 起点 | 源文档URL | 商业问题定义 |
| 组织方式 | 按产物类型（泳道/流程/信息流...） | 按场景（每个场景=完整闭环） |
| 场景来源 | AI从文档中提取 | AI推理+文档验证 |
| BA加载方式 | 关键词匹配→加载整个.yml | 场景ID匹配→加载特定场景的能力映射 |
| 跨域关系 | 隐式（BA自行判断） | 显式（cross_domain_bridges建模） |
| 可消费性 | BA需通读全文才能找到相关部分 | BA看场景地图即可定位 |

## 三、SDL V1.0.0 工作流（learn-domain V4.0.0）

### 3.1 新增阶段概览

```
V3.4.0: Step1→1.5→2→3→4→4.5→4.6→5→6→7→8
V4.0.0: Step0→1→1.5→2→2.5→3→4→4.5→4.6→5→6→7→8
         ↑                ↑
    新增SDL-0         新增SDL-2.5
    (商业问题发散)     (跨域衔接+角色视角)
```

### 3.2 Step0: 商业问题发散（SDL 核心新增）

```
┌──────────────────────────────────────────────────┐
│ Step0: 商业问题发散（SDL Layer 0）                 │
│ Owner: BA Agent                                  │
│ 输入: --domain + --category + --focus            │
│ 输出: 商业问题清单（business_problems）            │
│                                                  │
│ AI 执行3个子步骤：                                │
│                                                  │
│ 0a. 领域角色推断：                                │
│   - 这个领域涉及哪些业务角色？                      │
│   - 谁是付费方？谁是使用方？谁是受益方？             │
│   - 每个角色的核心诉求是什么？                      │
│                                                  │
│ 0b. 商业问题推导（每个问题回答5问）：               │
│   Q1: 这个角色面临什么核心痛点？                    │
│   Q2: 不做这件事的后果是什么？（pain_point）        │
│   Q3: 引入这个能力后能带来什么价值？（value）        │
│   Q4: 价值可量化吗？（evidence: 行业数据/案例）     │
│   Q5: 这个问题在SCRM场景下如何体现？（scrm_relevance）│
│                                                  │
│ 0c. 问题优先级排序：                              │
│   - 按SCRM相关性+通用性+可解决性综合排序            │
│   - 标注 priority: high/medium/low               │
│   - 生成问题依赖图（哪个问题是哪个的前置）          │
│                                                  │
│ 产出格式（参考 volcano-smart-outbound）：          │
│ business_problems:                               │
│   - id: "BP-{领域}-001"                          │
│     problem: "一句话描述商业问题"                   │
│     pain_point: "不做这件事的后果"                  │
│     value: "引入能力后的价值"                       │
│     evidence: "证据（行业数据/案例/AI推理）"        │
│     priority: "high"                             │
│     scrm_relevance: "在SCRM场景下的相关性"          │
│     related_problems: ["BP-XXX-002"]  # 依赖问题   │
└──────────────────────────────────────────────────┘
```

### 3.3 Step2.5: 跨域衔接 + 角色视角（SDL Layer 2+3）

```
┌──────────────────────────────────────────────────┐
│ Step2.5: 跨域衔接 + 角色视角（SDL Layer 2+3）      │
│ Owner: BA Agent + Arch Agent                     │
│ 输入: 场景地图 + DOMAIN-INDEX.yml（全量领域）      │
│ 输出: cross_domain_bridges + role_perspectives    │
│                                                  │
│ 2.5a. 跨域衔接建模（Cross-Domain Bridges）：       │
│   AI扫描所有已学领域，主动发现跨域联动关系：         │
│                                                  │
│   衔接类型（5种）：                               │
│   ① 数据衔接：A域输出数据 → B域输入数据            │
│     例：微信账号体系的 openid → 微信支付的用户标识   │
│   ② 流程衔接：A域场景是B域场景的前置/后置           │
│     例：商户入网(易宝) → 资金收付(易宝)            │
│   ③ 状态衔接：A域状态变化触发B域场景               │
│     例：客户加粉(企微) → 触发外呼欢迎(火山外呼)     │
│   ④ 渠道衔接：A域作为B域的消息/触达渠道             │
│     例：企微消息触达 + 火山外呼语音触达 → 双通道    │
│   ⑤ 降级衔接：A域不可用时降级到B域                 │
│     例：外呼未接通 → 降级企微消息                  │
│                                                  │
│   产出格式：                                      │
│   cross_domain_bridges:                          │
│     - bridge_id: "CDB-{from_domain}-{to_domain}-001"│
│       from: {domain, scene_id}                   │
│       to: {domain, scene_id}                     │
│       bridge_type: "data/flow/state/channel/fallback"│
│       content: "传递的数据/流程/状态"               │
│       trigger: "触发条件"                          │
│       scrm_value: "在SCRM中的业务价值"              │
│                                                  │
│ 2.5b. 角色视角建模（Role Perspectives）：          │
│   对场景地图中每个场景，展开为角色视角：             │
│                                                  │
│   每个角色回答5个问题：                            │
│   Q1: 在这个场景中，这个角色需要做什么操作？          │
│   Q2: 操作的输入/输出是什么？                       │
│   Q3: 操作成功/失败后的下一步是什么？                │
│   Q4: 这个角色关心什么KPI/指标？                    │
│   Q5: 这个角色最大的痛点是什么？（如信息不全/操作繁琐）│
│                                                  │
│   产出格式：                                      │
│   role_perspectives:                             │
│     - scene_id: "SC-XXX-001"                     │
│       scene_name: "场景名"                        │
│       perspectives:                              │
│         - role: "运营人员"                        │
│           operations: [...]                      │
│           kpis: ["线索转化率", "任务完成率"]       │
│           pains: ["名单格式不统一"]                │
│         - role: "客户"                            │
│           operations: [...]                      │
│           kpis: ["等待时间", "问题解决率"]          │
│           pains: ["重复接听多次骚扰电话"]            │
└──────────────────────────────────────────────────┘
```

### 3.4 增强：Step3 场景地图（SDL Layer 1）

传统 Step3 场景提取是被动的——从文档内容中识别场景。SDL Step3 是主动的——基于 Step0 的商业问题，**主动构建**场景地图，然后用文档内容**验证和补充**。

```
SDL Step3: 场景构建（主动→验证模式）

1. 基于 Step0 的商业问题，推导场景骨架
   - 每个商业问题 → 至少1个核心场景
   - 场景之间建立依赖关系（哪个场景是哪个的前置）
   - 生成"场景依赖图"

2. 为每个场景标注：
   - 触发条件（什么事件/条件触发这个场景？）
   - 业务闭环（从触发到结束的完整闭环是什么？）
   - 参与者角色（哪些角色参与？）
   - 期望结果（这个场景成功完成的标志是什么？）

3. 用抓取到的文档内容验证和完善场景
   - 文档中是否有这个场景的API支撑？
   - 场景的API链是否完整？（缺少的标注gap）
   - 文档中是否有额外的子场景？→ 补充到场景地图

4. 与传统Step3的区别：
   传统：文档场景 → 提取 → 场景清单
   SDL： 商业问题 → 推导场景 → 文档验证 → 场景地图
```

### 3.5 BA/Arch 集成增强

```
BA 需求分析时 SDL 加载优先级：
1. 用户描述需求 → Step0 匹配商业问题（BP） → "这个需求对应哪个商业问题？"
2. 商业问题 → Step2.5 匹配场景地图 → "这个问题的解决方案是什么场景？"
3. 场景地图 → Step2.5 加载跨域衔接 → "需要联动哪些其他领域？"
4. 场景 → Layer4 加载该场景的能力映射 → "需要哪些API/规则/状态机？"
5. 角色视角 → "这个需求的用户角色下，具体的操作和关注点是什么？"

Arch 架构设计时 SDL 加载优先级：
1. 场景地图 → 跨域衔接 → "需要设计哪些领域间的数据同步/事件传递？"
2. 能力映射 → API链 → "接口之间的参数流转如何设计？"
3. 商业问题 → 价值量化 → "架构决策的ROI依据是什么？"
```

### 4.3 SDL 重学执行策略

**核心原则：增量增强，不推倒重来。**

已有的 Part1-13（7部分产物+API学习产物+主题/场景清单）**全部保留**，增量添加 SDL 四层：

1. **Layer 0（商业问题）**：新增 `business_problems` 区块，AI从现有知识中推理
2. **Layer 1（场景地图）**：现有场景清单增强为 `scenario_maps`（场景含完整API链+触发条件+参与者+闭环）
3. **Layer 2（跨域衔接）**：新增 `cross_domain_bridges`，AI扫描全领域发现衔接
4. **Layer 3（角色视角）**：新增 `role_perspectives`，每个场景×角色展开
5. **Layer 4（能力映射）**：现有 Part1-13 全部保留，只是新增 `related_scenes` 索引字段

**版本规则：**
- SDL首次应用到已有领域：major+1（如 v1.0.0 → v2.0.0）
- SDL同版本内完善：minor+1（如 v2.0.0 → v2.1.0）
