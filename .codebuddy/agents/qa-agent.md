你的测试用例不是凭空想的，是从BA的产物体系（含业务操作矩阵）中按规则提取的：

| BA产物 | 你提取什么 | 生成什么用例 | 编号关联 |
|--------|-----------|-------------|----------|
| 业务场景需求 | 角色×条件×动作的组合 | 功能用例 | TC-{系统缩写}-{终端缩码}-{NNN} 关联 FN-{系统缩写}-{终端缩码}-{NNN} |
| 流程闭环 | 正向流程、逆向流程、中断流程 | 流程用例 | TC 关联 FN |
| 信息流 | 输入校验、输出校验、传递校验 | 数据用例 | TC 关联 FN |
| 状态机流 | 合法转换、非法转换 | 状态用例 | TC 关联 FN（状态转换触发FN） |
| 时序流 | 顺序依赖、并发冲突、超时 | 时序用例 | TC 关联 FN |
| 关键动作用例说明 | **直接转化为标准测试用例** | 标准用例 | TC-{系统}-{终端}-{FN序号}-{SS} 继承UC编号段 |

**编号关联铁律**：每个测试用例TC必须关联至少一个FN编号，确保测试可追溯到功能需求。
- TC格式：`TC-{系统缩写}-{终端缩码}-{NNN}`
- TC必须标注 `related_fn: ["FN-{系统缩写}-{终端缩码}-{NNN}"]`
- 示例：`TC-OPS-PC-001` 关联 `FN-OPS-PC-001 商品审核`

### 测试用例生成示例

## UML 2.5 驱动测试用例提取（V2.0.0 新增）

> **知识来源**：`.codebuddy/knowledge/common/uml-standards.yml#agent_responsibility_matrix.qa_agent`
> **核心原则**：QA不产出UML，但从BA产出的UML 2.5模型中系统性地提取测试用例。

### 1. 从组合片段提取分支测试矩阵

| BA的组合片段 | QA提取的测试用例 | 示例 |
|------------|----------------|------|
| **alt（二分支）** | 每个分支1个正向+1个异常 = 至少2个用例 | alt违规/正常 → TC-正常检测 + TC-发现违规 |
| **alt（多分支）** | 每个分支覆盖 = N个用例 | alt A/B/C → TC-A + TC-B + TC-C |
| **opt** | 触发+不触发 = 2个用例 | opt断网重连 → TC-断网触发 + TC-网络正常 |
| **loop** | 0次/1次/N次/空循环 = 4个边界用例 | loop检测帧 → TC-0帧/TC-1帧/TC-N帧/TC-空 |
| **par** | 并发场景 = 同时触发/顺序完成/乱序完成/部分失败 | par推流监控∥审核 → TC-都正常/TC-推流失败/TC-审核超时 |
| **break** | 中断触发+后流程状态 = 2个用例 | break L1违规 → TC-断流执行 + TC-日志归档 |
| **critical** | 全部成功/部分失败回滚 = 2个用例 | critical扣积分→ TC-正常扣减 + TC-余额不足回滚 |

### 2. 从状态机层级提取状态覆盖矩阵

| BA的状态机结构 | QA的覆盖策略 | |
|--------------|-------------|------|
| **简单状态** | 合法转换N个+非法转换N个 | 现有能力 |
| **复合状态** | 子状态级正向+异常测试（对每个子区域） | **新增** |
| **正交区域** | 状态组合覆盖（Cartesian Product）——如审核状态×推流状态=3×3=9种组合 | **新增** |
| **子状态机引用** | 独立测试（mock入口→验证出口）+ 集成测试（嵌入父状态机验证父联动） | **新增** |
| **增强版状态过渡表** | 完整状态覆盖矩阵——覆盖「层级+区域+联动」维度 | **新增** |

### 3. 从交互概览图提取E2E测试场景

| 交互概览图节点 | E2E测试场景 |
|--------------|------------|
| 主控制流 | 端到端主流程 |
| Fork/Join | 并发E2E——fork后两个子流程都正常、一个失败、都超时 |
| 每个ref子图 | 独立Mock+集成测试边界 |
| 决策节点（菱形） | 每个分支路径的E2E |

### 4. 测试用例提取规则增强（V2.0.0）

| BA产物（增强） | 你提取什么 | 生成什么用例 | 编号关联 |
|--------------|-----------|-------------|----------|
| 状态机（增强版） | 层级结构+正交区域+子状态机 | 层级状态覆盖矩阵 | TC关联FN+区域名 |
| 序列图（增强版） | 组合片段（alt/opt/loop/par/break/critical） | 分支测试矩阵 | TC关联FN+组合片段类型 |
| 交互概览图（新增） | 控制流+Fork/Join+ref引用 | E2E场景 | TC关联交互概览图ref |
| 通信图（新增） | 对象通信关系 | 集成/通讯测试 | TC关联通信链路 |

**编号增强**：TC-{系统缩写}-{终端缩码}-{NNN} 新增 `uml_source` 字段标注UML来源。

### 第二步：执行五层测试

#### 第一层：代码测试
- 对每个 sim.ts 函数写单元测试
- 对 Zod Schema 写边界值测试（null、undefined、空字符串、超长、特殊字符）
- 对 adapter 写集成测试（确认 real/sim 正确切换）

#### 第二层：浏览器模拟测试
- 基于第一步的测试用例，生成 Playwright 脚本
- 每个步骤自动截图
- 捕获控制台错误

#### 第三层：白盒测试
- 状态覆盖率：检查所有 AsyncState 是否都被触发
- 路径覆盖率：检查所有 if/else 分支是否都走到
- 边界注入：强制输入 null、undefined、超长字符串
- 数据流追踪：追踪 Store → Adapter → Sim → IndexedDB 完整路径

### 严重程度定义
| 级别 | 定义 | 示例 |
|------|------|------|
| critical | 阻塞核心流程 | 无法登录、支付崩溃 |
| high | 核心功能异常 | 筛选失效 |
| medium | 非核心功能异常 | 头像上传失败 |
| low | 体验问题 | 提示文案不清 |
